## 三、上机前必做的三件事（判据细节）

| 检查 | 判据 / 坑 |
|---|---|
| 测前清日志：`op=logclear` 广播（**不用重启微信**） | LogX 有 5000 行上限，写满是**环形覆盖**不是停写。清日志用广播，别 force-stop |
| `sh wxgroup/dev.sh sync` 报 `[STALE] apk_path` **不等于没注入** | 实测 STALE 时模块照样正常加载。**判据是日志里有没有 `installed`**，不是 sync 输出。无脑跑 `_lspfix.py` 每次白花 30 秒；只有「一条模块日志都没有」时才需要 |
| 微信必须在前台 | 后台时**广播不投递**，静默失败 |

判据：日志出现 `SNS_TAG installed` / `K9 installed` 才说明新代码真加载了。
⚠️ 装新包常不重载：`force-stop` + `am start` **做两次**。

## 四、探针速查（模块内广播，不用重新编译就能查状态）

```bash
adb shell am broadcast -a com.lx.wxgroup.action.PROBE \
  --es op <op> --es sub <sub> [--el id <long>] [--ei n <int>] -p com.tencent.mm
```

⛔ **`label sub=sql` 不会自己开库**（2026-10-25 真机定案，害我白跑 4 版脚本）：
它查的是**已收集的 db 实例池**，池子靠 `sub=on` 挂钩子在「微信开库那一刻」抓。
**微信每次冷启动（日志出现 `main package loaded`）进程重建 ⇒ 池子清零**，
之后所有查询只回一行 `LABEL sql: no db instance (先 sub=on 开窗口)`，**不报错、不出数据**。
症状极像「表没这字段 / SQL 写错了」，实际是窗口没开。正确顺序：
```bash
am broadcast … --es op label --es sub on --ei sec 180      # ① 先开窗口
am shell am start -n com.tencent.mm/.ui.LauncherUI          # ② 拉起进程触发开库
# ③ 日志出现 db ready / LABEL 就绪行后，再发 sub=sql 查询
```
⚠️ 与「微信后台不投递广播、要先 `am start`」是**两个不同的坑**，别混。
现成封装：`tools/_r21c_verify_hint6.py` 的 `open_window()` + 遇 `no db instance` 自动重开。

⚠️ **op 路由是两层**：`op` 选功能域，`sub` 选子命令；少数域还有第三层 `sub2`（如 `op=quiet sub=pat sub2=cls`）。
⚠️ `snsg dump` 的 `flag` 是**归档快照**（恒为 2），不代表当前值；查当前用 `snsg flags`。
⚠️ `snsg dump` / `one` 的输出**没有统一前缀**，grep 别按前缀过滤。

### 4.1 ⭐ 静态反编译取证（找不到 hook 锚点时的**首选**，别再蹲运行时探针）
运行时 hook（手势/监听器/栈）抓不到微信类名时，直接扫 dex，**1 分钟出真类名**：
```bash
adb shell pm path com.tencent.mm                 # → base.apk（379MB，pull 只要 16 秒）
python tools/_r4_dexscan.py                      # 解压 15 个 dex 搜关键词（中英文都试）
python tools/_r4_dexref.py classes4.dex patted   # 反查「哪个类的哪个方法引用了这个字符串」
python tools/_r4_dexref.py methods classes4.dex zx2.j          # 拿方法签名（参数/返回值）
python tools/_r4_dexref.py callers classes4.dex "Lzx2/j;->d"   # 拿调用点（上层是谁）
```
- 纯 Python 二进制解析 dex，1 秒出结果。**别用 dexdump**（反汇编几分钟、输出几百 MB）。
- ⚠️ 中文提示常是格式串拼出来的（`拍了拍` 搜不到）→ **改搜英文常量**（`patted` / `sendPatMsg`）。
- 拿到混淆名后**务必运行时再校验一次**（如 `op=quiet sub=pat sub2=cls`），确认这台机器上类还在。

### 4.2 ⚠️ 需要**指令级**反汇编时（宽表是唯一的坑）

要找「某个字段在哪个方法里被写」「这个方法到底调了谁」，就得自己解指令流。
**宽表错 1 unit，后面所有指令全部地址漂移**，而且错误会伪装成「看起来合理但结论相反」。

- ✅ **用 `tools/_r7_improve_verify.py`**（已用 androguard 全量 54362 方法逐条 diff，
  地址/宽度/助记符 100% 一致；含闭合自校验与分支目标落点校验）。
  ```python
  import sys; sys.path.insert(0,'tools')
  from _r7_q import load, decode
  d = load("classes3.dex")
  for addr, txt, tgt in decode(d, "Lcom/xxx/SomeClass;", "methodName"):
      print("[%4d] %-46s %s" % (addr, txt, ("-> [%d]" % tgt) if tgt is not None else ""))
  ```
- ❌ **别再用 `/tmp/_dex4.py` 那类手写宽表**：实测 15 个 opcode 宽度写错
  （`0x02/0x03/0x05/0x06/0x08/0x09` move 族、`0x14` const、`0x17` const-wide/32、
  `0x21` array-length、`0xFA-0xFF`、`0x7B-0x8F` 转换族），全 dex 抽样错误率 18.3%。
  尤其 `0x14 const` 规范是 3 units（常被写成 2），一个方法里只要出现一次就整段错位。
- **两个必须查的自校验**：① 末条 `addr + width == insns_size` 精确闭合；
  ② 每个分支目标必须落在指令边界上。任一条不满足就说明宽表错了，**不要相信后续结论**。
- ⚠️ `class_data_item` 里 field/method_idx 是**差分编码**，且 `direct_methods` 与
  `virtual_methods` 是**两个独立的差分序列**（各自从 0 累加）。合成一个累加器会让
  方法名整体串位 —— 表现为「某个类里冒出一堆别的类的方法名」。

## 五、自诊断读数顺序（SnsTag）

`snstag stat` 输出：`enabled / guard / tag / deleted / bound / added / binds / resolved / missed / lastMiss`

1. `binds > 0` —— 钩子活着（=0 说明 hook 没挂上或没限定到朋友圈）
2. `resolved ≈ binds` —— 解析通（真机 96.6%）
3. `missed` 接近 0，`lastMiss` 给出最后一条未解析的原因
4. `added > 0` 且 `hit=true` —— 标签打上且落点正确

### 8.1 为什么禁止并行改同一个源文件（实测约束）
1. 只有一台设备、一个微信进程、一份落盘日志；两个 agent 同时 `install` 互覆盖 APK，同时拉日志互污染。
2. 模块是单进程内联 hook，一个功能崩了带崩全部，并行改动无法归因。
3. LSPosed 模块重载不确定（`force-stop` 第一次常是旧代码），并行时更难判断跑的是谁的代码。

（**不同文件**并行改是允许且必须的，见 `CLAUDE.md` §四①。）

### 8.6 ⚠️ 后台子代理「team 托管成败」决定生死（2026-10-19 两次实测，派发前必看）

**后台子代理可用，但有条件**——成败取决于 **team 是否真的建起来**，不是「后台一定死」。

| 时间 | 结果 | teams 目录 | transcript |
|---|---|---|---|
| 01:29 那批（4 个后台子代理） | 全灭：`Status: killed` + 0 行 + 零文件改动 | `~/.workbuddy/teams/` **存在但为空** | 当天**没有** |
| 01:58 那批（3 个后台子代理） | ✅ 全部跑满 10+ 分钟正常产出 | `teams/_auto_<session>/` **有内容** | 正常写入（168KB） |

**根因**：后台子代理走 **team 托管**（agent_id 形如 `general-purpose-1@_auto_<session>`）。
team 没建起来 → 子代理成孤儿进程，跑几分钟被回收；`SendMessage` 也会报 `Not in a team`，
意味着**派出去后没法中途喂结论**。

**✅ 派发后 60 秒内做一次体检（判据，别等它自己死）**
```bash
ls ~/.workbuddy/teams/                                   # 应有 _auto_<session>/ 子目录
ls -la ~/.workbuddy/projects/.../<session>/subagents/     # 应有本次 agent_id 的 .jsonl 且在增长
```
- 两者都在 ⇒ **托管成功**，放心让它跑，主 agent 去干自己的活。
- 任一缺失 ⇒ **立刻停手**：`TaskStop` 掉，改派**前台**（不加 `run_in_background`），别浪费十几分钟。

**其它两条纪律**（与托管成败无关，都要遵守）
1. 给子代理的 prompt 里**要求「先落盘再分析」**（第一步就 Write 文件），万一被中断也留下可用产物。
2. 收工用**文件 mtime / `git status`** 核对真产出（别只看它返回的那几行报告）。
