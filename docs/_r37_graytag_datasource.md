## §1 问题定义：为什么现有三个候选判据全部**不能**用

灰标要回答的问题只有一句：**这条动态是不是「作者（或服务端）主动删掉了」？**
它的代价是不对称的 —— **错打（正常动态被标 `[删除已拦截]`）远严重于漏打**。
`SnsDeletedTagLogic.kt:46` 自己就把这条写死了：「打错标签比打不上糟得多」。
⇒ 判据选型必须**偏保守**，且**只接受「有正向证据」才打标**。

### 1.1 ❌ 判据候选 A：`sourceType` 的位变化（含「10→8」/「2→0」/「0」）

**为什么直觉上诱人**：时间线门槛就是 `sourceType & 2 != 0`（`SnsTimelineSrcLogic.kt:28`），
被删 ⇒ 不进时间线 ⇒ 自然是位被清了。

**反例（三条，逐条都是真机/代码事实）**

| 反例 | 事实 | 出处 |
|---|---|---|
| A-1 **方向反了** | 受控实验 verity\|1 删前 `src=2`，真实刷新后是 **`2 → 10`（位变多）**，不是变少 | `派发审计台账.md:2094`、`:2161` |
| A-2 **那个变化是模块自己写的** | `2→10` = `patchAlbumBit` 的 `curSrc or ALBUM_BIT`（`ALBUM_BIT=8`），由 `onSnsUpdateAfter` 在 `st != 0 && (st & 8)==0 && isAlbumTarget(id)` 时同步触发 | `SnsTimelineSourceFix.kt:365-366`、`SnsGuard.kt:332-339` |
| A-3 **位被清 ≠ 被删** | `src=0`（死来源）与 `src=4`（自己私密）**天生**没有 bit1；verity 名下早期 3 条就是 `type=2 src=0`，其中 2 条**从未被删** | `SnsTimelineSrcLogic.kt:16-17`、`docs/conclusions/moments.md:232-236` |

**⛔ R31h 事故本体**（`GroupDb.kt:516-536` 逐字记录，非二手转述）：
旧判据 = `T_SNS ∪ (T_SRC WHERE fixed_orig IS NOT NULL)`。补位范围扩到全量可见动态后
`fixed_orig` 涨到 **3447 条**，而它**只写不删** ⇒ **3447 条正常动态全部被判「已删除」**。
根因被 `GroupDb.kt:524-527` 钉住：**「`fixed_orig` 这一个字段背了两个语义」**
（① 补位台账「这条我动过」= 全部动态量级；② 已删判据「这条被删了」= 个位数）。

⇒ **结构性结论**：任何「我（模块）在这行上写过东西」的记录，都**不能**当删除判据。
因为模块写库的动机是「补位」，与「被删」只在旧版本里**碰巧**重合。

### 1.2 ❌ 判据候选 B：补位日志 / 补位计数（`SNS srcfix` / `SNS albumpatch` / `re-fix after burst`）

与 A 同源，但更糟：**补位是常态，删除是例外**。
- `reFixAfterClear` 每轮同步都跑，真机 `fixed=1596`（`派发审计台账.md:1982`、`R37-12` 段）。
- `SNS srcfix ... 8 -> 10` 日志 305→311 行全量扫，**受控实验目标 id 0 命中**（`:2059`、`:2163`）
  ⇒ 补位日志对目标**既无正例也无反例**，是**纯噪声**。
- ⛔ `SnsTimelineSourceFix.fixAlbum:214-236` 的注释更是直接记了一起同源事故：
  在 `already` 分支登记「已经带 bit8 的行」⇒ `held=229` 里 229 条几乎全被标已删
  ⇒ 用户报障「正常朋友圈也被插入已阻止删除」。注释原文：**「把『可见』写成了『已删除』」**。

⇒ 补位侧的**任何**信号都是「越写越脏」的方向，必须整类排除。

### 1.3 ❌ 判据候选 C：DELETE 拦截（`SNS blocked delete` / `T_SNS` 归档）

**这一条不是「错」，是「覆盖不到」**——它是对的，但只对**自己删自己的动态**成立。

- `T_SNS`(sns_archive) 是灰标**当前唯一**数据源：
  `SnsDeletedTag.loadIds → GroupDb.snsTagIds → SELECT sns_id FROM sns_archive`
  （`SnsDeletedTag.kt:1690`、`GroupDb.kt:537-544`）。
- 写入链唯一：`onDelete`/`onExecSql → saveAsync → GroupDb.archiveSns`
  （`SnsGuard.kt:433`/`:470` → `:642-657` → `GroupDb.kt:417`），全项目**仅此一处**调用 `archiveSns`。
- 而好友删动态**不走 DELETE**：受控实验 `blocked=1 archived=0 deleted=8` 全程不动
  （`派发审计台账.md:2163`），DELETE 通道对这个场景**结构上收不到事件**。
- ⛔ 附带风险：`SnsSql.matchDeleteCall` 已知会把某类 `whereClause` 误取首参溢出成
  `Long.MAX_VALUE`（`派发审计台账.md:1900-1903`），**假 id 也会进 `T_SNS`** ⇒ 连 C 自己都不干净。

⇒ C **保留**（自己删动态靠它），但**不能扩展到好友删动态**。

### 1.4 ⛔ 一句话红线（本文件后续所有设计的公理）

> **判据只能来自「服务端告诉客户端这条没了」或「客户端观测到这条从服务端视图里消失」，
> 绝不能来自「模块在这行上动过手」或「这行的本地位被改过」。**

### 1.5 ⛔ **单行字段路线整类判死**（2026-11-02 21:24 / 21:28 真机实测，三条独立证据）

> 这一节是 2026-11-02 主会话新取证后**追加**的，它把 §1.1 从「用错了台账」
> 升级为「**这一整类判据没有区分度**」。所有基于单行字段的方向（含 `serverExtFlag`
> 变体）在此一并判死。

#### 证据 1：全表 `sourceType` 分布 —— 「位缺失」在正常动态里遍地都是

21:24 真机 `select sourceType,count(*) from SnsInfo group by sourceType order by c desc`：

| sourceType | 行数 | 与「被删」假设形态的关系 |
|---|---|---|
| `2` | **158,853** | 正常（bit1） |
| **`8`** | **29,685** | ⛔ = 「`10` 清 bit1」的结果形态，与「被删」**同形** |
| `10` | 28,477 | 正常（bit1\|bit3） |
| `130` | 16,742 | 正常**折叠**动态（`128\|2`，`docs/conclusions/moments.md:206-207`） |
| **`0`** | **16,330** | ⛔ = 死来源，与「`2` 清 bit1」的结果形态**同形** |
| `22`/`84`/`86`/`70`/`68`/`12`/`6`/`4` | 200 | 杂值 |

⇒ 只看「bit1 没了」或「src 是 8 / 0」，**会命中 29,685 + 16,330 ≈ 4.6 万条正常动态**。
而真实被删的是**个位数**。⇒ **判据的信噪比约 1:5000，不可用。**
且最近 12 条按 `createTime desc` 里 10 条是 `2`、2 条是 `0`
⇒ ⛔ **`SnsTimelineSourceFix.kt:221` 那句「正常动态 sourceType 天生就是 10」与实测不符**
（实测 `2` 是绝对多数）。凡引用该注释推理的地方一律降级为「**假设**」。

#### 证据 2：同一作者 10 条**字段完全同形** —— 四个字段全无区分度

verity（`wxid_xlrbelf6hv0w22`）名下最近 10 条，逐条：

- **10 条全部** `serverExtFlag=1`、`localFlag=2`、`subType=0`
- `sourceType` 分布：`8`×4、`0`×5、`2`×1
- 被删那条（`-3401376990577159657`）**夹在 `8` 之间**，与其它未被删的兄弟行
  **只有 `createTime` / `snsId` 不同，其余字段逐字相同**

⇒ **`sourceType` / `serverExtFlag` / `localFlag` / `subType` 四字段在这 10 条上的
区分度均为零**。这解释了两个现象：为什么 `SnsGuard` 挂 DELETE 收不到事件，
为什么扫表也扫不出痕迹 —— **微信删好友动态时，本地行压根不留删除痕迹**，
只在「时间线列表数据源 / 缓存」层面剔除。

#### 证据 3：模块自己在**全表批量** `8 → 10` —— 位变化无法归因到单一主体

21:28:34 现场：
```
SNS srcfix snsId=-3411920557204098535 8 -> 10 rows=1
SNS srcfix snsId=-3411921946274557426 8 -> 10 rows=1    …（连续多条，全是 8 -> 10）
SNS srcstat snap=3000 fixed=500 skip=3500 priv=3 gone=0 fail=0 err=0 new=0 pages=30 ledger=7686 held=2834
```
`pages=30` / `fixed=500` / `skip=3500` ⇒ 这是 `run()` 的**按页全表扫描**
（`PAGE_SIZE=100` × `MAX_SNAPSHOT_PAGES=30`，`SnsTimelineSrcLogic.kt:54-58`），
补的是台账里所有缺 bit1 的行，**与某条动态是否被删毫无因果关系**。
目标动态此刻仍是 `8`，**只是还没轮到它那一页**。

⇒ ⛔ **必须作废的一处反向推断**：交付 1 §2 P2 ⑤ 已记 —— 台账 R37-17 曾把
「用户刷新后 `src 2→10`」当作「模块确实对这条动了手」的证据，
**现在看只是全表批量补位的副作用**。

#### 三个写入主体 ⇒ 归因不可能

| 主体 | 动作 | 与「被删」的因果 |
|---|---|---|
| 微信 | `UPDATE ... SET sourceType = sourceType & -3`（清 bit1）、`& -9`（清 bit3，按作者） | 部分相关，但**每轮都对所有行跑**（`SnsTimelineSourceFix.kt:511-514`） |
| 模块 | `patchAlbumBit`：`curSrc \| 8`（`SnsTimelineSourceFix.kt:365`） | **无关**（日常补位） |
| 模块 | `reFixAfterClear`：`sourceType \| 10` 分块批量（`SnsTimelineSourceFix.kt:558`） | **无关**（全表扫描补位） |

⇒ **观察到一个位变化，既无法反推是谁写的，也无法反推为什么写。**
⛔ 结论（写死，后续不再讨论）：

> **「单行字段判据」整类（`sourceType` / `serverExtFlag` / `localFlag` / `subType`
> 的绝对值或位变化，含任何 `src` / `serverExtFlag` 变体）= 不可行。**
> 判据必须落在**集合级 / 接口级**。

### H1 / 方向 A 时间线列表差集：「同窗口曾经出现 → 本次不再出现」

**原理**：时间线首屏/刷新吃的是响应内存对象 `zb5.f`（`LinkedList<SnsObject>`，
`SnsTimelineMerge.kt:22-28`）。若某 id 曾在**同一可信窗口**里出现过、之后**连续多轮**不在，
说明服务端不再下发它 ⇒ 被删。代码里已有同款机制：`SnsTimelineMerge.onBeforeResp`
收集 `respIds`（`:139-143`），`SnsTimelineMergeLogic.pickMissing(rotated, respIds, ...)`（`:182`）。

**可观测信号**：每轮 `respIds`（id 集合）+ `SNS-INJECT-STAT ... resp=<size>`（`:240-241`）。

**⛔ 头号误报源：分页 + 有限窗口导致的「假消失」**

不是理论风险，**本项目已栽过，且有事故数据**：
- `GroupDb.kt:552-556` 逐字记录：用「不在响应里」当判据时
  `SNS-INJECT-STAT attempt=24 ok=24 emptyBuf=0`，**24 条候选全部能从 `SnsInfo` 读回 attrBuf**
  ⇒ **全是正常动态，没有一条被删**。根因：**时间线分页（一页 10 条）**，
  200 条候选里必然有 190 条不在当前页 ⇒ 「不在响应里」被判成「被删」。
- 叠加滚动位置 / header-footer 偏移（`SnsDeletedTagLogic.kt:329-331` 实测偏移 ≤1），
  差集里绝大多数是「根本没被请求到」，不是「被删了」。

#### ⭐ 窗口可信度判定（本设计的核心，`W` 条件）

**第一原则：窗口必须按 `createTime` 绝对区间定义，绝不能按「前 N 条」定义。**
理由：时间线按 `createTime desc` 排列，**顶部插入新动态会让所有旧条目整体下移**。
按「前 N 条」定义窗口时，只要来一条新动态，原来的第 N 条就被挤出窗口 ⇒ **假消失**。
按 createTime 绝对区间定义则不受影响（`createTime` 是服务端下发的、不可变的时间戳）。

定义一次观察 `k` 的窗口 `W_k = [ctBot_k, ctTop_k]`（闭区间，`createTime` 秒）：
- `ctTop_k` = 本次观察到的最大 `createTime`（窗口顶锚点）
- `ctBot_k` = 本次观察到的最小 `createTime`（窗口底锚点）

**该 id 的消失「可信」必须同时满足 C1~C5，缺一即「放弃」（不打标、不记账）：**

| # | 条件 | 为什么必须 | 不满足时的失效形态 |
|---|---|---|---|
| **C1 顶锚未变** | `ctTop_k == ctTop_{k-1}` | 顶部进了新动态 ⇒ 说明服务端有新数据，窗口内容本就应变化，此刻的差集**不可归因** | 把「被新动态挤出」当成「被删」 |
| **C2 底覆盖** | `id.ct > ctBot_k + MARGIN`（`MARGIN` 建议 = 1 页跨度，保守取 600s） | 排除「该 id 在窗口**下沿之外**、本就没被翻到」 | 分页边界抖动 ⇒ 假消失 |
| **C3 顶覆盖** | `id.ct < ctTop_k - MARGIN` | 同 C2，排除上沿 | 同上 |
| **C4 双轮确认** | 连续 **≥2 次独立同步轮次**都缺失（不是同一次刷新的重复采样） | 单次缺失 = 抖动 | 一次抖动就打标 |
| **C5 本地行仍在** | 本地 `SnsInfo` 该 snsId 行仍在（按 id 点查，不是按 sourceType） | 行没了 = **物理删除**，那是 `T_SNS` 那条路，不是本判据；混进来会重复计算 | 与 `blocked` 语义打架（见 §3.3 互斥项） |
| **C6 非空响应** | 本轮 `respIds.size > 0` | ⛔ `SnsTimelineMerge.kt:145-150` 明写 `c3.N` 会被**每秒调用**且**列表可能为空**（增量/心跳类请求）⇒ 空响应下的「缺失」是**无信息量**的 | 拿心跳空包当「全被删了」 |

**⛔ 两条实现纪律（直接来自本项目的前车之鉴）**
1. **必须按 id 集合比对，绝不按 `size` 比对。**
   前车之鉴（K7）：`snaps` 仅 `size != n` 才重算 ⇒ **条数不变时重排永冻**。
   集合大小相同但成员全变是完全可能的 ⇒ `size` 相同就跳过检查 = 静默漏判。
2. **差集的基准是「上一次同一窗口的观察集合」，不是「本地全表」。**
   本地 `SnsInfo` 有 17.6 万行，其中 `src=8`/`0` 等不在时间线的约 **4.6 万条**（§1.5 证据 1）
   ⇒ 拿全表当基准，差集里绝大多数是**本来就不进时间线的正常动态**。

**实现成本**：中（`respIds` 收集已有，需新增窗口账本 + 每轮快照落盘）。
**纯客户端**：是。
**裁决**：⚠️ **可行但脆弱**。C1~C6 六条全过的场景在真机上有多常见**未验证**
（尤其 C1「顶锚未变」——朋友圈活跃时几乎每次刷新顶部都会变）
⇒ **不作主判据**，作**兜底交叉校验**。

**可证伪探针**（测 C1 的可满足率 —— 这是 H1 能否实用的生死数据）：
```bash
# 连续 5 轮同步，每轮记 ctTop / ctBot / respIds.size
adb shell am broadcast -a com.lx.wxgroup.action.PROBE -p com.tencent.mm \
  --es op snsg --es sub merge
# 若 5 轮里 ctTop 变化 ≥1 次（常态）⇒ C1 经常不满足 ⇒ H1 的可用窗口很窄，不宜作主判据
```

### H2 ❌ **不可行**（已被 2026-11-02 真机数据判死，原设计作废）

原设计：「`sourceType` bit1 被清**且未被模块补回**」。
⛔ **整类作废**，理由见 §1.5 的三条独立证据（全表 `8`=29,685 / `0`=16,330；
同作者 10 条字段完全同形；模块全表批量 `8→10`）。

补记原来的四条误报面（保留作历史记录，**均已升级为「已被实测证实」**而非「理论风险」）：
1. 补位会立刻抹掉信号（350ms 静默后 `reFixAfterClear` 写回，`SnsGuard.kt:354-367`）；
2. 微信第二种清位写法 `& -9` 模块不认领（`SnsTimelineSrcLogic.kt:81-89` 只匹配 `& -3`）；
3. `src=0`/`src=4` 天生无 bit1 —— **现已量化**：`0` 有 16,330 条；
4. 两个写入主体（微信 + 模块）无法归因 —— **现已现场抓到**模块批量 `8→10`。

**裁决**：❌ **不可用**。⛔ **任何 `sourceType` / `serverExtFlag` / `localFlag` / `subType`
的单行字段变体同理不可用**，不再逐一列举。

**可证伪探针**（若有人仍想救这条路线，用这条先测区分度）：
```bash

# 同时 dump 该作者的兄弟行（未被删的）。若两者字段同形 ⇒ 单行字段无区分度，路线判死
```

### H3 服务端同步回包里删除了该 id —— 拆成两支，**一支否掉、一支是主判据**

#### H3a ❌ 时间线响应（`c3.N`，getType=211，`q54.zb5`）里带删除列表

**静态取证已否掉**，不是假设：
`docs/conclusions/moments.md:227` —— 「时间线响应体 `q54/zb5` 字段全是 LinkedList/嵌套对象，
**没有 deletedIds / tombstone 形态**」。同段 `:228` 补刀：「现场：好友删除后零 `SNS delete seen (off)`，
本地行与 `localFlag` 均未被改动 ⇒ 靠『少返回』，不靠『多下发一条删除记录』」。
`SnsTimelineMerge` 侧实际能拿到的也只有**正向列表** `zb5.f`（`SnsTimelineMerge.kt:130-143`）。

⇒ **H3a 明确否掉**，无需再取证。

#### H3b ✅ **同步 NetScene（`x2`，scene 256，`mmsnssync`）的删除动作** —— 本节的主判据

**原理（静态取证，两条独立落点）**：`NetSceneSnsSync`（`com.tencent.mm.plugin.sns.model.x2`，
`super = modelbase/k1`，`getType()=214`，CGI `/cgi-bin/micromsg-bin/mmsnssync`，`<init>(I)V` 单 int 参数
= scene；`docs/_r25_moments_bg.md:44-50`）内部有**两个只在「整条动态被删」时才走的方法**：

| 方法 | 名字 | 落点 | 语义 |

### H4 / 方向 B 好友相册接口返回集合 vs 本地集合较差（**接口级差集**）

**原理**：好友个人相册页走**网络拉取**，不是读库渲染的旁路
（`docs/_r30_lane2_album_page.md:607`：「这与主时间线（吃响应内存对象 `zb5.f` → `oh3/p`）是**两套通路**」）。

**⭐ 为什么它的窗口可信度比方向 A 高一个量级**
| 维度 | 方向 A（时间线） | 方向 B（好友相册） |
|---|---|---|
| 集合规模 | 全站混合，17.6 万行、分页 | **单作者**，通常几条~几十条 |
| 顶部插入干扰 | ⛔ 严重（任何人的新动态都会挤走我的窗口条目） | ✅ 无（只含该作者） |
| 分页覆盖 | 一页 10 条，覆盖极小 | 一个作者的历史常常**一页可覆盖** |
| 窗口可比性 | 需要 C1 顶锚未变（活跃时几乎不满足） | 只需确认覆盖到该 id 的 `createTime` |

**锚点（已取证，且已挂上）**：`h3.N(Lq54/jc5;Ljava/lang/String;)V`，getType=212，
`q54/jc5` 的字段 `f` 与 `zb5.f` **同名同型** `LinkedList<SnsObject>`

#### ⭐ 方向 B 的窗口可信度（`G` 条件，缺一即放弃）

| # | 条件 | 为什么必须 | 不满足时的失效形态 |

### H5 本地行 `createTime` 落在「已完整拉取过的历史窗口内」且本次全量比对缺失

**原理**：若我们确信「`[t0, t1]` 这段时间的动态已被完整拉取过」（有全量快照），
那么该窗口内某行的消失就不可能是分页造成的。

**误报面（⛔ 这条有一个绕不过去的自举问题）**
- **没有任何「窗口已完整拉取」的可信标记**。`SnsTimelineSrcLogic` 的快照是
  **分页扫描且带上限**（`PAGE_SIZE=100`、`MAX_SNAPSHOT_PAGES=30`，
  `SnsTimelineSrcLogic.kt:54-58`）⇒ 一次快照**最多 3000 行**，而真机 `SnsInfo` 是
  **17.6 万行**（`SnsTimelineSourceFix.kt:269`）。⇒ 「完整」这个前提**永远不成立**。
- 真机印证：台账 `:1982` 的 `srcstat snap=3000 fixed=500 skip=3500` —— **扫 3000 就停了**，
  后面 3500 行是 skip。用这种快照做「全量比对」⇒ 缺失里绝大多数是**根本没扫到**。
- 时间窗还会被**新动态持续推高**：`createTime` 落在窗口内 ≠ 当时就拉过。

**实现成本**：高（要建可信的窗口完整性账本）。
**纯客户端**：是。
**裁决**：❌ **不可用**（在 17.6 万行的量级下，窗口可信度无法建立）。

**可证伪探针**（若有人坚持 H5，用这条先测窗口可信度）：

| H6b | `commentflag==2` 读回 | 行 | ✅ | 覆盖面残缺 + 业务零读取 | 低 | 是 | ❌ 仅旁证 |
| H6c | `d2.S7` 清位批次 | 行 | 否 | 每轮 100% 命中，零区分度 | 低 | 是 | ❌ 判死 |
| H6d | 作者维度整体消失 | — | ✅ | 人工，模块拿不到 | — | — | ❌ 仅人工确认 |

**⭐ 一句话**：**行字段路线全灭**（实测判死）；可用的只剩**接口级**与**集合级**两条路，
其中只有 H3b 是**正向证据**，方向 A/B 都是**缺席推断**（必须配窗口可信度条件才敢用）。

## §3 推荐方案

### 3.1 选型（2026-11-02 修订：主判据**不落在任何单行字段上**）

⛔ **前置**：`sourceType` / `serverExtFlag` / `localFlag` / `subType` 的绝对值与位变化
**一律不得作为纳入判据**（§1.5 实测判死）。本节所有判据只吃**接口事件**与**集合差集**。

- **主判据 = H3b / C-1**：`NetSceneSnsSync`（`x2`，scene 256）的 `x2#U`/`x2#O` 删除动作，
  **双通道确认**（H6a 并入）。它是**服务端下发的正向事件**，不是缺席推断。
- **交叉校验 = 方向 B（H4）**：好友相册接口返回集合 vs 本地集合较差，
  **必须过 G1~G5 五条窗口可信度**才采信。
- **兜底交叉校验 = 方向 A（H1）**：时间线同窗口差集，**必须过 C1~C6 六条**才采信。
  它的 C1（顶锚未变）在活跃朋友圈上大概率不满足 ⇒ 定位兜底，不指望它。
- **保留**现有 `T_SNS`（物理 DELETE 拦截）判据 —— 覆盖「自己删自己的动态」，与新判据**并集**，语义不变。

**⛔ 唯一例外（允许的保守用法）**：`isPrivate`（`sourceType & 4`）只作**排除闸门**，
不作**纳入判据**。二者方向不同：排除闸门的误报方向是「少打标」，符合 §4.1 的保守公理；
纳入判据的误报方向是「错打标」，不允许。

### 3.2 ⛔ 存储设计：**新开一张表，不给 `T_SRC` 加列**

`GroupDb.kt:533-535` 给出的 R31h 方案 B 是「给 `T_SRC` 加一列记录「该 snsId 在不在最近一次
服务端回包里」」。**本 lane 不建议照做**，理由就是 `GroupDb.kt:524-527` 自己钉住的那个根因：

> 「根因不是 SQL 写错，而是 **`fixed_orig` 这一个字段背了两个语义**」

给 `T_SRC` 加列，等于让 `sns_visible_src` 这**一行**同时承载
① 曾经可见台账（量级 = 全部动态）② 补位回滚依据 ③ **已删判据**。
任何一处「顺手记一笔」都会再次污染判据 —— 这正是 R31h 的形态。

⇒ 建议**新表** `sns_del_ev`（事件账本，语义单一）：

```
sns_del_ev (
    sns_id      INTEGER NOT NULL PRIMARY KEY,   -- snsId（结构化参数 / 差集元素，均非行字段推导）
    ev_at       INTEGER NOT NULL,               -- 首次命中的 wall-clock
    ev_kind     INTEGER NOT NULL,               -- 1=U/O 服务端事件  2=相册差集(方向B)  3=时间线差集(方向A)
    ev_src      INTEGER NOT NULL,               -- kind=1 时的位标记: 1=U(updateSnsDel) 2=O(processSnsDelAction)
    ev_rounds   INTEGER NOT NULL DEFAULT 1,     -- 连续命中的独立轮次（≥2 才确认）
    win_ok      INTEGER NOT NULL DEFAULT 0,     -- 窗口可信度是否通过: kind=2 → G1~G5；kind=3 → C1~C6
    local_row   INTEGER NOT NULL DEFAULT 0,     -- 命中时本地 SnsInfo 行是否还在（按 id 点查，1=在）
    confirmed   INTEGER NOT NULL DEFAULT 0,     -- 是否已确认打标（0/1）
    revoked_at  INTEGER                         -- 被 restored 撤销的时刻（非 null = 已撤销）
)
```
⛔ `win_ok` 这一列是**方向 A/B 的命门**：`kind=2/3` 的记录**必须** `win_ok=1` 才允许进入确认流程，
`win_ok=0` 的记录**只能计数、永远不许打标** —— 把「窗口没钉住」这件事**显式落库**，
而不是靠调用方自觉（这正是 C-4 / R31h 那条路翻车的地方）。

三条设计约束（逐条对应已发生的事故）：
1. **`sns_del_ev` 只由「服务端下发的删除动作」写入**，永远不由 srcfix / 补位 / 归档写
   ⇒ 与 `T_SRC`（补位台账）**物理隔离**，结构上不可能重演 R31h。
2. **`confirmed` 与 `revoked_at` 互斥**：`revoked_at != null` ⇒ 判据**立即**失效，
   且**同一 snsId 在 N 天内不允许再次 confirmed**（防抖动重复打标）。
3. **打标读端仍是 `GroupDb.snsTagIds` 的单点**（`SnsDeletedTag.kt:1690`），
   只在**那一个方法**里改成 `T_SNS ∪ (sns_del_ev WHERE confirmed=1 AND revoked_at IS NULL)`。
   ⛔ **其它任何地方**（`listArchiveIds` 注入候选、`snsLedgerIds` 相册回捞）**一律不改**，
   保持 R31h 收窄后的语义不变（`GroupDb.kt:552-558`）。

### 3.3 判据表

**字段定义（七个，逐条可观测；⛔ 无一个来自单行字段推导）**

| 字段 | 含义 | 来源 |
|---|---|---|
| `B` = blocked | 本地物理 DELETE 被拦 ⇒ 行在 `T_SNS` 里 | `GroupDb.kt:537`（现状） |
| `S` = syncDel | `x2#U` 或 `x2#O` 以该 snsId 为参数被调用 | **新增**（H3b / C-1，接口事件） |
| `S2` = syncDelDual | `U` 与 `O` **同轮**都命中同一 snsId | **新增**（H6a） |
| `A` = albumMiss ∧ **G1~G5 全过** | 好友相册响应 `jc5.f` 缺该 id，**且**窗口可信度五条全过 | **新增**（方向 B；`win_ok=1`） |
| `T` = timelineMiss ∧ **C1~C6 全过** | 时间线同窗口差集缺该 id，**且**窗口可信度六条全过 | **新增**（方向 A；`win_ok=1`） |
| `R` = restored | 该 id 在**任一**后续 `zb5.f` / `jc5.f` 里重新出现 | **新增**（C-2 复用现成的 `respIds`） |
| `L` = localRow | 命中瞬间本地 `SnsInfo` **行是否还在**（按 id 点查，**不看任何字段值**） | 现有 `probe`（`SnsTimelineSourceFix.kt:1024`） |

⛔ **`A` / `T` 的定义里已经含 `win_ok=1`**：窗口可信度没过 = 该信号**不存在**（不是「弱证据」）。
不允许出现「窗口没钉住但先记一笔」的中间态 —— 那正是 R31h 的污染路径。

**⛔ 互斥关系（先写死，再写表 —— 这些不能并列成 AND 列表）**

- **`B` 与 `R` 互斥**：`B` 的前提是「行还在库里（我们拦住了）」；`R` 是「服务端又把它发回来了」。
  两者同时为真在语义上矛盾 ⇒ 出现时**以 `R` 为准**（撤销 `B` 对应的标记），并打一条 warn
  （说明旧归档可能是误拦）。
- **`S` 与 `R` 互斥**：`R` 出现 ⇒ 立即 `revoked_at = now`，`confirmed` 强制回 0，**不看 `ev_rounds`**。
- **`B` 与 `S` 可共存但不叠加**：`B ∧ S` 时只记一次（打标是布尔量，不是计数）。
  它们描述的是**两条不同的删除通道**（自删 / 他删），不是同一件事的两条证据。
- **`L` 不是独立判据**：`L=0`（行已物理消失）时 `S` 仍然成立（服务端删了，微信随后清了本地行），
  只是**无法通过注入还原** ⇒ 打标照旧，但不进 `listArchiveIds` 注入候选。

**判据表（信号组合 → 动作）**

| # | 信号组合 | 动作 | 理由 |
|---|---|---|---|
| **0** | **`R`（任一时刻，无论其它）** | ❌ **撤销**：`revoked_at=now`、`confirmed=0` | **互斥项优先级最高**；重现 ⇒ 之前判错了 |
| 1 | `S2`（U∧O 同轮） ∧ `L=1` ∧ `¬R` | ✅ **打标**（立即） | 服务端删除动作**双通道**确认 + 本地行还在 ⇒ 最强组合 |
| 2 | `S` ∧ `ev_rounds ≥ 2` ∧ `L=1` ∧ `¬R` | ✅ **打标** | 单通道但连续两轮同步都命中 ⇒ 排除单次抖动 |
| 3 | `S` ∧ `ev_rounds = 1` ∧ `L=1` ∧ `¬R` | ⏸ **不打标**（`ev_rounds++`，等待） | 保守：单轮单点证据不采信 |
| 4 | `S` ∧ `A`（方向 B，G1~G5 全过） ∧ `¬R` | ✅ **打标**（即使 `ev_rounds=1`） | 独立交叉校验成立 ⇒ 可放宽轮次 |
| 5 | `A` ∧ `ev_rounds ≥ 2`（无 `S`） ∧ `L=1` ∧ `¬R` | ⏸ **暂不打标**（进观察态，打 info 日志） | ⚠️ 纯缺席推断 ⇒ **默认不打标**；这是保守侧默认值，只有 team-lead 明确接受漏标风险时才可开 |
| 6 | `T`（方向 A，C1~C6 全过） | ⏸ **仅计数，不打标** | C1（顶锚未变）在活跃朋友圈上大概率不满足 ⇒ 定位兜底，不单独采信 |
| 7 | `S` ∧ `L=0` ∧ `¬R` | ✅ **打标**，但**不进注入候选** | 服务端确实删了；本地行没了没法还原 |
| 8 | `B` ∧ `¬R` | ✅ **打标**（沿用现状） | 自己删自己的动态，`T_SNS` 已覆盖 |
| 9 | `S` ∧ ¬`A` ∧ ¬`T` ∧ `ev_rounds < 2` ∧ `¬R` | ⏸ **不打标**（等待） | 只有单点证据，无交叉校验 |
| 10 | `isPrivate` 为真 或 `snsId == 0` | ⛔ **永不打标** | 私密闸门（**只作排除**，见 §3.1 末段）+ 哨兵值闸门（`SnsDeletedTagLogic.kt:81-82`） |
| 11 | 单轮任一信号命中数 > `MAX_CONFIRM_PER_ROUND`（建议 20） | ⛔ **整轮放弃 + warn 日志** | 防「一夜之间几百条」重演（`SnsTimelineSourceFix.kt:415-419` 的 512 条事故、`GroupDb.kt:521` 的 3447 条事故）；正常删除是**个位数**事件 |

**⛔ 表的使用纪律**
- **第 0 行（互斥撤销）优先级最高**，先于 1~8 执行；第 10/11 行是**绝对闸门**，也先于 1~8。
- 「打标」= 只写 `sns_del_ev.confirmed=1`；**界面打标仍由 `SnsDeletedTag` 的
  View↔数据对账**（`SnsDeletedTagLogic.pickByAuthor`/`matchName`）决定，本设计**不改**那一层。
- **`A`/`T` 未过窗口可信度时，该信号视为不存在**，不写 `ev_rounds`、不进观察态
  ⇒ 避免出现「记了一堆不可信候选，后来某轮碰巧凑够轮次」的污染路径。

## §4 误报 / 漏报代价分析与保守侧兜底

### 4.1 代价不对称（设计的第一公理）

| 方向 | 用户看到 | 代价 |
|---|---|---|
| **误报（错打）** | **正常动态被插上 `[删除已拦截]` 灰标** | ⛔ **严重**。用户会以为模块在乱标/乱改他的朋友圈；R31h 事故就是 3447 条全被标，构成**用户报障**（`GroupDb.kt:521-522`） |
| **漏报（没打）** | 被删的动态没有标记 | 轻。功能「没生效」，但**界面无污染**，用户无感知 |

代码里同一取舍已经写死过三次，本设计沿用：
- `SnsDeletedTagLogic.kt:46`：「打错标签比打不上糟得多」；
- `SnsDeletedTagLogic.kt:326-327`：「宁可 `hits != 1` 返回 `-1` 让这一格不打标」；
- `SnsTimelineSourceFix.kt:154`（`AUTHOR_VIEW_CLS` 注释）：「失效形态被**故意**设计成可见的……`rows == 0` ⇒ 一个标签都不打。这是**保守**方向」。

⇒ **判据表 §3.3 里每一条「⏸ 不打标」都不是妥协，是设计目标。**

### 4.2 保守侧兜底（六条，逐条对应一个已知失效形态）

| # | 兜底 | 防的是什么 |
|---|---|---|
| D1 | **双通道 / 双轮次门槛**（`S2` 或 `ev_rounds ≥ 2`） | 单次抖动 ⇒ 单点证据不采信（判据表 3/8 行） |
| D2 | **`R`（重现）无条件撤销**，`revoked_at` 优先于一切 | 「删了又回来」/ 分页假消失 ⇒ 立刻止损（判据表**第 0 行**，优先级最高） |

| D5 | **物理隔离**：新表只由服务端删除动作写，srcfix/补位/归档**一律不写** | 结构上排除 R31h（一个字段背两个语义） |

### 4.3 已知的**必然漏报**（明写，不算缺陷）

1. **微信进程从未跑过 `mmsnssync`** 的时刻 ⇒ 无 `S` 信号 ⇒ 不打标（等下一次同步）。
2. **好友删动态后我方长时间没刷新**：`x2` 由微信自己的事件监听器触发
   （`docs/_r25_moments_bg.md:52-63`，`l93/q4.callback` → `new x2(256)`），
   刷新频率由微信决定 ⇒ 打标延迟是**分钟级**。
   （⚠️ 原先引用的「123 延迟数分钟后 `10→8`」这条**只能证明延迟**，
   **不能再当作「删除已落地」的证据** —— `src` 变化已不可归因，见 §1.5。）
3. **`x2#U`/`x2#O` 若只对自删触发（F1）** ⇒ H3b 整体作废，只剩 `T_SNS` 现状
   （即好友删动态**永远**打不上标）。这是 §5 必须先跑的生死实验。
4. **方向 B 的 G2 不满足**（目标 id 的 `ct` 落在相册响应覆盖区间之外）⇒ 该次放弃，不打标。
   ⛔ 这是**设计内的放弃**，不是 bug —— 见判据表第 6 行与 §3.1。

### 5.2 双向对照矩阵（2 × 2）

**轴 A = 开关**（`Keys.ANTIREVOKE_SNS`）；**轴 B = 好友是否真的删了**。

| | B1 好友真删（受控） | B2 好友不删（对照） |
|---|---|---|

| **A2 关** | **期望**：`sync-del` 仍出现（钩子与开关无关）但 `on()`=false ⇒ **不打标**，`deleted`/`painted` 不变。用于证明「信号采集」与「打标」两层是分开的 | **期望**：全零 |

**执行顺序（每格都要走 R37-13 定下的规程，`派发审计台账.md:2030-2034`）**
1. 好友发新动态（独特标记）→ 2. 我方滚到顶 dump **记下 `u=`** → 3. Python 换算**负 id**
   → 4. **按 id 查库存删前基线** —— ⚠️ 2026-11-02 修订：基线**只需存「行在」+ `createTime` + `snsId`**，
   **不要存 `src`/`serverExtFlag`/`localFlag`/`subType` 的期望值**（§1.5 已证这些字段无区分度，
   存了也没法比对，只会误导判读）
   → 5. 明确回「已记下，可以删」→ 6. 好友删 → 7. 我方**真实下拉刷新**（⛔ 不用 msync，免节流）
   → 8. 按 id 查库（**只查行在与否**）+ 抓 `sync-del`/`snstag stat`。

  ⇒ 那么「真删了却没标」就只能是**判据没命中**，不是渲染坏了。

### 6.3 一句话结论（2026-11-02 修订版）

> **① 单行字段路线整类判死**（`sourceType` / `serverExtFlag` / `localFlag` / `subType`）——
> 真机实测：全表 `8`=29,685 / `0`=16,330，同作者 10 条字段完全同形，模块还在全表批量 `8→10`。
> **判据只能落在接口级或集合级。**
>
> **② 主判据 = `NetSceneSnsSync`（`x2`，scene 256）的 `x2#U`/`x2#O` 删除动作** ——
> 服务端下发的**正向事件**（不是缺席推断），参数是结构化 snsId，不碰任何行字段，
> 且 `x2` 已被 `installAlbumSyncTrigger` 挂住 ⇒ 成本极低。
> 它**不落在 `sourceType` 上**，故不受上面三条新证据影响（§2 H3b 末的表已逐条核对）。
>
> **③ 交叉校验 = 方向 B（好友相册接口集合较差），必须过 G1~G5 窗口可信度；
> 兜底 = 方向 A（时间线同窗口差集），必须过 C1~C6。** 两者都是缺席推断 ⇒ 默认不打标。
>
> **④ 新信号落新表 `sns_del_ev`，`win_ok` 显式入库，绝不能回写 `T_SRC` / `fixed_orig`。**
>
> ⛔ **⑤ 生死项两个**：**F1**（`x2#U`/`x2#O` 是否覆盖好友删动态）与 **G2 可满足率**。
> 建议顺序：**先跑 G2（零成本、今天可测，见 §5.2 的 V9）→ 再决定要不要为 F1 加钩。**
