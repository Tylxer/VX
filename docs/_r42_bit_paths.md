# R42 实测：朋友圈动态在本地库里的两条「消失路径」

> 全部结论来自 2026-11-05 ~ 11-06 的真机实测，设备 `467cf5bc`（PJD110），微信 8.0.48/2588 GP。
> 涉及的数据一律用 `op=sql` 只读探针查得，写入行为一律来自 `SnsGuard` 六个钩子的计数与事件行。

## 0. 一句话结论

**动态在界面上消失，从来不是「行被删掉」，而是「`sourceType` 里对应的位被摘掉」。**
摘 bit1（`& -3`）= 时间线看不见；摘 bit3（`& -9`）= 好友主页相册看不见。
现有拦截（路线甲）只拦「把值写成 `0`」这一种动作，而这两个「从可见到不可见」的步骤**都不写 0**。

---

## 1. 位语义（已定案）

| 位 | 值 | 含义 |
|---|---|---|
| bit1 | `2` | 朋友圈**时间线**可见（唯一闸门） |
| bit3 | `8` | 该动态**当前在好友主页相册列表里**（记账位） |
| bit2 | `4` | 私密（`isPrivate`） |

典型取值：`2`=只在时间线、`10`=时间线+相册、`8`=只在相册、`0`=都不可见、`130`=`128+2`、`136`/`138` 等高位组合。

全库分布（2026-11-06 20:0x，`SnsInfo`）：

```
2    159,241
8     29,876
10    28,742
0     16,426
130   16,808
```

其中 **一年以上的**里：`2`=115,975、`10`=18,944、`8`=13,006、`130`=11,614、`0`=**仅 237**。
⇒ 老动态长期保持 bit3，说明**常规刷新不会无差别清 bit3**；`0` 极少，说明「彻底清零」是罕见事件（即删除）。

## 2. 三类动态的删除路径（全部实测）

| 类型 | `type` | 删除前 src | 轨迹 | 甲的结果 |
|---|---|---|---|---|
| 纯文字 | `2` | `2` | `2 → 0` | ✅ 拦 4 次（21:52:15 / 21:53:02 / 21:56:07 / 22:01:30） |
| 图片 | `1` | `10` | `10 → 8 → 0` | ❌ 零命中 |
| 视频 | `15` | `10` | `10 → 8 → 0` | ❌ 零命中 |

**类型不是变量**。`bit3` 的有无与 `type` 无关：10-27 那条纯文字（`type=2`）是 `src=8`，带 bit3。
决定走哪条路径的是**删除前的位型**，不是动态类型。

### 2.1 图片（19:35 发，19:42 删）
```
19:41:49  src=10

19:42:49  src=0    ← 8  & ~8   由 execSQL UPDATE ... sourceType & -9 触发
```
计数：`hit` 零增长、`zero` 零增长、`sqlSrc +4`。
时间线与主页最终均不可见。

### 2.2 视频（19:54 发，20:01 删）
```
19:58:23  src=2 → 10   ← 进好友主页触发加 bit3
20:00:54  src=10 → 8   ← update 写 8，放行
20:02:25  src=8  → 0   ← execSQL & -9
```
计数：`hit=2` 未增、`zero=2` 未增、`nonZero +12`、`sqlSrc +4`。
与图片逐字一致，包括「进主页时 `& -9` 空跑一次」这个细节。

## 3. 进好友主页时微信做了什么（AAA 对照，2026-11-06 20:14）

对象 `AA889900000`，名下有 3,051 条 `2`、300 条 `10`、264 条 `8`、105 条 `0`。

**一次进主页（约 20 秒）内的全部写入：**

| 动作 | 写什么 | 本次数量 | 甲 |
|---|---|---|---|
| 服务端返回了、本地无 bit3 → 加 | `2 → 10` | 有 | 放行（非零） |
| **服务端未返回、本地有 bit3 → 清 bit3** | **`10 → 2`** | **25 条**（`10` 从 325 降到 300） | 放行（非零） |
| 服务端未返回、本地是 `8` → 彻底清零 | `8 → 0` | **61 次**（`before=8 after=8 blk=1`） | ✅ 全部拦住 |

计数：`hit=61 blocked=61 nonZero=35 sqlSrc=0 sqlUnmatched=0`。
⚠️ `sqlSrc=0` ⇒ **清 bit3 走的是 `update` 写 `2`，不是 `& -9`**；那条裸 SQL 这次一次都没执行。

### 3.1 「不是按最近 N 条重算」

AAA 的 `10` 型里最早一条是 `1651043545` = **2022-04-27**，仍在相册位。
⇒ 不存在「只保留最近 N 条」的分页策略。被清的 25 条只能是「服务端这次没返回」。

### 3.2 界面为什么查不到

好友主页相册的查询条件：

```sql
SELECT ... FROM SnsInfo
WHERE userName=? AND sourceType IN (8,264,10,266,12,268,...) AND type IN (...)
```

那 64 个候选值**全部含 bit3**。所以：

- `10`（含 bit3）⇒ 查得到
- `2`（不含 bit3）⇒ 查不到，**哪怕 bit1 还在**
- `0` ⇒ 查不到

## 4. 四类写入与甲的关系（完整矩阵）

| 写入 | 场景 | 甲当前 | 甲应该 |
|---|---|---|---|
| `2 → 0` | 好友删除（无相册位） | ✅ 拦 | 拦 |
| `8 → 0` | 已删动态被彻底清零 | ✅ 拦 | 拦 |
| `10 → 8` | 好友删除（有相册位） | ❌ 放行 | **拦**（否则时间线丢失） |
| `10 → 2` | 进主页对账清 bit3 | ❌ 放行 | **拦**（否则主页丢失） |
| `0 → 2` / `2 → 10` / `0 → 8` | 加位（新入相册等） | 放行 | 放行（必须） |

现判据是 `if (st != 0) 放行`（`SnsGuard.kt:295`）—— 只认「写 0」，因此上表后两行必然漏。

## 5. 由此产生的两个产品结论

1. **6.2「删除后好友主页可见」曾被我判为不可做，现已推翻。**
   理由从「微信按最近 N 条重算、保不住」更正为「清 bit3 走 `update` 写 `2`，拦得住」。
   （21:45 之前的判断基于错误前提，作废。）

2. **拦 `& -9`：当前不做（用户 2026-11-06 20:29 决定方案 A）。**
   单独拦它无收益（清 bit3 主通道是 `update` 写 `2`，它当时根本没执行）；
   但在拦住写 `8` 之后，位型会停在 `10`，而该 SQL 的 WHERE 枚举里**含 `10`**
   （`sourceType in (8,264,10,266,12,268,...)`），理论上会把 `10` 削成 `2`。

   > ⚠️ 这一步是**推论，未实测** —— 现有甲拦不住 `10→8`，构造不出「位型停在 10 时执行 `& -9`」的场景。

   **方案 A（本次实现）= 拦写 `8` + 拦写 `2`，`& -9` 只识别不拦截。**
   预期效果边界：

   | 场景 | 时间线 | 好友主页 |
   |---|---|---|
   | 进主页对账（写 `2`） | ✅ | ✅（写 2 被拦，位型停 10） |
   | 好友删除（写 `8` + `& -9`） | ✅ | ⚠️ 可能丢（`& -9` 把 10 削成 2） |

   留观测：`& -9` 补识别并单独计数，新包上机后可直接验证它是否真会命中 `10`。

## 6. 已知取舍（无法用技术消除）

`10 → 2` 同时发生在「好友删除」与「好友改为私密/部分可见」两种场景，服务端信号完全相同
（都是「本次没返回」）。拦住它 ⇒ 两种情况下你都继续看得见。用户已确认接受该取舍。

## 7. 取证工具备忘

- 探针 `snsg sub=stat|block|blockstat|trace`、`op=sql`（只读）。
- `BLOCK ev` 字段：`before`=写前库里值、`after`=写后回查值、`keys`=ContentValues 列数、
  `C`=含 content、`A`=含 attrBuf、`blk`=摘键是否成功。
- `sql-unmatched` 原文：去重 + 上限 60 条，落盘长度 1500 字符（R42 放宽，原 200）。
- ⛔ `adb shell` 里 SQL 用 `createTime < N` 会被设备端 shell 吃掉（日志无任何 SQLX），改用 `between 0 and N`。
- ⛔ `SnsInfo` 列名是驼峰 `userName`，不是 `user_name`；`rcontact` 不在 sns 库。

## 8. 方案 A 真机验证结果（2026-11-06 21:18，已定案）

对象：`snsId=-3397825059229724135`（verity，`type=1` 图片），流程：发图 → 进主页（`2→10`）→ 删除 → 再进主页。

```
21:18:15  写 8 被拦       BLOCK drop  before=10  want=8  keys=18  blk=1
21:18:15  after 回查      after=10
21:19:38  & -9 执行       sqlClear9 4→10（进主页一次 6 条）
21:20:04  src 10 → 2      trace 采样
21:19:57  写 0 被拦       before=2  want=0  blk=1  after=2
21:20:19  查库            sourceType=2
```

计数：`drop seen=29 blocked=1 allow=28 unknown=0`；`hit=1 blocked=1`；`sqlClear9=10`。

### 8.1 结论

| 步骤 | 结果 |
|---|---|
| 好友删除清 bit1（写 `8`） | ✅ **新判据首次实证拦截**（`10→10`） |
| 进主页清 bit3（`& -9`） | ❌ 未拦（方案 A 边界外）→ `10→2` |
| 随后彻底清零（写 `0`） | ✅ 拦住 → 停在 `2` 而不是 `0` |

最终：**时间线可见、好友主页不可见**。

### 8.2 ⛔ 一条被证伪的判断

此前多次认为「`& -9` 只在好友删除流程出现」。本次实测：**进一次好友主页就执行 6 条**，其中一条正好命中目标动态。
⇒ 它的触发面比预想宽，方案 B 的副作用评估必须按「每次进主页都会执行」来算，不能按「只在删除时执行」。

### 8.3 实测的完整 SQL（方案 B 的设计依据）

```sql
UPDATE SnsInfo SET sourceType = sourceType & -9
 WHERE SnsInfo.userName="<好友>"
   AND (sourceType in (8,264,10,266,12,268,...,478))   -- 64 个值，全含 bit3，含 10
   AND  (snsId != 0  )
   AND  (snsId > A)  [AND (snsId < B)]                  -- 按 id 区间分页，不是全表
```

## 9. 方案 B 真机验证结果（2026-11-06 22:03，已定案）

对象 `snsId=-3397803690084199920`（verity，`type=1`），同流程：发 → 进主页（`2→10`）→ 删除 → 再进主页。

| 步骤 | 微信想写 | 结果 |
|---|---|---|
| 22:00:26 进主页 | `2→10` | ✅ 加位**放行**（不误拦），`src=10` |
| 22:01:49 对方删除 | `10→8`（砍 bit1） | ✅ 拦住 → `after=10`，**时间线还在** |
| 22:03:10/12 再进主页 | `10→2`×2（砍 bit3） | ✅ 拦住 → `after=10`，**主页还在** |
| 22:03 再进主页 | `& -9` SQL×8（首屏 + 分页） | ✅ `-9→-1` 全拦，`blkFail=0` |

**结论：`sourceType` 停在 `10`，时间线与好友主页同时可见。** 这正是方案 A 做不到的一格
（8.1 里 `& -9` 未被拦 ⇒ `10→2` ⇒ 主页消失），方案 B 补上后两处都保住。

计数：`drop seen=26 blocked=3 allow=23 unknown=0`、`afterOk=3 afterFail=0`、
`sqlClear9=8 sqlBlock9=8 blkFail=0`、`delSns=1 delRow=1`（**全程零 DELETE**）。

⛔ **反向对照已做（22:10）**：只关 B 层（`sns_sqlblock_off=true`）再进主页 ⇒ **主页消失、`src 10→2`**，
`sqlClear9` +2 / `sqlBlock9` 不变 / `blkOff` +2。⇒ **B 层是主页可见的必要条件**，不是冗余保险。
⚠️ 该实验还证明：这次 `10→2` **完全没走 ContentValues**（`drop blocked` 未增）⇒
**A 层看不见 SQL 通道的清位**，「拦了 `want=2` 就够了」是错的。详见 `docs/_r42_bit_b_report.md` §8。
详细时序与日志原文见 `docs/_r42_bit_b_report.md` §7。

### 9.1 记账边界（已知，不影响正确性）

「只有上界」的分页（`snsId < B`）`rangeKey` 解析不出 key，记成 `?`，
但**拦截照常生效**（计入 `sqlBlock9`）。只影响「同一批行被重试几次」的统计粒度。
