# R43 · 朋友圈视频导出 —— 落点取证（2026-11-07）

> 背景：用户要求导出「文字 + 图片 + 视频」。文字/图片已有（R26 真机 PASS），**视频缺失**。
> 历史只有手动探针 `imgdl` 能下，R42 拆除乙方案时随 `sns_archive` 归档表一并物理删除
> （`_r42_purge_report.md:95`）。当前自动导出链路固定写 `"jpg"`，只扫本地 sns 缓存。

## 一、判据（真机库实测，262581 行）

| 判据 | 结果 |
|---|---|
| `SnsInfo.type == 15` | **24517 行** |
| 其中 contain `snsvideodownload` | **24513 行 = 99.98%** |
| 非 type=15 但含 `snsvideodownload` | 242 行（0.09%，噪声） |

⇒ **`row.type == 15` 就是「朋友圈原生视频」判据**，置信度 99.98%，不需要解析 protobuf 结构。

⚠️ **推翻了既有注释**：`MomentsLogic.VIDEO_MARKS = listOf("stodownload")` 有两处错：
1. `stodownload` 主要出现在 **type=28 视频号分享**（`wxapp.tc.qq.com/251/2030x/`），不是朋友圈视频；
2. 真正的朋友圈视频域名是 **`szzjwxsns.video.qq.com/102/<n>/snsvideodownload`**，
   字符串 `snsvideodownload` **不包含** 子串 `stodownload` ⇒ 现有 `kindOfUrl` 对真视频返回 `UNKNOWN`（=不下）。

## 二、URL 形态（一条 type=15 动态的完整样本）

```
http://szzjwxsns.video.qq.com/102/20202/snsvideodownload?encfilekey=…&token=…&idx=1&bizid=1023&dotrans=9&dur=15&…
http://szzjwxsns.video.qq.com/102/20250/snsvideodownload?encfilekey=…&token=…&idx=1&bizid=1023&dotrans=0&…&ui=1&ut=…
```

- `20202` 带 `dur=<秒>` ⇒ **主视频源，优先取**
- `20250` 带 `ui=1&ut=…` ⇒ 备用源
- 两条都带 `token=` ⇒ **有有效期**，过期即不可下载

## 三、落点

- `GroupDb.SnsRow` **已含 `type: Int`**（`GroupDb.kt:326`），
  `SnsGuard.listCurrentSns` 的 SQL 也已 select 该列（`SnsGuard.kt:1107`）
  ⇒ **不需要改查询**，直接用 `row.type`。
- `MomentsLogic.extractUrls(blob)` 已能扫出这两条 URL（正则扫 UTF-8 串）。
- `MomentsLogic.fileNameFor(snsId, index, kind, ct)` 已能按 Content-Type 产出 `vid_<snsId>_<i>.mp4`。
- 缺的只有：类型判定入口、下载器、`MomentsExport` 的调用分支、独立开关。

## 四、真机实测（2026-11-07 22:5x，设备已 root，设备上 curl）

### 4.1 400 的根因 = 缺 User-Agent

同一条 type=15 动态（1.4 小时前）的 `/20202/` URL：

| 请求组合 | 结果 |
|---|---|
| 裸 URL | `400` ct=video/mp4 size=0 |
| **+ 微信 UA** | **`200` ct=video/mp4 size=9,614,961** |
| + Referer `http://weixin.qq.com/`（无 UA） | `400` |
| + Referer `https://servicewechat.com/`（无 UA） | `400` |
| UA + Referer | `200`（同上，**Referer 无影响**） |
| `/20250/` 裸 | `400` |
| `/20250/` + UA | `200` 但 **ct=image/jpg size=32,312** |

⇒ **唯一决定因素是 UA**。无 UA 恒 400，有 UA 恒 200。

#### UA 的判别粒度（第三轮实测，**决定性结论**）

| UA 值 | 结果 |
|---|---|
| `WeChat` | **200** 9,614,961 |
| `MicroMessenger` | **200** |
| `WeChat/arm64` | **200** |
| `wechat`（小写） | 400 |
| `Weixin` | 400 |
| `Mozilla/5.0` | 400 |
| `okhttp/4.9.0` | 400 |
| `Dalvik/2.1.0 (Linux; U; Android 13)` | 400 |
| `Android` | 400 |
| `curl/8.0` | 400 |
| 空串（不发 UA 头） | 200（**异常特例，不可依赖**） |

⇒ 判据 = **UA 含大小写敏感的 `WeChat` 或 `MicroMessenger`**。
⇒ ⛔ **不需要版本号 / 机型 / Chrome 版本**，这些字段不参与校验。
⇒ 实现上用常量 `WeChat/arm64` 即可，永不过期；不要硬编码 `8.0.48.2580(0x28003036)` 之类。

### 4.2 ⛔ 订正：`/20250/` 不是备用视频源，是封面图

`200` 但返回 `image/jpg` 32KB ⇒ 是**封面**，不是视频。
先前文档写的「20250 = 备用源」**作废**。设计上视频只取 `/20202/`。

### 4.3 token 有效期：7 天有效 / 30 天失效

| 动态年龄 | 结果 |
|---|---|
| 1.4 小时 | `200` 9.6 MB |
| 1 天 | `200` 1.0 MB |
| 3 天 | `200` 17 MB |
| 7 天 | `200`（总长 **77.8 MB**，curl 30s 只收到 31MB 即超时） |
| **30 天** | **`400` size=0** |

⇒ 有效期落在 7~30 天之间（14d/21d 未测）。
⇒ 老动态下载失败是**永久失败**，不能重试轰炸；7 天内的仍可补（回填轮有实际价值）。

### 4.4 体积量级

1 MB / 9.6 MB / 17 MB / **77.8 MB** ⇒ 单文件上限取 200 MB 有实测依据。
⚠️ 超时不能照抄 30s，77MB 在弱网下需更宽；且必须有总时限，不能挂死导出轮。

## 五、已排除的失败假设（不用再试）

- ❌ URL 被截断：已核对原始字节，URL 末尾 `uzid=7a1ca` 紧跟 protobuf 边界 `28 01 32 d2 02`，
  说明 `7a1ca` 就是完整值。
- ❌ Referer 缺失：加与不加结果相同。


## 五、建议开关

新增独立开关 `moments.copy_videos`（默认 **false**）：
与 `copy_images` 分开 —— 视频要联网、体积大，不应被图片开关顺带拖起来。

## 六、真机验证（2026-11-07 23:38）—— 链路通了，但下回来的是**密文**

### 6.1 探针输出（`sub=viddl`，生产同一函数）

```
VIDDL id=-3398536920689724692 gate=bypass type=15 hit=true url=有 outcome=copied
      bytes=9884961 file=…/落浔张桂凤(wxid_xij8e08lqr3e22)/2026-11-05-2141/vid_-3398536920689724692_0.mp4 ms=20910
```

判定链全部正确：`type=15` 命中、URL 提取到、HTTP 200、9.4MB 落盘、耗时 20.9s、tmp→rename 成功。

### 6.2 ⛔ 但文件不是 MP4，是**加密数据**

拉回本地分析（`.tmp/sns/v.mp4`，9,884,961 字节）：

| 检查项 | 结果 |
|---|---|
| 头部 16 字节 | `38 69 d3 90 2d 38 c0 ea ad ab 9e 51 41 f7 d2 a8`（高熵随机） |
| 熵 | **8.000 bits/byte**（理论上限 = 完全加密） |
| `ftyp` / `moov` / `mdat` | **全部 `-1`（不存在）** |
| 尾部 16 字节 | `b4 b4 b4 … b4 bc`（块填充） |

⇒ 下载到的是**密文**，**不能播放**。当前导出的 `.mp4` 无实用价值。

### 6.3 根因（与既有取证吻合）

微信 SNS CDN 的下载**不是**明文直传：`docs/_r10_cdn_api.md` / `_r14_ok0_n.md` 早已取证到
`CdnLogic$BatchSnsReqImageData` 携带 `decryptKey` / `fileKey`，解密发生在**微信 native 层**。
裸 HTTP（哪怕 UA 对了、拿到 200）只能得到密文 —— 这正是当初图片放弃 URL 路线、
改走「本地 sns 缓存索引直扫」的同一个原因（R19/R26）。

`encfilekey=` 参数名本身也印证：它是"加密文件 key"，不是鉴权参数。

### 6.4 已清理

设备上那个密文 `.mp4` 已删除（避免被当成可用视频）。
本地 `.tmp/sns/v.mp4` 留作分析样本。

### 6.5 下一步的三条路线（未开工，需决策）

| 路线 | 做法 | 代价 / 风险 |
|---|---|---|
| **A. hook 微信视频下载器** | 找 SNS 视频下载的落盘点，拿**解密后**的文件（等同于 R26 图片的「直扫缓存」思路） | 需新取证；但和图片链路同构，已有 R10/R14 的 decryptKey 线索可复用 |
| **B. 找播放后的明文缓存** | 微信播放过的视频可能落盘明文，扫那个目录 | 依赖用户点开播放；朋友圈视频是否缓存明文未验 |
| **C. 自己解密** | 用 `encfilekey` / `decryptKey` + 微信 AES 算法解 | 需逆向算法与参数派生，风险最高，微信升级易失效 |

⚠️ 路线 C 是唯一能纯离线批量做的，但也是最脆的。A/B 更稳，但都依赖微信自己的解密动作。

## 七、⭐ 决定性发现（2026-11-08 00:0x）：缓存里就是**明文完整 MP4**，A 路线可能不必做

### 7.1 `sight_*&enc*` 不是密文，是标准 MP4

微信 SNS 缓存根 `/sdcard/Android/data/com.tencent.mm/cache/<hash32>/sns/<a>/<b>/` 下，
视频文件名 `sight_<20位mediaId><hex后缀>&enc<10位数字>`。`&enc` **不是加密标志**。

三个现场样本（22:57-22:58 生成，即滚朋友圈那一刻自动落盘）：

| 文件 | size | 头 32B | moov | mdat |
|---|---|---|---|---|
| `sight_14851818046781395541…` | 4,246,691 | `ftyp isom mp41` | @32 | @21295 |
| `sight_15048749099634930388…` | 2,215,501 | `ftyp isom mp41` | @32 | @5491 |
| `sight_15048712562070008502…` | 13,489,836 | `ftyp isom mp41` | @32 | @18575 |

box 树精确覆盖到 EOF（拉回本地逐个解析）：
```
ftyp 28 + moov 5451 + free 8 + mdat 2210014 = 2,215,501 = 文件长度（零残留）
```
⇒ **完整、合法、可播放的 MP4**。与 §六 那个 9.4MB 密文（熵 8.0、无 box）**完全相反**。
差别就在：密文来自「裸 HTTP 直连 CDN」，明文来自「微信自己下载后落盘」。

### 7.2 mediaId 可从 `content` 精确反查（无需 CDN 回调）

三个 mediaId 在 `SnsInfo.content` 里各命中**唯一**一条 type=15 动态：

| mediaId | snsId | userName | type |
|---|---|---|---|
| 15048749099634930388 | -3397994974653697277 | wxid_qfcog70mfgxe22 | 15 |
| 15048712562070008502 | -3398031512421977341 | wxid_qfcog70mfgxe22 | 15 |
| 14851818046781395541 | -3594926027890027960 | hyq954168708 | 15 |

⇒ 与图片链路同构（R14 §4：`keys[1]` = mediaId = 文件名后缀），**不需要任何 CDN 回调**。

### 7.3 由此得出的两个判断

1. **A 路线（hook 视频下载器）的增量价值基本为零**：hook 的目的是拿「解密后的落盘文件」，
   而微信本来就把解密后的文件落在 `sns/` 缓存里 —— 能 hook 到的东西，扫目录就能拿到。
   且 `C2CDownloadResult.picCachePath` 在 R14 里实测**恒为空串**（native 不填），视频侧路径字段未取证。
2. **真正的约束不是解密，是「微信有没有下过」**：冷启清 `sns/` 缓存（R19 实测），
   只有本次运行期内滚到过的视频才在缓存里。当前设备只有 3 个 sight_ 文件，
   而名单内好友有 114 条视频动态 ⇒ **覆盖率是主要矛盾，不是技术可行性**。

## 八、⛔ 对照实验：后台同步 / 滚动 对「图片」与「视频」的效果完全不同（2026-11-08 00:05）

用户目标：**配合「定时刷新朋友圈」+「自动加载朋友圈」，保存特定好友的动态（文字+图片+视频）**。
为此测了两种触发方式对 SNS 缓存的实际影响。

### 8.1 后台同步 → 零媒体

微信退到桌面（`topResumedActivity=launcher`），手动投递 `msync sync`：
```
MSYNC OK scene=256 type=214 cgi=mmsnssync
```
同步前后：总文件 909 → **909**，`sight_` 3 → **3**，近 5 分钟新写文件 **0 个**。

⇒ **纯后台同步只更新 `SnsInfo` 元数据，不下载任何媒体文件。**

### 8.2 滚动朋友圈 → 图片有、视频没有

进 `ImproveSnsTimelineUI`，`input swipe` 滚动 6 次（每次 3s）：

| 指标 | 滚动前 | 滚动后 | 差值 |
|---|---|---|---|
| 总文件数 | 909 | **945** | **+36** |
| `sight_` 视频 | 3 | **3** | **0** |
| `snst_` / `snsu_` 缩略图 | — | 新增 | ✅ |

⇒ 滚动**会**触发图片缓存（与 R14 实证一致），**不会**触发视频下载。

### 8.3 原因：视频没有自动播放

截图确认：列表里的视频显示**播放按钮 ▶**，未播放。

网络状态：`Active default network: MOBILE[NR]`、`wifi_on=0` ⇒ **走 5G 流量**。
微信「仅 WiFi 下自动播放朋友圈视频」的默认设置生效 ⇒ 不播放 ⇒ 不下载。

### 8.4 三层可行性结论

| 内容 | 定时刷新（后台） | 自动加载（滚屏） | 全自动可达成？ |
|---|---|---|---|
| 文字 | ✅ 落 `SnsInfo` | — | ✅ **可以** |
| 图片 | ❌ | ✅ 落 `snst_/snsu_/snsb_` | ⚠️ 需要滚屏 |
| 视频 | ❌ | ❌ | ❌ **需要「让它播」** |

⇒ 用户目标里「视频」这一环，**卡在"微信不下"而不是"我们取不到"**。
拿到明文不需要解密（§七 已证），缺的是**触发下载**。

### 8.5 三条可选解法（待决策）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 只对名单内好友强制自动播放** | hook 微信"是否自动播放"判定，仅当作者在导出名单内返回 true ⇒ 滚动即下载，再走缓存直扫 | 需要 dex 取证播放判定锚点；会耗流量（可加 WiFi-only 闸门） |
| **B. 定时拉起朋友圈 + 深度滚动** | 复用 `auto_load`，在后台时段主动拉起界面滚到底再退出 | 界面会闪；滚不到的历史仍拿不到 |
| **C. 主动调 native 下载** | 取证 aeskey 来源后自己构造 `C2CDownloadRequest` 调 `startSNSDownload` | 需逆向 aeskey 派生；最容易随微信升级失效，但唯一能「不靠用户滚」 |

A + B 组合 = 不需要解密即可全自动（依赖"滚到"）；C 是唯一能补历史/不依赖滚动的路。
