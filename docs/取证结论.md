## 会话列表（K7 / ConvFilter）
- 结构：`ConversationListView` → `HeaderViewListAdapter`(headers=14,footers=1) → `mAdapter=com.tencent.mm.ui.conversation.p3`（2900+ 项）→ `getItem()=com.tencent.mm.storage.r4`(field_username)。
- **「停在顶部」≠ child0.top==0**：顶部栏是第一个 header，正常停靠 **-2713**（运行时抓，别硬编码）。`setSelectionFromTop(0,0)` 会制造 ~2051px 虚假下拉 → 弹小程序面板。
- **`ListView.correctTooHigh()` 会整块下移内容**（`fillSpecific` 里也调）→ 只能 hook 吞掉（`before` 里 `param.result=null`）。⚠️ 已废弃方案：补尾部填充行（会把 lastBottom 钉死 → cannotScrollUp 恒假 → 上拉滚到底空白）。
- 换 adapter 后必须按新 `viewTypeCount` 重建 `RecycleBin`，否则回收池串类型 → 会话行整片空白。
- **AOSP 滚动边界对巨型 header 不成立**：`cannotScrollDown` 恒假 → 下拉无限制。见 `ScrollDock`：hook `trackMotionScroll`，after 里把 child0.top 钳回停靠位（`offsetChildrenTopAndBottom` 是 @hide，**必须反射**，失败一次永久停用）。
  ⚠️ **两个守卫分开**：吞 correctTooHigh 只看结构（`firstVisiblePosition==0 && child0.top<0`）；下拉钳制只看筛选态（`currentGroupId()>0`）。不筛选时 firstVisiblePosition **也是 0**。
- **`headerAnchor` 只认藏得最到位的那次（取 min）**（可动区间 [dock,0]，用户下拉停在 -1500 也是 0）。`restoreAnchor` 拿不到锚点要 **return 不要退回 0**。
- 行点击走**每行自己的 OnClickListener**，不走 `performItemClick`（`onItemClick` hook 零命中）。
- `ConversationListView` 覆写了 set/get `OnItemClickListener` → `is ClickRemap` 判幂等失效 → 必须剥到最里层（`unwrapLongClick`）+ ThreadLocal 重入守卫，否则无限递归 ANR。
- `AbsListView.LayoutParams.viewType` 是包内可见字段，读要反射。
- 实测项数：不筛选 2957（内容溢出），筛选态 2。

## 会话长按菜单（A15 / ConvMenuInject）
- **微信长按菜单是自绘 PopupWindow，跟 AOSP ContextMenu 是两条平行链路**：
  `PopupWindow$PopupDecorView(601x884)` → `va4.m4`(容器) → `va4.j3`(525x808, ListView 子类) → 4 个 TextView（行高 202）。
  不走 `MenuBuilder.add`（零命中）、不走 `View.createContextMenu`（那条链全空）。
- **K7 的 `LongClickRemap` 会让这 4 项菜单消失** → 开关 `chat.conv_longclick_remap` **默认 false（弃用该包装）**。分组行长按走 `GroupRowMenu`，不受影响。
- 注入方案：hook `View.performLongClick`(2 重载) 的 **before** 记 lastWxid（`getPositionForView`+`ConvFilter.wxidAt`，早于 show 约 60ms）；hook `PopupWindow.showAsDropDown/showAtLocation`(5 重载) 的 **after**，4 秒窗口内动手。
  ⚠️ show 瞬间容器是空的 → 主线程轮询重试（0/40/80…ms，最多 8 次）。
  ⚠️ 容器是 AdapterView，`addView` 抛 UnsupportedOperationException → 走 `ListView.addFooterView(v,null,false)`（isSelectable=false 必须，否则同时触发微信 OnItemClick，footer 位置 getItem 为 null 可能崩）。
  ⚠️ 加进去的 View 必须是 `AbsListView.LayoutParams`（`setupChild` 无条件强转，普通 LP → CCE 崩微信）。
  ⚠️ 窗口固定高度（601x884，列表 808=4×202 刚好填满）→ 必须让 box/父容器/popup 一起长高 `行高×项数`，再 `popup.update(w,h+need)`（只接受 >0）。
- **adb 长按触发不了微信菜单**（被识别成点击），必须真手长按。做基线对照时触发方式要和实验组一致。
- 探针 `probe/MenuHuntProbe.kt`：`op=menuhunt sub=on|off|flush|tree|win|snap|clear [--ei sec N]`，70 个候选 hook + 不依赖 hook 的 View 树 diff。长按自动开 8 秒窗口；测完务必 `sub=off`（hook 了 addView/setVisibility 会拖慢微信）。
  ⚠️ 调用栈过滤没剔 LSPosed 桥接帧 → 要看真实调用点读每条 HIT 行 `at` 后**第 4 帧起**。
- 自弹 AlertDialog 方案（v0.2.5 `feature/ConvMenu.kt`）**已删除**。

## 分组行长按菜单 / 标记已读（v0.2.2）
- 长按菜单自己弹 AlertDialog（`GroupRowMenu`），**别注入微信的长按菜单**（那个 PopupWindow 无可挂 hook）。
- **长按回调必须 return true**（false 会冒泡 → 微信按会话处理弹「删除该聊天」/ 变点击）。
- **长按 listener 包装必须有调用期重入守卫**：微信 `conversation.z2` 在 `onItemLongClick` 内会回头调 `list.getOnItemLongClickListener()` 拿到我们的 wrapper → 无限回环栈溢出。`unwrapLongClick` 救不了。重入时返回 **true**。
- **Dialog 的 Context**：`HostContext.activity()` 靠 hook `Activity.onResume`，但 **LauncherUI 覆写了 onResume，hook 基类不触发** → 恒 null → BadTokenException。已改 `Application.registerActivityLifecycleCallbacks`。需 Dialog 处**优先用 View.getContext**。
- `GroupedAdapter.rebuild()` 的指纹缓存**必须含分组状态**（`db.listGroups().hashCode()`），否则置顶/重命名/删分组后列表不刷新。
- A7 标记已读只改内存（`field_unReadCount`=0），重启微信恢复；真落库需 DexKit 定位写库接口，别硬猜混淆名。
- A13：会话对象 `field_flag` 恒为 `conversationTime | (1<<62)`，**没有置顶位** → adapter 判不出原生置顶区块，pinned 分组行排最前。

## 返回键 / 退出行为（v0.2.1）
- **LauncherUI 的返回不在 `onBackPressed` 里**：走 `dispatchKeyEvent` → `HomeUI.r()` → `LauncherUI.moveTaskToBack()`，拦 onBackPressed **永远来不及**。
- 要拦返回：hook `LauncherUI`（沿继承链）的 `dispatchKeyEvent`，`KEYCODE_BACK + ACTION_DOWN + repeatCount==0` → `param.result=true`。
- 判定「在会话列表而非聊天页」：我们包装的 ListView 是否 `isShown && windowVisibility==VISIBLE`；取不到**保守放行**。
- 筛选态没有「返回全部」行，退出筛选靠系统返回键。
- 定位「谁把 App 退出去了」：hook `Activity.moveTaskToBack`/`finish` 打 16 层 stackTrace。

## 通知静音（K9 / NotifyMute）
- 通知**只在主进程** `com.tencent.mm` 发出（`:push` 一条没有）→ 装 bootstrap 即可，DB 直接可用。
- **「来自哪个群」只能从 `NotificationItem` 拿**（extras 无 chatroom id，contentIntent 反射取不到）。字段 `d`=id(int)、`h`=talker。`NotificationItem.a` 是**实例方法**（nargs=1）→ `hookAllMethods(cls,"a")` 拿得到 thisObject。取法两级降级：先正则解析 `toString()`（`id: ...,msgId: ...,userName: ...,unreadCount: ...`，功能性格式比混淆字段名稳），失败退字段名。
- `notify(String tag,int id,Notification)`，tag 恒 null，**id 与 `NotificationItem.d` 一一对应且稳定**。
- **响铃和震动不在 Notification 对象上**（sound/vibrate 全 null，defaults=0），是系统按 channel `message_channel_new_id` 播的（`[300,200,300,200]`）→ 改 Notification 字段**没用**，正解是**反射换 `mChannelId` 为自建静音通道**（IMPORTANCE_HIGH + setSound(null) + enableVibration(false)），通知栏/角标/heads-up 全部原样，连提示音也一起掐掉。
- **微信前台不响铃不震动** → 验证必须 `input keyevent 3` 退后台，否则探针抓不到。
- 来电判据（取自真机 VOIP 通知，**放行逻辑未真机验证**）：`category=call` / channel 以 `voip_` 开头 / `fullScreenIntent != null`，任一即可。
- ⚠️ PrefKind 要和读法对齐：TEXT 项（`chat.at_aliases`）**不能**用 `Kv.getList()`（按 JSON 数组解析，裸文本返回空列表）。昵称匹配防短名误伤：`@V` 会命中 `@Verity` → 要求 @alias 后不是字母/数字/下划线/短横线。
- 验证静音类功能**必须做反向对照**（关开关再发一条，确认恢复响+震）。

### 6.3 自然触发验收 —— ✅ 2026-10-19 双向 PASS（连修 7 个根因）

首次验收（开关 ON、真人发 0.01 红包并点开）结果：**没自动拆**，`found=0 scans=9 clicked=0`。
但人工补发一条 `op=redpacket sub=dry` **立刻命中** `cd="开"` —— 说明判断逻辑（`RedPacketLogic`）是对的，
问题全在**扫描调度与点击方式**。逐层挖出 7 个根因，全部修完后双向验收通过。

#### 根因 1~3：调度层（扫描根本没跑起来）

**① `REDPACKET_DELAY_MS` / `REDPACKET_MAX_ATTEMPTS` 是空壳配置**
设置页有「识别后的等待时长」（默认 800ms）和「同一红包最多试图决策几次」（默认 3），
但代码里扫描延迟写死 `SCAN_DELAYS = [220, 600, 1100]`，这两个键当时**只有已删除的探针读出来打印**。
⇒ 改成 `scanDelays` 由 `REDPACKET_DELAY_MS` 按比例缩放（base/3、base*3/4、base*11/8），
再补一拍长尾 `base + 2000ms` —— 网络慢时按钮要好几秒才渲染，「开」按钮是**晚到**不是没有。

**② 红包页 resume 被节流吞掉 + 没扫到不补扫（连环坑）**
- `onResumed` 无条件走 `scheduleScan` 的 `BURST_MS=5200ms` 节流。真机实测拆完一个红包会连跳
  `NotHookReceiveUI → BeforeDetailUI → DetailUI → NotHookReceiveUI`，几次 resume 挤在 4~8 秒内，
  节流把**用户手动点开的下一个红包**一起吞了 → `scans` 卡在 9 不再增长。
  ⇒ 红包页 resume 改走 `force=true` 绕过节流（这是「用户真要拆一个红包」的强信号）。
- `cands.isEmpty()` 直接 return，不补扫。⇒ 加 `retryOnEmpty`：空结果时补扫，最多 4 次、间隔 1.5s
  （probe / verify 两路不补扫，避免双重排程把空扫配额提前耗光）。
- 派发过但按钮**还在**（动画未结束空响 / 界面又弹回来）时要补发 ⇒ `RESEND_DELAY_MS=700` 补扫。

**③ 去重键用全局 session 计数器 → 必然误判**
`session` 每次 Activity resume 自增，用它做去重键意味着「只要期间没 resume 过，同一个界面永久不点」。
⇒ 改成 **`identityHashCode(targetView) + 页面类名`**：第二个红包的按钮是不同 View 对象，天然不撞。

#### 根因 4~6：点击层（扫到了、点下去、但红包不开）

**④ `performClick()` 对微信这个 PAG 按钮无效**（最关键的一条）
`View.performClick()` 返回 `true`、日志打 `clicked`，红包**纹丝不动**。
那个「开」是 PAG 动画按钮，只认真实触摸流。⇒ 改成向**根 View** `dispatchTouchEvent`
派发 `ACTION_DOWN` / `ACTION_UP`（`MotionEvent.obtain` + `setSource(SOURCE_TOUCHSCREEN)`）。

**⑤ UP 必须真延迟 60ms，不能同一轮连着 dispatch**
同一轮里连续 dispatch DOWN、UP，实际间隔 ≈0ms，PAG 会判成长按/空响。
⇒ `mainHandler.postDelayed(..., 60)` 里派发 UP。**DOWN 抛异常时必须补一个 `ACTION_CANCEL`**，
否则 ViewGroup 的 `mFirstTouchTarget` / `mPressed` 留在按下态，会**吃掉下一次真实点击**。

**⑥ 坐标必须取自扫描命中的那个「开」View，不能上溯到 clickable 父容器**
旧代码上溯到父容器再 `performClick`，那时对象身份只决定"调谁的 listener"；
改成坐标派发后，**对象身份就是坐标** —— 上溯到全屏容器 = 点在整屏中心，必然点空或误点。
真机取证：「开」正好 `360x360@540,1853`，中心 `720,2033`。⇒ 坐标一律用 `target.view`。

#### 根因 7：验收判据本身写错了（假红 + 假绿）

**⑦ `clicked` 不能当成功判据，且只查一次必然判死**
- `clicked` 只说明"触摸派出去了"，**不代表拆开**（根因 ④ 就是被它骗过去的）。
- `opened` 判据必须**同时满足两条**：① 离开原页（`top` 变了）**且** ② 新页仍是
  `RedPacketLogic.isRedPacketClass`。只满足"离开了"不算 —— 用户可能自己按了返回，
  计进 `leftPage` 单独统计，**不计 opened**。
- 只查一次 900ms 会把慢的成功判死：真机实测派发→跳页 **1226~1424ms**。
  ⇒ 改成轮询：首查 `VERIFY_MS=900`，之后每 `VERIFY_STEP_MS=400` 查一次，
  总预算 `VERIFY_TOTAL_MS=4000`。

### 一、A 项 `del=0` —— 「精确匹配」那段代码从未被执行过

真机漏斗输出原文：

```
SNSC_FUNNEL item=48 sns=36 del=0 rows=0 got=0 keyOk=0 typeMiss=0
```

**`del=0` 的判据含义**：`delMap` 里当前时间线的任何 `snsId` 都没有对应的已删评论集合
⇒ 主流程里「精确匹配」那段代码**一次都没被执行过**。
因此 `got=0` **不能**用来证明「精确匹配逻辑有 bug」——它只说明入口条件从未满足。

**根因已查清（不是代码 bug）**：设备上的归档库 `sns_comment_archive` 只有 **1 行**历史 seed：

```
(snsID=-3412346577660079447, createTime=1792240578, talker='wxid_55uz5752kbtk21', type=1, commentSvrID=1)
```

该 `snsID` **不在当前时间线** ⇒ `delMap[snsId]` 恒为空 ⇒ `del` 恒 0。

**反证：snsId 解析本身是好的**（否则下面两个现象都不成立）：

- `sns=36` 且在涨；
- 新增的 `recentSns` 环形采样能打出真实 snsId（如 `-3410888102863957446`），
  且**每个 snsId 出现两次** —— 对应「先摘标签后打标签」的两趟 bind。

**下一步（尚未执行）**：把当前屏幕真实评论灌进归档库（`tools/_r8_seed.py`，R8 已写），
让 `del>0`，才能验精确路径。

### 二、B 项 `rows=0` —— 「时机太早」与「样本无评论」两种解释尚未区分

- 现象：连续滚 20 屏 + 单屏滚动后立即 `probe("ids")`，**连续 7 次**都是 `rows=0`：

```

```

- **但历史上曾拿到过 `rows=6`**（事后扫描能扫到）⇒ 不能断言「永远扫不到」。
- 两种互斥解释：
  - (a) **时机太早**：`onBind` 触发时评论行尚未上树，此刻扫不到；
  - (b) **该条动态本就没有评论**：纯粹是样本问题。
- **尚未定案**。判死方法：滚动后按延迟序列（0 / 0.5 / 1 / 2 / 5 秒）多次探 `ids`，
  看 `rows` 是否随延迟上升（脚本 `tools/_r8_rows.py`，R8 已写）。
- 另有一条**静态取证** lane 在并行推进（看 `TimelineCommentView.b` 的调用时机），
  结论落在 `_cache/r8_static_rows.md`，定案后回填本段。

### 三、已知不可行路线清单（避免后人重踩）

1. **按 `commentSvrID` 定位评论行 —— 不可行**。
   UI 层评论 proto（`q54/q95`）的两个 long 字段 `q` / `r` **恒为 0**（6/6 行实测）。
   DB 侧 `commentSvrID` 确实存在且非 0（实测 417/1185/1251/1347），但微信**不带上去**。详见 ⑩ 段。
2. **`DELETED_FLAG_MASK` / `commentflag` 路线 —— 不可行**。
   `commentflag` 只表示「某人删光自己评论」=1、「整条动态被删」=2，业务零读取。
   删单条评论是**物理 DELETE**（`s1.Q0`）。详见既有结论段。
3. **`am start -n` 直接进朋友圈 —— 不可行**。
   `ImproveSnsTimelineUI` **未 export**，`am start -n` 会静默停在 `LauncherUI`。
   必须走 UI 点击（发现 → 朋友圈）。
4. **`am broadcast --el` 传 unsigned 64 位 snsId —— 不可行**。
   snsId 是 unsigned 64，超过 `Long.MAX_VALUE` 时 `--el` 抛 `NumberFormatException`，
   且**整条广播不送达**（不是参数丢失，是整条没投递）。必须转 signed： `u - 2**64`。
5. **靠 `probe("seed")` 长期注入 —— 不可行**。
   `SET_TTL_MS = 5000L`，seed 注入后 5 秒即被 `loadAsync()` 用 DB 内容覆盖 `delMap`。
   seed 必须在 5 秒内消费。

> 相关脚本：`tools/_r8_seed.py`（灌库）/ `tools/_r8_rows.py`（延迟探）；静态取证见 `_cache/r8_static_rows.md`。

### ⑫.1 ⛔ 更正：`createSNSDownload` **不在**朋友圈链路上

此前（本会话 01:1x 口头汇报）据 `CdnLogic.createSNSDownload` 字面推断它是 Sns 图片下载入口 —— **错了**。

- ✅ 全 APK 只有 **2 个调用点**，均与朋友圈无关：
  `Lhj0/t;->invokeSuspend`（实为 **MJTemplate Flutter 插件的 Maas 音乐短视频 demo 素材下载**，
  同方法体有 `'MicroMsg.MJTemplateApiFlutterPlugin'` / `'maas_music_demo_resource'`）+ `createGroupNoticeDownload` 内部互调。
- ⇒ **直接 hook `createSNSDownload` 抓不到朋友圈图片请求。**

### ⑫.2 ✅ 真正的 Sns 图片下载链路

```
Ljf3/f;->k([String)Integer        ← SnsCdnDownloadBase#doInBackground（✅ SnsMethodCalculate 原名实测）
   └ new BatchSnsReqImageData 并 iput 全部 6 字段（url/fileKey/decryptKey/imageCachePath/picIndex/totalFileSize）
      └ SubCoreCdnTransport.addRecvTask       ← 日志 '[%s][media:%s]SubCoreCdnTransport addRecvTask succ/failed mediaId:%s'
         └ Lok0/x0;->o(Ltj/h;)I               ← CdnTransportEngine（✅ log tag 实测）
            └ CdnLogic.startSNSDownload(...)  ← ⛔ NATIVE
```
`Ljf3/d;->C2(...)` 是 `BatchSnsReqImageData` 的**唯一字段读取点**（读 `picIndex`×5 / `retry`×1）⇒ 可作"批量回调是否真触发"的探针。

### ⑫.3 ⛔ 硬约束：所有 `start*Download` 都是 native，Xposed 直接 hook 不了

`CdnLogic` 的 `startSNSDownload` / `startC2CDownload` / `startURLDownload` / `startHttpsDownload` /
`startHttpVideoStreamingDownload` / `allowBatchImageDownload` 等，**access_flags = 0x109（ACC_NATIVE）**，无 Java 实现体。
⇒ 只能 hook **调用方**（`ok0.x0#n`）或**回调实现**（`ok0.x0#onC2CDownloadCompleted`），
或改走 native inline hook（Dobby/AndHook，本项目未引入）。

### ⑫.4 ✅ 推荐 hook 点（按价值降序，均为 **java** 方法，可 hook）

| # | hook 点 | 能拿到什么 |
|---|---|---|
| 1 | `ok0.x0#n(Ltj/g;)I` | ★**批量请求全量**：`req.l1 = [BatchSnsReqImageData]`（url/fileKey/decryptKey/imageCachePath/picIndex/totalFileSize）+ feedId/feedPicCount。**在调 native 之前**，可读写入参 |
| 2 | `ok0.x0#onC2CDownloadCompleted(String, CdnLogic$C2CDownloadResult)` | ★**结果全量**：`errorCode`、`picCachePath`（**图片落盘路径**）、`fileSize`/`recvedBytes`、`picIndex`、`realUsedURL`、`httpStatusCode` |
| 3 | `jf3/f#k([String)Integer` | 唯一 `BatchSnsReqImageData` **构造点**，可改 `imageCachePath` 控制落盘位置 |
| 4 | `com.tencent.mm.plugin.sns.ui.dk#a()Z` | 批量链路**开关**（见 ⑫.5），强制返回 true 可试开批量下载 |
| 5 | `ok0.x0#onDownloadProgressChanged(String,long,long,boolean)` | 判断任务是否真的在跑 |

⚠️ 「hook `C2CDownloadRequest.setXxx` 系列 setter」**抓不到主链路** —— `ok0.x0#n` 里是**直接 `iput` 字段赋值**，不走 setter（✅实测）。

### ⑫.5 ✅ 批量开关是**两道门**（与关系），不是一道

```java
dk.a()  ==  CdnLogic.allowBatchImageDownload()  &&  dk.j
```
任一为假 ⇒ `return false` 并打印 `'groupDownloadDisable!!!'`；两者都真才 `true`。
- `allowBatchImageDownload()` 是 **native**（只能 hook `dk.a()` 本身绕过去）。
- `dk.j` 是**非 final 静态布尔**，在 `dk.<init>` 里由一次服务调用结果赋值（🟡赋值来源未逐条确认）。

### ⑫.6 🔴 对既有结论「图片存不了」的影响（**可能翻案，但必须真机**）

`6.4b` 定案「三条路全关、图片存不了」是在**没有这条链路信息**时下的。现在静态显示：
微信内部**有**批量图片下载通路，且**有落盘路径**（`imageCachePath` 入参 / `picCachePath` 出参）。

⇒ R4「点开大图不落盘」的**另一种解释**：不是"图片存不了"，而是**批量下载这道开关当时是关的**（`groupDownloadDisable!!!`），
所以微信走流式显示、不下盘。

**新路线（比"自己解密"便宜得多）**：翻 `dk.a()` 开关（hook 强制 true）→ 让微信**自己**批量下载并落到 `picCachePath`
→ 我们只读文件，**不需要自己发 HTTP、不需要自己解 aeskey**。
⛔ 这是 🟡**推断**，未真机验证；若 `dk.j` 由服务端下发且恒 false，则此路不通。
