### Q2：既有结论"加密 dex 静态不可解、不可复制"在图片转发上还成立吗？

**结论：成立，但需要精确到"哪一环不可复制"——"静态不可解"与"字节来源不可复制"都成立；"微X图片清晰模式整体不可复制"不成立，且第四轮裁决自己已经找到了宿主侧可复制的"终局"。没有任何新证据推翻 R72 定案，也没有遗漏一条"我方此前没识别出的可复制模式"（P3 就是那条，早已在案）。**

**逐条检验：**

1. **"静态不可解"是否仍成立**——【源码确定】仍成立，且 R73 真机观察是"黑盒侧观察"，不改变静态结论。R72 定案三卡点：① 8 个 `92 c5 01 00` 高熵密文容器（非 7，R72 §4 已订正）+ 2 ELF `libwxcoreloader.so`（符号剥除，导出 `JNI_OnLoad`/`CallMethod`）+ 1 DER；② 真正解容器的 `CallMethod` 在 native `.so`（壳 dex 里 `WxCoreLoader.CallMethod` `code=0x0` 无方法体）；③ 所有常量串经 rolling-XOR（两张 8191/2968 字符表 + splitmix64 式）混淆。锚点：`docs/_r72_microx_forward_parse.md` §1.6/§4.4。**R73 期间没有任何材料解开这层，此结论未被触碰。**

2. **"字节来源不可复制"是否仍成立**——【真机确定 + 源码确定】成立。23:11 真机 `R5/j6/B8/C2` 下载链全零 + `m.a=-1` + `r0.u=EMPTY`，是微X**没走宿主任何公开下载/解码 API**的直接证据；而大图字节又确实被造出来了（对端清晰 + `cache/_<uuid>` 临时文件存在且发后已删，`stat` 返回 No such file）。⇒ 字节来源必然在微X加密 dex 的私有实现。我方是宿主 dex 内的 Java 层，**无法反射调用一个宿主 dex 里不存在的方法**，这一环确实不可复制。锚点：台账 `:5231-5235` + `wxgroup/docs/_r73_ma_residual.md` §9.4 理由 1。

3. **"微X图片清晰模式整体不可复制"是否成立**——**不成立，这是需要校准的地方**。第四轮裁决 §9.4 已经自洽地把这件事分成了两层，并给出宿主侧可复现的"终局"：

   - **不可复制层（字节来源）**：微X私有下载/解码通道（加密 dex），我方照抄不了。
   - **可复制层（终局 = 让 stock j2 读到字节）**：j2 读图唯一走 `R()=o2(j2.i)→r0 → z3(r0.e/f/g/j) → o6.l()`（`_r73_ma_residual.md` §9.1 字节链，【源码确定】）。要让 r0.e 指向大图字节文件，我方 dex 内**唯一现成入口**就是 P3 的：
     - `b1.R5` @`2a710c`（下载大图落 image2 桶，原生 `MsgRetransmitUI.j6` `62d176` 用同一入口）
     - `b1.z3` 的 `SERVERID:// → Y2(msgSvrId)` @`2a6ae4`/`2a6b30`
     - `b1.Q2/a3` @`62ca30`/`62ca8a`（B6 取 r0 的范式）
     - `r0.l` @`2b3ea4` 写 `r0.e/j`、`r0.n` @`2b3ee4` 写 `r0.f`、`b1.u8` @`2a5398` 持久化

   这些全在宿主 dex、可反射调用、不碰加密 dex。⇒ "P3 是我方拿到大图字节的唯一可实施路径"（§9.4 理由 2）**成立**，这正是"可复制模式"，并非本轮新发现，第四轮已给出。

**有没有被前几轮漏掉的、我方确实可复制的模式？** —— 复查结论：**没有漏掉的新入口**。逐个排查：

- 建组/删组：可复制模式 = 补发宿主通知（`s4.b`），R67/R70 已落地并真机验收，非"漏掉"。
- 文本转发：可复制模式 = G1 原生链，R71 已通且定案无标记，非"漏掉"。
- 图片转发：可复制模式 = P3 字节落盘，第四轮 §9.3/§9.4 已给出 dex 锚点 + 真机判据，非"漏掉"。

### Q3：微X图片清晰的实现模式本质是什么？

**本质结论：不是"私有下载通道"本身，而是"在转发前把大图字节落到本地文件，并让 stock j2 经 `z3(r0.e)` 指向它"。** 更精确：**"清晰"的机制本质 = 构造一条让宿主 j2 通过 `z3(r0.e)→o6.l()` 读到本地大图字节的终局（宿主通用链，可复制）；"字节从哪来"（下载/解码）才是加密 dex 私有（不可复制）**。第四轮把它归为"加密 dex 私有通道"针对的是"字节来源"这一环，**不算武断**——它在 §9.4 已经明确把"来源不可复制"和"终局可复制"分开了；只是"微X用加密 dex 私有下载/解码通道"这句概括句容易被误读成"整条清晰链路都不可复制"。

**逐个检验用户点名的三处细节：**

**（a）`j2.O` 的 `m.a=-1` + `r0.u=EMPTY` + `m1.n(1)` 短路分支**——【源码确定，第四轮 §9.5 已逐字节直证】

- `j2.O` 起于 `2acc44`：`2accb4 m1.n(1)→v4`（全局 CDN 开关值），`2accbc if-nez v4,0056`——**`m1.n(1)!=0` 时直接短路到 0056（构造 CDN task），根本不走到 `2accc0` 的 `r0.u` 判空**。
- 因此真机 `r0.u=EMPTY` 却 `ret=true` 的机制 = **`m1.n(1)!=0` 短路分支**，不是 `r0.u` 判空的结果。第三轮把 `r0.u` 当"清晰判别开关"是**过窄**的（§9.3 已纠正）。
- 真正喂给上传 task 的图源是 `2ace9c field_fullpath = z3(r0.e)`（§9.3）。⇒ 清晰度与 `m.a`/`r0.u`/`q1.*`/`ori` 参数**全无关**，唯一决定量 = `z3(r0.e)` 指向的本地文件是否大图字节。

**（b）微X把大图字节从哪喂进 `z3(r0.e)`**——【源码确定读图链 + 推断落盘链，置信中】

- j2 读图唯一入口（§9.1 字节链，【源码确定】）：doScene `2adaa6 j2.R()`；`R()`=`2ad864`：`j2.q` 空则 `b1.o2(j2.i)→r0`；再 `2adece/2adee2/2adf06 z3(r0.e/g/f)` → `2adf0c o6.l(path)` 取长度。**r0 来自 `o2(j2.i)`（本地记录 id，由 L5 插入返回），不是 `o2(m.a)`**——这是第四轮对第三轮的精度修正。
- 构造器的 `m.a>0` 分支（`2af15c if-lez` 二选一）把 `o2(m.a)` 结果挂到 `t0.o`（上传参数），与 doScene 用的 `o2(j2.i)` 是**两条**。所以微X `m.a=-1` 只意味着"不挂 t0.o、不预解析路径"，**不影响 doScene 从 `o2(j2.i)` 读图**。
- 结论：微X要让 doScene 读到清晰字节，唯一路径是**让 `o2(j2.i)` 返回的那条 ImgInfo2 记录的 `r0.e`（大图路径字段）指向含大图字节的本地文件**（`cache/_<uuid>`）。即字节是"经 `r0.e` 字段"喂进 `z3` 的，**不是经 j2 的 ori/str[3] 参数**（§9.1 已证 ori→`j2.L`/`t0.b` 仅元数据/埋点，不进 `o6.*` 读文件）。

**（c）`cache/_<uuid>` 是谁写的、写进 ImgInfo2 还是自建 task**——【源码确定命名形态 + 推断写入者，置信中，属未闭合取证缺口】

- **谁写的**：`_ffb490d4-0f98-4698-99c0-57068cb6484a` 是 128-bit Java `UUID.randomUUID().toString()` 形态。宿主 dex7 内 `com.tencent.mm.cache` / `UUID.randomUUID` **零命中**；宿主现成的是 `MsgRetransmitUI.C6`(`62cddc`) 的 `getCacheDir()+"/share_img_tmp_"`（`62ce58` string@1dbe，从 Intent STREAM 落 cache）。⇒ `_<uuid>` 命名生成在**微X加密 dex**，R72 定案静态不可解。【推断·高】
- **写进 ImgInfo2 还是自建 task**：第四轮 §9.2 给出两条宿主侧可见的达成方式并标 UNKNOWN——
  1. 落盘 + `r0.l(String)`(`2b3ea4`→`r0.j`)/`r0.n(String)`(`2b3ee4`→`r0.f`) 写 ImgInfo2 路径字段（微X主动调 r0.l/n，是另一条写入者，与第三轮"C2/j6 不写 e/j/g/f"不冲突）；
  2. 直接构造 ot5/fullpath（不经 j2 读图链，`2ace9c field_fullpath=z3(r0.e)` 由微X自建 task 喂）。
  **未 hook `r0.l/n`/C6 真机确认，故无法定论走 1 还是 2**。【推断·中，UNKNOWN】
- **但一条硬约束成立**（§9.2，【源码确定】）：**大图字节必然在转发前已存在于某本地文件，且 `z3(r0.e/f)` 必然指向它**——否则 doScene `2adf0c o6.l()` 取长度 ≤0 → `2adf30 goto 05d5` 错误出口，对端不可能收到清晰大图。这条与真机 ori=cache 临时文件 observation 互相印证（微X确实写了这个文件，只是它不是经 j2 的 ori 参数被读）。

**对"第四轮归类是否武断"的最终判断**：**不武断，但需精确表述**。第四轮 §9.4 的"微X通道 = 加密 dex 私有下载/解码 + 终局 = z3(r0.e)"已经正确分层；它唯一把"加密 dex 私有通道"当作图片清晰的**概括标签**，容易被误读。准确结论是：**图片清晰是"来源（私有、不可复制）" + "终局（宿主通用、可复制）"两段，第四轮没有混淆这两段，反而给出了可复制的终局入口（P3）**。遗留的 UNKNOWN（微X用 r0.l/n 写 ImgInfo2 还是自建 fullpath）不推翻结论，只影响我方"照抄微X内部细节"这一无需做的事。
