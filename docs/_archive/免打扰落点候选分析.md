> 目的：给「新加群自动免打扰」找到微信**自己那个开关**存在哪。
> 本文只做**候选收敛**，不实现、不写库、不碰设备。所有结论标注来源与等级。

## 一、结论摘要（先看这个）

1. 现有 17 个 `rconversation` 列**全部能对上"消息流/运行时状态"的语义**，没有一列像开关（A，见 §2.2 逐列表）。真正没查的是**还有没有第 18 列**——完整列清单从来没取过（A，`tools/cols.py` 存在但无输出留痕）。
2. 上一轮 SQLite 写路径"零捕获"**不能证明微信没写库**，有三个已从代码里确认的盲区：写操作被 `catchKey` 丢弃、`mute1/mute2` 默认**不 dump `userinfo2`**、以及 `byte[]`/`ContentValues` 参数在 `catchKey` 里退化成 `[B@...`（A，见 §5）。
3. 当前最值得先查的落点是 **`userinfo2`**：它已被实证是"语义化常量 key + 值"的 KV 表（A，`dbg.txt` 20:32:26 的 `DELETE FROM userinfo2 WHERE sid=?` 与参数 `USERINFO_WALLET_REALNAME_DISCL...`），且在任务背景里存在两个 **MUTE 相关全局 key**（B）。`USERINFO_CHATROOM_MUTE_DETAIL_*` 的字面含义就是"群免打扰详情"。
4. 总体判断：这个开关**大概率不是 `rconversation` 的某个布尔列**，而是「服务端为准 + 本地一份 per-chatroom 详情缓存」（C）。因此**找到 setter 比找到列更有价值**——见 §4。

## 三、剩余候选（按 可能性 × 取证成本 排序）

排序原则：**先做"能在 10 秒内把整类可能性砍掉"的检验，再做"逐表逐列找"**。
所以第 1 位不是"某张表"，而是"一类存储"。

### 3.1 【最优先】`userinfo2` 的 per-chatroom key（可能性 中高 / 成本 极低）

**为什么怀疑它**

- **硬证据 A**：`dbg.txt` 20:32:26 出现 `DELETE FROM userinfo2 WHERE sid=?;`，绑定参数是 `USERINFO_WALLET_REALNAME_DISCL...`。
  → 由此可确认三件事：表名 `userinfo2` 真实存在；**`sid` 是语义化常量字符串**（不是数字 id）；该表在 8.0.48 的**活跃写路径**上（取证当时正在被删）。
- **上游线索 B**：该表已知存有 `USERINFO_CHATROOM_MUTE_DETAIL_CLIENT_GRAY_BOOLEAN`、`USERINFO_SETTING_CARE_MODE_MUTE_BOOLEAN` 这类全局 key。
  - 这两条证明了「**8.0.48 的免打扰相关配置确实落在 userinfo2**」，只是被认定为全局；
  - 而 `..._CHATROOM_MUTE_DETAIL_...` 的字面含义是"**群免打扰详情**"——**详情（detail）** 这种命名习惯通常意味着"一个 key 里塞一张表/一段 proto"（C）。
- **为什么上一轮一定看不见它（关键）**：`MuteHuntLogic.tableHit("userinfo2")` 返回 null —— 把 `STRONG_TABLE_HINTS` / `WEAK_TABLE_HINTS`（`MuteHuntLogic.kt:39-53`）逐个比对，"userinfo2" 一个词根都不命中。而 `dumpMuteSnapshot` 在未强制指定表时会 `continue` 掉所有未命中的表（`LabelHuntProbe.kt:555`）。
  → **`mute1/mute2` 从来没有 dump 过 userinfo2**；它零变化完全不能作为排除依据。**A**

**证伪 / 证实命令**（一条，零用户操作）

```
adb shell am broadcast -a com.lx.wxgroup.action.PROBE -p com.tencent.mm \
  --es op label --es sub sql \
  --es sql "\"select * from userinfo2 where sid like '%MUTE%'\""
```

- 说明：走的是既有只读 SQL 通道（`isReadOnly` 白名单，`LabelHuntProbe.kt:414-424`）；该命令会在**每个已打开库**上执行一次，只有 EnMicroMsg.db 有这张表，其余库报 `no such table` 属正常。
- 输出形态是 `sid=... | value=...`，**每个值截断到 60 字符**（`LabelHuntProbe.kt:889`）。若 value 很长，追一条 `select sid, length(value) from userinfo2 where sid like '%MUTE%'`，再用 `substr` 分段取。
- 若 `%MUTE%` 无 per-chat 行，再补两条（同样是一条命令一条）：
  - `... sid like '%58783890225%'`（key 里直接拼群 id）
  - key 用 md5 时：先本地 `python -c "import hashlib;print(hashlib.md5(b'58783890225@chatroom').hexdigest())"`，再用该 hex 串做 `like`。

**证实后长什么样**

```
sid=USERINFO_CHATROOM_MUTE_DETAIL_CLIENT_GRAY_BOOLEAN | value=...58783890225@chatroom...   ← 详情里带群
或
sid=<某个前缀>_58783890225@chatroom | value=1
```
并满足：**同一个 key 在"关"的时候 value 也变**（这才是开关；只有一次采样只能说明"有关"，不能说明"跟着动"）。

**证伪长什么样**：`%MUTE%` 只命中 2 行、且 value 里**不含任何 `@chatroom`** → per-chatroom 状态不在 `userinfo2`，降级到 §3.2/§3.5。

### 3.3 `chatroom` 表的**非 `roomflag` 列**（可能性 中低 / 成本 低）

**为什么怀疑它**

- **A**：`dbg.txt` 20:34:54 的 FLUSH 汇总里有 `5x ... | chatroom | xmlChatroomno...` → 该表确有 XML 列且**在运行时被反复更新**；
- **A**：`dbg.txt` 20:30:33 有 `update chatroom ... <tousr>58783890225@chatroom</tousr> ... where rowid = ? 833` → 群资料的写入是**按 rowid** 的（这也是 §5.1 盲区的实证来源）。
- 只排除了 `roomflag`；`roomdata` / `xmlChatroomnotice` / `chatroomStatus` 这类 BLOB/XML 列**没有被评估过**（B 的结论只覆盖 roomflag）。

**为什么可能性不高**：`chatroom` 表更像"群资料/公告/成员数"，而"我对这个群免打扰"是**用户维度**设置，放这里会让同一群在不同账号下冲突。

**证伪 / 证实命令**（一条，零用户操作）

```
adb shell am broadcast -a com.lx.wxgroup.action.PROBE -p com.tencent.mm \
  --es op label --es sub sql \
  --es sql "\"select length(roomdata) as rd from chatroom where chatroomname='58783890225@chatroom'\""
```

- 目的不是看值，而是**先确认这一行的定位键**（`chatroomname` 是否存在、是否精确命中）。命中后再用 `mute1/mute2 --es table chatroom` 做逐列 diff（diff 会打列名与前后值，BLOB 会被 `hexOf` 压成 `BLOB[len=...]`，见 `LabelHuntProbe.kt:780-803`，足以看出"变没变"）。
- **证实**：diff 出现该表 `CHG`，且变化的列在 `roomflag` 之外。
- **证伪**：该行在切换前后**逐列零变化**（`changes=0`）。

**为什么留着**：`mutetables` 的两路筛查（表名词根 / 列名词根）都是**启发式，不是锚点**（`MuteHuntLogic.kt:24-26` 自己写明了）。而且**现有日志里没有任何 `MUTE` 前缀的行**（A：本仓库 `dbg.txt` 全 318 行 grep 无 `MUTE`），说明 `mutetables` 至今没有可用的输出留痕——我们其实**没看过**这张表清单。

### 3.5 MMKV（`/data/user/0/com.tencent.mm/files/mmkv`）（可能性 中高 / 成本 中）

**为什么值得排在 SQLite 之后但仍然很高**

- **A**：MMKV 根目录实证为 `files/mmkv`（`_live.log:2258`，`initializeMMKV root dir: .../files/mmkv`）。
- **A（反面）**：现有 `muteprefs` 检查的是 `<dataDir>/mmkv` 而不是 `<dataDir>/files/mmkv`（`LabelHuntProbe.kt:659`），**这个分支永远不会命中**；而且它只打 `files=<N>` 计数，不打文件名（`LabelHuntProbe.kt:662-664`）。→ "MMKV 里没有"这个结论目前**没有工具支撑**。
- **B**：`mmkv_chatroom_display_name_cache` 的存在证明微信**确实有"per-chatroom 的 MMKV store"这一命名/使用惯例**。
- **C**：开关是布尔，MMKV 里就是 1 个字节，**与 wxid 无任何文本关系**；如果 key 是 `md5(群id)` 或值是 protobuf，按 wxid 明文 grep **必然漏**。

**已知文件逐个评估**

| 文件 | 内容判断 | 结论 |
|---|---|---|
| `mmkv.default` | 默认 store，杂项全局开关（C） | **保留为候选**：per-chat 布尔最可能藏在这种"杂物间" |
| `_hellhound_mmkv` | `hellhound` 是微信的灰度/ABTest 平台代号（C）；与 `..._GRAY_BOOLEAN` 类 key 对得上 | 不太可能是 per-chat；更像"这个灰度功能开没开" |
| `SyncMMKV_*` | 同步游标/版本号（B：内容形态） | 排除 |
| `MicroMsg.RecentForwardInfoStorage` | 最近转发列表（B） | 排除 |
| `mmkv_chatroom_display_name_cache` | 群显示名缓存（B） | 排除为"开关"，但**证明存在 per-chatroom store 惯例** |
| `1432478943TransInWriting` | "正在输入"状态（C，字面 TransInWriting） | 排除（瞬时状态） |
| **`notify` / `mute` / `silent` / `setting` 命名的文件** | **一个都没出现在已知清单里** | ⚠️ 但已知清单是"**按内容 grep**"得来的，不是目录清单 → **不能推断不存在** |

**证伪 / 证实方法（两步，不需要解析 MMKV 二进制）**

1. 取目录清单（这是目前最大的信息缺口）：

```
adb shell su -c "ls -l /data/user/0/com.tencent.mm/files/mmkv"
```

2. 切换开关**前后**各做一次全目录哈希，比对：

```
adb shell su -c "md5sum /data/user/0/com.tencent.mm/files/mmkv/*"
```

- **证实**：只有**一个**文件 hash 变了，且不是已知的通知队列类文件 → 该文件即候选，再把该文件 hex dump 出来找 diff 偏移（MMKV 是明文 key/value 的 varint 格式，可直接脚本解析）。
- **证伪**：全部文件 hash 不变 → MMKV 整条路出局（前提：切换后等 2~3 秒再取，避开 MMKV 的写入合并）。
- 若设备没有 root shell：退化成给 `muteprefs` 补 5 行（把 `files/mmkv` 的文件名 + size + MD5 打出来，并支持 before/after 两组快照），成本仍然很低。

### 3.7 服务端下发 + 进程内存（可能性 中高 / 成本 中，且是"最终兜底解释"）

**为什么必须列它**：免打扰状态必须**跨设备一致**，这在产品上就是服务端权威（C）。本地可能只有一份"最近一次同步"的缓存，甚至是每次登录重算、只在内存里。

**判别实验（不需要找任何列）**

1. 断网（飞行模式）→ 切换某群免打扰 → 观察开关是否**立即回弹**。
   - 回弹 = 必须服务端确认（强服务端权威）；
   - 不回弹 = 本地有缓存/乐观更新（缓存位置待查，回到 §3.1/§3.5）。
2. 飞行模式切换后**强杀微信再启动**：状态还在 → 本地确实落了东西；状态丢了 → 纯内存 + 服务端。

**更有价值的替代路线：抓 setter，而不是抓存储**

- 在设置页开关上做栈回溯：hook `android.widget.CompoundButton.setChecked(boolean)`（Android 公开 API，不猜微信类名），用户点开关时打 16 帧栈 → 第 4 帧起就是微信自己的设置页逻辑 → 顺着看它调了哪个 `Storage.setXXX` / 哪个 `NetScene`。
  - 这与本项目既有方法论一致：`docs/取证结论.md:50` 就是"hook 公开 API + 打栈"定位到 `HomeUI.r()` 的先例。
  - 已有同类探针可复用：`MenuHuntProbe` 的 16 层栈回溯（`docs/取证结论.md:33`）。
- 一旦拿到 setter，**直接调它**即可，不必知道它写到哪：省掉"写库→内存缓存不一致→UI 不刷新"的全部坑（`docs/取证结论.md:42` 的"A7 只改内存、重启恢复"就是这个坑的反面教材）。

## 四、推荐取证顺序（3 步，每步一条命令）

> 每一步的**空结果都是一条结论**，不是"再试一次"。

### Step 1 —— 判定「切开关到底写不写 SQLite」（决定 §3.1~3.4 是否还有意义）

```
adb shell am broadcast -a com.lx.wxgroup.action.PROBE -p com.tencent.mm \
  --es op sns --es sub catch --ei sec 20
```

- ⚠️ **必须用 `--ei sec`**（`getIntExtra`，`EntryReceiver.kt:213`）。现有 `tools/mute_v2.py` 把所有参数都按 `--es` 发（`mute_v2.py:17-22`），`--es sec 600` 会被当成字符串 → 实际回落到默认 150 秒。这也是"窗口看起来开了很久、实际更短"的坑之一。
- 操作要求（**比命令本身更重要**）：
  1. 先把微信拉到前台（后台不投递广播，`docs/取证结论.md:178-180` 已踩过）；
  2. **不带 `--es table`**（上一轮就是因为带了 wxid 过滤才漏掉 `where rowid=?` 形式的写）；
  3. 看到 `SNS catch ON` 后 **3 秒内**切换目标群的「消息免打扰」，**切换前后各截一张图**（证明开关真的动了——上一轮最大的不确定性就是"用户到底有没有操作"）；
  4. 20 秒后 `adb pull /sdcard/Android/data/com.tencent.mm/cache/wxgroup_dbg.txt` 再读。
- **命中** → 直接拿到表/列，回去用 `mute1/mute2 --es table <该表>` 做二次确认（一次切换、两次 dump）。
- **空** → SQLite 写入面基本出局（钩子挂在类上，覆盖全部库实例，不是只挂某一个 db），**跳到 Step 2**，不必再折腾 `mutetables`。

### Step 2 —— 读「存量状态」：per-chatroom 设置存在哪个 key

```
adb shell am broadcast -a com.lx.wxgroup.action.PROBE -p com.tencent.mm \
  --es op label --es sub sql \
  --es sql "\"select * from userinfo2 where sid like '%MUTE%'\""
```

- 为什么在 Step 1 空之后还要查：**写可能发生在登录/同步时，切换只改内存 + 发协议**；但"当前状态"一定被读出来了，所以存量里能看到它。
- **命中带 `@chatroom` 的 value** → 得到落点，并顺手确认它是"详情表"还是"布尔"。
- **只有两条全局 key** → `userinfo2` 的 per-chat 路线降级，**跳到 Step 3**。

### Step 3 —— 判定「非 SQLite 的本地存储」（MMKV / SP / 其它文件）

```
adb shell su -c "md5sum /data/user/0/com.tencent.mm/files/mmkv/*"
```

- 切换前后各跑一次（切换后等 2~3 秒），两端 `diff`。
- **有且只有一个文件变** → 解析它（MMKV 明文格式），拿到 key/value；若 key 是 hash，先算 `md5(群id)` 对账。
- **全都不变** → 本地没有 per-chat 落点，**结论就是 §3.7：服务端权威 + 内存**。此时不要再找列，改走 §3.7 的 setter 栈回溯路线。

## 五、已确认的取证工具缺陷（会让"没写"变成假结论）

这几条不是猜测，都是从代码里读出来的，必须在下一轮开跑前知道：

### 5.1 `catchKey` 对 `byte[]` / `ContentValues` 是瞎的（A）

`SnsHuntProbe.kt:559-567` 的 `flat()` 只展开了 `Array<*>` / `Iterable`；`ByteArray`（primitive array）走到 `else -> v.toString()`，结果是 `[B@1a2b3c`。
而 `ContentValues.toString()` 里 byte[] 值同样是 `[B@...`。
→ **如果免打扰详情是以 BLOB 形式写进 `userinfo2.value`**，SQL 里没有 wxid、绑定参数里也看不见 wxid → 这次写会被 `catchKey` **静默丢弃**（`SnsHuntProbe.kt:604`）。
这正是"上一轮零捕获 ≠ 微信没写"的最强技术解释，也是把 `userinfo2` 排第一的理由。

### 5.2 `mute1/mute2` 默认范围不含 `userinfo2`（A）

`dumpMuteSnapshot` 在未指定 `--es table` 时只 dump `tableHit()!=null` 的表（`LabelHuntProbe.kt:555`）；而 `"userinfo2"` 不命中任何词根（`MuteHuntLogic.kt:39-53`）。
→ 上一轮的开关对照法**结构性地看不到这张表**。要看得显式 `--es table userinfo2`。

### 5.3 `muteprefs` 的 MMKV 路径是错的，且只打计数（A）

`LabelHuntProbe.kt:659` 用 `File(root, "mmkv")`（= `<dataDir>/mmkv`），真机实际在 `<dataDir>/files/mmkv`（`_live.log:2258`）。
→ 那句"⚠️ 发现 mmkv 目录"永远不会打印。且即便路径对了，也只打 `files=N`，不给文件名/hash（`LabelHuntProbe.kt:662-664`）。

### 5.4 输出会截断，长结果必须分段（A）

- `rows()` 每个值 `take(60)`（`LabelHuntProbe.kt:889`）→ 长 value / 长 JSON 必须用 `length()` + `substr(...)` 分段读。
- FLUSH 汇总行在 ~190 字符处就被砍（`dbg.txt` 20:34:54 的 `5x ... | chatroom | xmlChatroomno` 即断在此）→ 表名清单、列名清单不要在一条日志里塞，`tools/cols.py` 的"每段 8 个"就是这个教训的产物。

### 5.5 `mutetables` 的 `all=` 只在"零命中"时才打（A）

`LabelHuntProbe.kt:514-521`：有命中就不打全表名。想拿完整表清单只能人为把 hint 全废掉或分批 `--es table`。→ 别把它当"库里有哪几张表"的清单工具用。

## 六、可能性判断（如果本地 SQLite 全排除）

**最可能的机制（C，按概率从高到低）**

1. **服务端下发 + `userinfo2` 里的 per-user 详情缓存（BLOB/JSON）** —— 最符合 `USERINFO_CHATROOM_MUTE_DETAIL_*` 这个 key 的字面形态，也解释了"切开关时可能只写一个不含 wxid 的 BLOB"。
2. **服务端下发 + MMKV 缓存** —— 符合微信"per-chatroom 用 MMKV"的既有惯例（`mmkv_chatroom_display_name_cache`），且布尔极小、key 可能被 hash。
3. **纯服务端 + 进程内存** —— 切换立刻发协议，回包才更新内存对象；本地只在下次登录时重新拉。这种情况下**本地永远找不到列**，找多久都是白费。

**对应的验证与落地**

- 先做 §3.7 的"断网切换"实验：能区分 1/2 与 3。
- 无论命中哪一种，**落地优先选"调微信 setter"而不是"写存储"**：
  - 写库不刷新内存 → 界面不显示（A7 的教训，`docs/取证结论.md:42`）；
  - 写库不发协议 → 换手机就丢，且下次同步被服务端覆盖；
  - 只有 setter 能同时满足"界面变 / 跨端同步 / 不被覆盖"。
- 如果最终确认是第 3 种（纯服务端 + 内存），那么本功能的**正确降级**就是现在这样（静音通道），并在 UI 上如实说明"仅本机静音，不改微信开关"——这比硬写一个会被覆盖的本地缓存更可控。

## 附录 B：`attrflag` 的排除前提复核（**不作为候选**，只为把结论钉死）

§2 的排除只在"用户确实静音过某些群"时成立。一条 SQL 即可结案（把已知静音群与未静音群并排比）：

```
--es op label --es sub sql \
  --es sql "\"select username,attrflag,flag,unReadMuteCount from rconversation where username in ('<已静音群>','<未静音群>')\""
```

- 两行 `attrflag` 相同 → 排除成立，本节永久关闭。
- 两行只差一个位 → 该位就是开关，直接结案（这是成本最低的一条"意外收获"路径）。
