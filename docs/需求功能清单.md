### 三处重复是怎么合并的

**① 静音逻辑三合一（K9）** —— 防止被@、免打扰时段、微信来电放行，这三者要拦的是**同一个点**：「收到消息 → 播放提示音 / 触发震动」。如果各写各的，三个 hook 会抢同一个入口、互相覆盖，最坏情况是免打扰把微信电话也掐了。合并成一个判定函数：

```
if (是微信来电)            → 放行（照常响铃振动）
else if (免打扰时段已开启 && 当前在时段内) → 静音
else if (防止被@已开启 && 这条@了我 && 群在作用域) → 静音
else                      → 保持微信原样
```

作用域判定：先查排除名单（命中则不生效），再看允许名单。

**② 选择器七处合一（K3）** —— 群发目标、转发目标、防@允许名单、防@排除名单、朋友圈导出名单、加入分组、添加成员，以前是七个各自要做的页面，现在是一个组件三个参数搞定。差异只在：数据源（好友·群·分组·标签）、单选还是多选、能不能新建。

**③ 设置页共用渲染器（K2）** —— 五个二级页加起来 20 多个设置项，控件只有 5 种。渲染器统一负责画和存，加一个新开关只需加一行配置，不用碰 UI 和备份代码。

## 二、数据层（合并后的表）

| 表 | 字段 | 说明 |
|---|---|---|
| `groups` | id / name / sort_order / pinned / created_at | 分组。`sort_order` 由分组管理页的 **▲▼ 上移/下移按钮**写入（点一下即交换相邻两位并存库），不使用按名称/时间的固定排序 |
| `group_members` | id / group_id / username / display_name / type / added_at | **username 上加 UNIQUE 约束**，数据库层面强制"一个好友只能属于一个分组"（旧库是 `PRIMARY KEY(group_id, wxid)`，允许一人多组，必须改） |
| `auto_dnd_done` | chatroom_id（主键）/ handled_at | 已自动设过免打扰的群，用于"只设一次、手动关掉后不再自动打开" |
| `kv` | key / value | 全部开关与数值。配置项处理规则：导入时只覆盖备份里存在的项 |
| `friend_cache` | username / nickname / avatar / updated_at | 好友与群名缓存，供 K3 选择器与 K10 取数使用 |

约定：主键一律用 username（wxid / chatroom id），**不用昵称**（昵称会改、会重名）；分组活跃时间运行时算，不落库；只在微信主进程打开 DB（避开 `:push` / `:tools`）；DB 建在宿主 `filesDir`；**升级必须增量迁移**（drop-recreate 会让用户分组数据全没）；配置**不存 SharedPreferences**（在宿主私有目录，adb pull 不出来，出问题只能猜）。

| 防止朋友圈动态撤回 | 拦截朋友圈动态被删除 |
| 显示朋友圈动态[已删除]标签 | 已删动态加标签 |
| 防止评论撤回 | 拦截朋友圈评论撤回 |
| 显示朋友圈评论[已删除]标签 | 已删评论加标签 |
| 显示撤回提示 | 防撤回生效后，是否**额外显示一条我们自己生成的「已阻止」提示条**；关闭时连以前插过的也一并隐藏 |
| 恢复默认显示 | 开启期间，被防撤回救下的消息（含这期间新拦的）**显示为正常撤回**的样子；关掉后恢复显示原文 |

**默认值：7 项全部默认关闭**，由用户自己逐项打开（v6.3 定）。

> **作用域**：整个域只作用于他人的消息。自己撤回照常成功，自己的「你撤回了一条消息」照常显示，不受任何开关影响。
> **⚠️ 微信自带的撤回灰色条不受任何开关影响**（自己撤回产生的、防撤回关闭时他人撤回产生的都照常显示）——两个提示类开关管的都是**我们自己造出来的东西**。
> **「显示撤回提示」**：管的是防撤回生效后我们自己插入的那条「已阻止」提示条，不是微信原生的撤回提示。
> **「恢复默认显示」**：只是**显示层的伪装**——防撤回照常在拦，消息原文一直在库里，开关只改「看起来是什么样」，关掉就全回来，**不会丢内容**。

**真机验证（2026-10-16，v0.2.9 全部通过）**：
防止消息撤回 / 显示撤回提示 / 恢复默认显示 三开关全链路已验证：他人撤回被拦、原文保留；
「已阻止」提示条插入（负数 msgId 区间，不与微信自增冲突）且按开关显示/隐藏（含历史）；
「恢复默认显示」开启时消息显示为原生撤回灰条、关闭时**原状完整写回**（含 isSend/lvbuffer/reserved 双向快照），原文无损来回切。
自己撤回的放行不受影响；两个「显示」开关同时开时提示条与撤回灰条并存，属预期。

**朋友圈链路取证（2026-10-16 真机实测）**：

朋友圈用的是**独立的库** `MicroMsg/<md5>/SnsMicroMsg.db`（不是主消息库 `EnMicroMsg.db`），
动态在 `SnsInfo`（18 列，`content` / `attrBuf` / `postBuf` 为 BLOB），评论在 `SnsComment`（16 列）。

| 动作 | 微信实际做的 | 线程 |
|---|---|---|
| 删动态 | `delete(table="SnsInfo", whereClause="snsId=?")` —— **物理 DELETE 整行** | main |
| 删评论 | `execSQL("delete from SnsComment where snsID=? and commentSvrID=?")` | `[D]#worker` |

> ⚠️ **删动态和删消息撤回是两个机制**，别套用同一套实现：消息撤回是 `update` 把行改写成撤回态
> （可拦、可还原）；朋友圈是**把行抹掉**，所以策略只能是「拦 DELETE + 把整行归档」，不是「拦 + 改写」。
>
> ⚠️ **删评论还有一层**：评论的可见列表存在 `SnsInfo.attrBuf` 里，而微信在发这条
> `delete` **之前**就已经把 attrBuf 重写掉了（实测顺序：update SnsInfo → replace SnsInfo → delete SnsComment）。
> 所以只拦 `delete SnsComment` **留不住详情页里那条评论**，必须做 attrBuf 的差量检测与还原 —— 成本高一个量级。

**「防止朋友圈动态撤回」已实现并真机验证（2026-10-16）**：三步齐全 ——
① 拦截 `DELETE FROM SnsInfo`；② **恢复 `localFlag` 可见位**；③ 整行（含 `content` / `attrBuf`
/ `postBuf` 三个 BLOB）归档进模块库 `sns_archive` 表。

> ⚠️ **只拦 DELETE 是不够的**：微信删动态是两步 —— 先 `update SnsInfo` 把 `localFlag`
> 的可见位（bit4=16）清掉（实测落成 2），再 `DELETE`。时间线的查询是
> `where localFlag in (16,2064,18,2066,24,2072,…)`，**白名单里每个值都置了 bit4**。
> 只拦第二步 → 行还在库里但查不出来，表现就是「库里有、界面没有」。
> 修法：拦完立刻写回 `localFlag = 原值 or 16`（2 → 18，18 在白名单里）。

实测：删除被拦（`snap=true`）、可见位恢复（`2 -> 18`）、归档三个 BLOB 齐全、64 位 snsId 完整；
重新进入相册后动态确实回来了。

> **能力边界**：只能保住**开启开关之后**删除的动态。之前就删掉的，微信库里那行早被真删了、
> 也没有归档，无从恢复（不是 bug，是数据已经不存在）。

> ⚠️ **作用域实证（与消息撤回不同，别套用）**：微信本地**只删自己的动态**
> （真机归档下来的三条 `userName` 全是本人 wxid），别人删自己的动态在本地不产生 DELETE。
> 所以这里**不区分作者一律拦** —— 若照「只作用于他人」实现，开关永远不生效。
> 实际效果是「不让微信把朋友圈动态从本地库里抹掉」，偏**留档 / 防误删**。
>
> 微信每次删除会发**两遍**（main 一次 + `[D]#worker` 一次），两遍都被拦，归档靠判重只记一条。
>
> 📌 **修正上面的「只删自己的动态」**（2026-10-16 晚，样本变大后）：实际**别人的动态在本地也会被 DELETE**。
> 实测归档 6~8 条，`userName` 是各种不同好友（`wxid_lx9vwt2`、`katherine_zh`、`wxid_2768237` …），
> `createTime` 集中在删前 1 小时内。所以「不区分作者一律拦」不仅是实现选择，也是**必需的**。

**「显示朋友圈动态[已删除]标签」已实现并真机验证（2026-10-16）** —— 见下节。

### 6.2.1 朋友圈动态 [已删除] 标签（`SnsTag`）

**落点取证（四轮真机，全部实测）**：

| 结论 | 说明 |
|---|---|
| ❌ 老版 tag 链在新版不存在 | 新版时间线是 `ImproveSnsTimelineUI`。整棵 View 树上只有一个 `com.tencent.mm.plugin.sns.` 前缀 tag：`MaskImageView` 上的 `qh`，里面只有 `sns_table_256863` 这种**表名**，没有动态 id |
| ❌ child → position 走不通 | 微信自带**重打包过的 androidx**：`getChildAdapterPosition(View)` 报 `NoSuchMethodException`，ViewHolder 的位置字段恒为 -1 |
| ✅ 走 adapter 绑定回调 | `com.tencent.mm.view.recyclerview.WxRecyclerAdapter`（**类名未混淆**）的 `onBindViewHolder(holder, pos)`；`adapter.getData()` 返回 List，元素字段的 `toString()` 形如 `ImproveInfo(name=贸易商陈健峰, snsID='15033729556253184615', rowid=256862, …)` |

**实现要点（每条都踩过坑）**：
1. 钩子挂**基类** `WxRecyclerAdapter`，但 `onBind` 里必须 `adapter.javaClass.name.startsWith("com.tencent.mm.plugin.sns.")` ——
   否则聊天列表 / 通讯录 / 发现页**所有**列表都进解析（性能灾难）。
2. 子类可能覆写 `onBindViewHolder`（挂基类=死钩）→ 额外挂 `WxRecyclerView.setAdapter` 抓具体 adapter 类补挂；
   2 参与 3 参（payloads）重载都要挂。
3. **`position` 与 `getData()` 下标错位**（列表前面有「封面头」等非动态项）→
   拿 item 子树里的作者文字与 `ImproveInfo.name` 对账，`±2` 窗口内**必须唯一命中**才采用
   （`nameOk` 是双向包含，同一作者的相邻动态互相都能通过 → 取第一个会让标签打到别人身上）。
4. **`holder → itemView` 必须排除 RecyclerView 本身**：ViewHolder 普遍持有指向列表的 rv 引用，
   「面积最大」的兜底必然选中它 → 所有 holder 解析到同一个 View → 标签全加到列表容器上，
   且**往 RecyclerView 里 addView 会把微信搞崩**（进程重启）。`ensure()` 里另加了一道拒绝。
5. item 根布局实测是 **LinearLayout 子类**（`lh3.b0` / `lh3.u3`），默认 `addView` 追加到末尾 →
   标签跑到底部、视觉上紧贴**下一条**动态，看着像给别人打的标。必须**插到 index 0**。
6. 严格校验，**宁可不打标**：拿不到名字 / 读不到文字 / 名字短于 2 字 → 一律不采信
   （打错标签比不打标签糟糕得多）。
7. `sns_archive` 只查 `sns_id` 一列且**不加 LIMIT**（无 ORDER BY 时 LIMIT 取的是任意 N 行，
   归档一多就静默漏标）；首屏同步读一次，之后一律后台刷新；`LogX` 是主线程同步文件 IO，热路径日志必须限流。
8. 开关语义 = `antirevoke.sns AND antirevoke.sns_deleted_tag`（数据源是 `sns_archive`，只由防删除写入）。

**真机验证（2026-10-16，全部通过）**：
- 解析率 **114/118 = 96.6%**（`binds=122 sns=118 resolved=114 missed=4`，missed 全是封面头 + 1 个 `ambig2`）
- `offset` 自动校准出 `-2`/`-1`（被 `list.size` 指纹绑定，列表变化即重算）
- **端到端**：对 dump 出的 id 精确模拟「这条被删」→ 标签**正好落在选中那条**上（`hit=true`，
  且该 item 的文字与选中项一致 → offset 无错位）
- **真删全链路**（模拟微信两步删除：`update localFlag=2` → `delete`）：
  `SNS blocked delete … flag=18` → `SNS archived … ok=true` → `SNS_TAG label added #1` → dump `hit=true`（标签**自动贴回**，无需重进页面）

**自诊断**（`adb … --es op snstag --es sub stat|dump|mark|fake|unmark`）：看数顺序
`binds>0`（钩子活）→ `sns>0`（朋友圈限定生效）→ `resolved≈sns`（解析通）→ `hits>0`（清单/符号对）→ `added>0`（真贴上去了）。

**探针**（`--es op snsg --es sub flags|fixall|simdel`）：
- `flags` —— 列归档里每条的**当前** `localFlag`。⚠️ 别拿 `dump` 里的 `flag` 当依据，那是**归档快照**，恒为微信清位后的 2。
- `simdel` —— 模拟微信真实两步删除（走真实拦截路径），验证「拦下 + 恢复可见 + 归档 + 贴标」。
- `fixall` —— 把归档里已不可见的动态批量恢复可见（修历史遗留；实测当前 `hidden=0`，无需修）。

**实测澄清**：归档里的动态 `localFlag` 当前是 **50（含 bit4，可见）** —— 防删除的可见位恢复一直是生效的
（用户反馈的「以前删除的没有回来」原因是那些行**当次**没被拦到、已被物理删除，不是恢复失败）。

> **能力边界**：只能保住**开启开关之后**删除的动态。之前就删掉的，微信库里那行早被真删了、
> 也没有归档，无从恢复（不是 bug，是数据已经不存在）。
> ⛔ **2026-10-20 用户决定：评论 `[已删除]` 标签 + 朋友圈评论防删除 —— 不做了**。
> 代码（`SnsCommentGuard` / `SnsCommentTag` / `SnsCommentLogic`）**保留冻结**，不再投入开发与真机批次；
> 是否物理删除待定。取证与处置见 `docs/取证结论.md` ⑪ 段 与 `docs/并行开发轮次计划.md` R9 段。
> ⚠️ 别误伤：**动态**防删除 + 归档恢复（`SnsGuard` / `sns_archive`）**照常保留**。

**实现状态（2026-10-18 R2，SAF 已接线）**

- ✅ **`core/ActivityResultRelay.kt`（新增）**：模块 APK 没有自己的 Activity，SAF 必须借宿主 Activity 发起、
  再截 `onActivityResult`。挂的是 `android.app.Activity` 的**框架方法**（不受微信混淆影响），三路覆盖：
  ① 精确签名 `(int,int,Intent)`；② 泛化签名（名字含 `onActivityResult`、参数里恰有一个 `Intent`、参数数 3~4）；
