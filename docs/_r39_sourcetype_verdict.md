# R39 · 朋友圈 `sourceType` 位语义定案（2026-11-03 真机）

> 本文只记录**今晚实测得到的事实**，不改写 R38 的架构结论。
> 唯一目的是把「位语义 / 清位延迟 / 存量分布」三件事钉死，供后续判据设计引用。
> 真机：PJD110 / 微信 8.0.48(2588) GP / 模块 0.2.8 / 设备 `467cf5bc`。

---

## §1 三条定案

| # | 结论 | 强度 |
|---|---|---|
| **V1** | `sourceType` 的 **bit1（值 2）是「好友可见位」**，是时间线可见性的**唯一闸门** | 双路径实证（§2.1 同屏对照 + §2.2 真实删除） |
| **V2** | 好友删动态 = `sourceType & -3`（清 bit1）。初始 `2` → `0`；初始 `10` → `8` | 真实删除实测（§2.2） |
| **V3** | 清位**有延迟**：删除后本地行仍为 `2`（正常）约 **3~7 分钟**，之后才被清 | 真实删除逐分钟采样（§2.2） |

配套：bit3（值 8）= **相册位**。它保留与否只决定「当初有没有同步进相册」，与朋友圈能否看见**无关**。
`10 = 2 | 8`、`8 = 仅相册`、`2 = 仅好友可见`、`0 = 都不可见`。

## §3 与 R38 的关系（**不推翻 §1-3**）

这是本文最需要说清的一段，避免误读成「R38 判死行字段判据是错的」。

### 3.1 两个判据必须分开

| 类型 | 命题 | 是否成立 | 依据 |
|---|---|---|---|
| **状态判据** | `&2 == 0` ⇒ 这条**当前不可见** | ✅ **成立**（V1） | §2.1 五条对照 |
| **事件判据** | `&2 == 0` ⇒ 这条**刚刚被删** | ❌ **不成立**（R38 §1-3 仍然正确） | §2.3 存量 36,653 条历史遗留 |

R38 §1-3 排除的是**事件判据**，理由「同作者同形、信噪比 1:5000」在今晚数据下依然成立
（12% 的行长期停在 0/8，单看一行无法区分「刚被删」与「三年前被删」）。

今晚新增的是**状态判据**：给定一个 snsId，`&2==0` 可以**确定**它不会出现在时间线上。
这条以前没有单独验证过，现在有实证了。

### 3.2 `&2==0` 的正确用途

不是「发现删除」，而是：

1. **注入前的可用性筛选**：决定某个 id 值不值得尝试重新插回响应；
2. **渲染侧的可见性预期**：给定 id 预测已渲染列表中「该不该有它」；
3. **快照行的可恢复性判断**：`&2 != 0` 的行本来就在响应里，无需注入。

### 3.3 R38 哪些结论仍然成立

- §1-1（零 DELETE）✅ 不受影响
- §1-3（行字段不能做**事件**判据）✅ **明确保留**
- §1-4（改库 ≠ 改界面）✅ 不受影响——今晚 `src=2` 却仍可见，正是因为**界面由响应决定**，反过来也印证：注入是唯一改界面的路
- §1-14（补位与清位两个写入主体并存、不可归因）✅ 加强：见 §4 新增的「微信自修行值」
- §3 三层架构（快照 / 判删 / 可见）✅ **全部保留**，P3 不可砍

### 3.4 R38 需要订正的一处

§1-2 原文写「实测是 `2→0`，不是 `10→8`」。今晚证明**两条路径都存在**：

- 初始 `2`（仅好友可见）→ 删后 `0`
- 初始 `10`（可见+相册）→ 删后 `8`

R37 观察到的 `2→0` 与今晚 §2.1 第 4 条（`10` 原始行被改为 `8` 后不可见）都成立，不是互相矛盾。
原文的措辞容易让人以为「只有 2→0」，建议在 R38 计划里补一句「`10→8` 同样存在」。

## §4 新发现：微信会自己修行值

| 观察 | 时间窗 | 说明 |
|---|---|---|
| `0 → 2` | 约 7 分钟 | 人工写入非法值 0 后，微信自行改回 2（正常） |
| `8 → 10` | 约 11 分钟 | 人工改为 8 后，微信自行改回 10 |

**对开发的直接影响：**

1. **`setsrc` 实验结果不可信**。改完必须立刻读，中间不能给微信任何同步机会。
2. **未来判断「模块补位是否生效」时，看到的 `8→10` 可能不是模块干的**，是微信自己修的。判据必须同时看模块日志（`SNS srcfix ... 8 -> 10`）与时间戳，不能只看库值变化。
3. **`setsrc` 自身会污染台账**：`SnsGuard.setSrc` 内部会 `upsertVisibleSrc` + `markSrcFixed` + `invalidateAlbumIds`，等于主动制造一条「救回」记录。做实验必须紧跟 `srcfix clean`。

### 未解项 U1：清位的确切触发点

已知：删除后 3~7 分钟内不写库；21:24 刷新、21:26 重进都没有触发；21:28 的某次刷新完成了清位（`2→0`）。
**未确定**：是下拉刷新、是重进、还是后台定时同步。

这条影响「模块在哪一刻截获最稳」，列为下一步取证项。

## §5 实验方法教训（过程记录）

**我犯的错**：20:40 改库改的是「星光龙阳洋」（11-02 18:37），却让用户去找「AAA福盒餐盒厂家」（11-02 20:07）。
两串 snsId 不同，用户看的那条从头到尾都是 `src=10` 的正常动态，导致 20:45~20:51 三轮「还在」全部无效，
一度得出「P3 可砍」的错误结论。发现异常的线索是 `setsrc` 日志打印 `8 -> 8`（而非 `10 -> 8`）。

**规则（写入开发流程）：**

1. 改库与让人看，必须**同一个 snsId**，并在改完立刻回读确认；
2. 让用户找目标时**必须给唯一标识**——同一人同一时段的相邻动态，仅靠「昵称+时间」无法区分；
3. 反直觉结果（如 `8 -> 8`）**必须追到底**再下结论，不能当作读数抖动放过。

## §6 对开发计划的作用（一句话版）

- **P3（可见侧注入）不可砍**，它是唯一能让被删动态重新出现在时间线上的路径（R38 §1-4 已证「改库 ≠ 改界面」）。
- **判删链可以简化**：不必再发明复杂的双轮缺席判据，`&2==0` 直接给出「这条现在不可见」的确定性结论；但**「刚刚被删」仍需基于响应集合的轮次对比**，两者配合使用。
- **灰标不能按全库 `&2==0` 打**：36,653 条存量会淹没真实信号，必须限定在当前渲染集合内。
- **7 分钟窗口期是存档的机会**：删除后本地行短期保持 `2`（内容完好），模块在这段时间内取快照成功率最高。
