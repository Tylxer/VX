## §3 推荐主判据 H（含误报边界、时序证明）

### 3.1 H 的完整定义（优先级分支）

> ⛔ **本节已由 §9 二次修订（2026-11-05 20:51 分页预取实测）改写主干：候选 H 的"双轮缺席"作废，主干换成 §9.3.2 的 B+。**
> 下面的分支块**保留原文仅供对照**，实现请照 §9.3.2。作废理由见 §9.2（缺席在分页语义下必然，与 C1 同类错误）。
> 唯一不变的是**分支顺序哲学**：`&2` 先于 `&4`（bit1 是唯一闸门），私密必须早于删除判定。

```
【作废，仅留档】原 H：
  1) id ∈ 本轮 respIds                          → 撤销
  2) 本地行不存在                                → 放弃（物理删除）
  3) (src & 2) != 0                             → 放弃（可见，防假消失）
  4) (src & 2)==0 && (src & 4)!=0               → 放弃（私密）
  5) 连续 ≥2 个独立轮次缺席 && &2==0 && &4==0    → 疑似删除   ← ❌ 作废（F13/F15）
  6) 其余                                        → 观察态
【生效】见 §9.3.2
```

- 分支顺序的关键（对新主干同样成立）：**可见分支先于私密分支**——bit1（`&2`）是时间线可见性唯一闸门（F1/V1），先判 `&2` 才能正确分流；`&2==0` 之后才轮到「私密 vs 删除」二选一，由 `&4` 分叉。**私密必须早于删除判定**，否则 `src=4` 会被误判「已删」。
- 可见分支是这套判据的灵魂：把 C1（顶锚未变）这个「反推窗口没变」的间接证明，换成「直查行还在不在可见态」的直接证明。§1-7 的分页假消失就是「被挤出 page1 就当消失」，在新主干里该行 `&2!=0` ⇒ 走可见分支，**结构性排除**。
- **私密分支是 F11 的硬闸门**：私密位（bit4）与删除在库里本就可分（`SnsTimelineSrcLogic.kt:127`），漏写会把私密动态误标成「好友删除」——0.3% 但用户一眼能看出错。`reFixAfterClear` 的补位条件 `(src&2)=0 AND (src&4)=0`（`SnsTimelineSourceFix.kt:549`）早已如此处理，判据必须同口径。
- 撤销分支（新主干 2）优先级最高，与「疑似删除」互斥，出现即撤销（`docs/_r37_graytag_datasource.md:553-554`）。新主干里撤销信号 = 「读到 `&2!=0`」，不再依赖「重现于响应」（那只是"这一页返回了它"，F13）。

### 3.2 `&2==0` 的成因清单 vs 用户视角（回答「算不算误报」）

| 成因 | 位形态 | 证据强度 | 用户视角是否「消失了」 | 处理 |
|---|---|---|---|---|
| 好友删动态（`& -3` 清 bit1） | `&2==0 && &4==0` | 已定案（F1） | 是，确定消失 | 判「已删」（分支 5） |
| 好友设为私密 / 仅自己可见 | `&2==0 && &4!=0` | 已定案（F11） | 是，但语义是「仅自己可见」 | ⛔ 判「私密」，**不打已删标**（分支 4） |
| 内容被审核 / 下架 | `&2==0 && &4==0` | **假设（未验证）**：与「删」同形态，无独立位 | 是，用户看也是「消失」 | 判「已删」，用户视角无差 |
| 相册位变更（`10→2` / `2→10`） | bit3 独立，不清 bit1 | 已定案 | 否 | 不进 H，无影响 |
| 自己删自己（物理 DELETE） | 行直接删掉 | 已定案（§1-9） | 是 | 走 T_SNS 路（分支 2），不与 H 打架 |
| 历史存量（30 天前删的） | `&2==0` 各种形态 | 已定案（F10：88.6% 在 30 天前） | 是，但**早就消失了** | **H 靠「曾 ∈ 近期 respIds」挡掉**：陈年行从未进过近期快照，不在候选集 |

**结论（文案与语义对齐）**：
1. **私密与删除库里可分（F11）**，不再是悬案。分支 4 显式处理私密后，**文案可以回到「好友已删除」，无需降级成「已不可见」**——前提是分支 4 真的按私密单独处理，否则 0.3% 的私密动态会被误标。
2. 残余不可分的是「内容下架/审核」（与删同 `&2==0 && &4==0`），但用户视角两者都是「这条我看不到了」，判「已删除」**不构成用户可见的错**。
3. 真正的误报只有一种：**「还在，却被判消失」**。H 的分支 3（`&2!=0` 放弃）把这一种结构性排除。§1-7 的分页假消失就是这一种，H 不会重演。

### 3.3 时序证明：快照要不要记当时的 `src`？

**不需要把 `src` 当判据输入**，理由（三选一，互斥）：

- **`respIds` 成员资格本身就是「当时可见」的证明**：时间线响应只含服务端决定返回（= 渲染）的行。id ∈ respIds ⇒ 当时可见，**无需读 `sourceType` 佐证**。读 `src` 反而重新引入 F9/§1-14 的 `sourceType` 不可归因污染。
- **「本来就没 bit1」和「曾经有、后来被清」由「是否进过 respIds」区分，不由 src 区分**：进过 respIds = 曾经可见；没进过 = 本就不在时间线（分页外 / 存量），不在候选集。

**时序证明由「轮次 + 时间戳」承载，不由 src 承载**：
- 事实序列：`round k: id ∈ respIds`（快照记轮次号 + 时间戳）→ `round k+1, k+2: id ∉ respIds`（缺席）→ `读当前行 &2==0`（确认已清位）。
- 三段各带时间戳，构成完整时序链，**不需要中间态 src**。
- 唯一要读 `&2` 的时刻是**缺席侧确认、且 gate 窗口关闭之后**（分支 3/5），且必须读**当前**值，不是快照里的旧值（旧值在清位前必然 `&2!=0`，读了会漏判，见 §3.4）。

**具体反例（为什么记 src 反而错）**：两个 id `A`、`B` 都 `&2!=0` 且都进过 `respIds`。`A` 三年前进过、之后躺库里；`B` 昨天进过。若快照只记 src，两者 src 相同（都是 2 或 10），**无法区分**。但「曾 ∈ respIds」配时间戳能区分：`B` 近期、`A` 三年前。H 只对 `B` 生效，`A` 被快照 TTL 淘汰，不进候选 ⇒ 12% 存量天然隔离。**「本来就没 bit1 vs 曾经有后来被清」是时间维度的问题，src 解决不了，只有时间戳能解决。**

### 3.4 致命前提：`&2==0` 状态确认**必须**在补位关闭下进行

- F9：模块 `reFixAfterClear`（`SnsTimelineSourceFix.kt:531`）在微信写 0 的同一时刻把 bit1 补回。开着开关，被删行 `&2` 永远读不到 0（或只能在 350ms 静默窗内抢读，racy）。
- **读值时机（订正 P1-3）**：U1 时序（`docs/_r40_p0_gate.md:218-238`）是「响应到达 → 落库清位 → 补位」**在同一轮内完成**，清位发生在响应之后、补位之前。所以 `&2` 应在 **gate 窗口关闭（`onResponse` 后 3000ms，`SnsRoundLedger` 的 upsert 窗口到期）之后**读，此时清位已大概率完成——**不是「响应那一刻」读**。原 §3.3「缺席侧确认那一刻读」的措辞需据此修正为「缺席侧确认**且窗口关闭后**读」。
- ⇒ **补位关闭是 H 状态确认的必要前提**（双轮见下）。补位关闭还有三重收益：(i) §1-4 已证「改库≠改界面」，补位本就不解决痛点；(ii) F5 补位污染 `sourceType` 归因；(iii) 补位是 H 状态确认的头号干扰源。
- **补位关闭是第 1 期必须落地的改动**（开关默认关，或判据评估期强制关），代价与回滚在 §5 登记。

#### 3.4.1 「双轮缺席」的取舍（P1-3 补）

> ⛔ **本节结论整体作废（§9，2026-11-05 20:51 分页预取实测）。**
> 作废原因不是"取舍偏好变了"，而是**本节的两个前提都被推翻**：①「轮 = 独立事件」——分页响应内容必然不同、间隔 3.3s 即越过 `DUP_GAP_MS`，每翻一页就记一轮（F15）；②「缺席可跨轮累加」——每轮窗口只覆盖它自己那一页（F13/F14），跨页累加等于把"不在这一页"当成"不在服务端"。**生效方案见 §9.3.2，确认机制由「缺席」换成「状态跨 `epoch` 持续」。** 本节保留以记录当时为什么选了折中。

U1 说清位同轮完成，`&2` 在窗口关闭后读时清位已大概率完成 ⇒ **单轮缺席 + 读 `&2==0` 可能已足够**；双轮会把判定推迟 ≥5 分钟（微信节流，F3）。三选一，**本 lane 选「折中」**：

| 取向 | 判据 | 代价 | 判定 |
|---|---|---|---|
| 保守（双轮） | 连续 ≥2 轮缺席才判 | 判定推迟 ≥5 分钟；且缺「双轮必要性」的实测证据 | ❌ 证据不足 |
| 激进（单轮） | 单轮缺席 + 窗口关闭后 `&2==0` 即判 | 若清位偶发 >3000ms，读 `&2` 会读到旧值 ⇒ 漏判（假阴性，非误报） | ⚠️ 可选，需登记假设 + 证伪探针 |
| **折中（选定）** | **单轮缺席 + `&2==0` → 观察态；双轮缺席 + `&2==0` → 疑似删除** | 判定仍推迟，但观察态即时反馈 | ✅ 精确率优先，符合 §1-7 事故后的保守默认 |

**折中的理由**：假阴性（漏判、推迟标记）无害——用户最多晚几分钟看到灰标；假阳性（误标正常动态）有害——重演 §1-7 满屏假消失。所以宁可慢，不可错。**「双轮」防的不是「清位延迟」竞态（那已被「窗口关闭后读」解掉），而是「单轮抖动/空响应」这类采样噪声**——它的存在性不依赖清位时序。

**登记假设（H5）**：「gate 窗口关闭（3000ms）后，被删行的清位必已完成」。证伪探针：受控删除后逐 500ms 读 `sourceType`，若存在「>3000ms 才清位」的轮次 ⇒ 单轮读 `&2` 会漏判，双轮兜底依然成立（观察态不升级）。

### 3.5 H 的边界（覆盖不到的，明说）

> **订正（§9）**：B+ 的候选面不再是「进过 `respIds`」，而是「`T_SRC` 成员（`last_seen ≥ T0`）」。覆盖面因此**变宽**（不再是 P0-2 的 25%，而是快照能扫到的全部可见行，上限 3000 行），但同时也把"覆盖率够不够"变成了一个必须实测的量（§9.6 G3），不再是"结构上只能 25%"。

### 4.3 Q3：P0-2（25% 覆盖）对架构的强制约束 + 补档旁路 + T_SRC 关系

P0-2 的 `pct=25%` 必须拆成两件事（`docs/_r41_srcdist.md:187-190`）：
- **A. 容量/累积型缺口**：分母是库最近 60 条，分子是账本（≤12 轮×10 条）里出现过的 id。3 轮只积累 30 个 id ⇒ 25% 是**轮次不足**，随轮次累积上升。**低成本可解**：窗口点查（F12）+ 更多轮次。
- **B. 结构性缺口**：首屏响应只覆盖最近 ~10 条（约 24 分钟跨度），更早的历史动态只有走「翻页」才被读到，而翻页不经 `c3.N` ⇒ 永远进不了 `respIds`。**只能靠「可见范围从库点查」或 `T_SRC` 台账的 `everVisible` 补**。

**Q3 核心回答：快照 = 复用既有两张表，**不新建第三张。**

| 需求 | 现成实现 | 结论 |
|---|---|---|
| **成员/everVisible 台账**（哪些 id 曾可见 + 时序） | `SnsTimelineSourceFix.snapshotVisible()`（`:693-720`）键集分页扫 `&2!=0` → `GroupDb.upsertVisibleSrc`（`:646`）写 `T_SRC`（`sns_visible_src`，`GroupDb.kt:51`）；schema 含 `sns_id PK / source_type / first_seen / last_seen / fixed_orig`（`:252-258`）；`listVisibleSrc`（`:686`）读 | **复用**。`first_seen/last_seen` 天然承载 §3.3 要的时序证明，不新造第二套成员台账（否则 = P1-5 双读端闪烁） |
| **内容快照**（注入 payload：content/attrBuf/postBuf 三 BLOB） | `T_SNS`（`sns_archive`，`GroupDb.kt:50`）**已存在**，schema 含 `content/attr_buf/post_buf`（`:214-229`），`archiveSns`（`:417`）写入 | **复用**，但**改填充入口**：现由「DELETE 拦截」写（本场景零 DELETE ⇒ 现为空，F6）；第 1 期改为「快照路径」（respIds/窗口点查的可见行）也写 `T_SNS` |

**关键点**：
1. **`T_SRC` 天然免疫「灌满存量」**：`snapshotVisible` 只扫 `sourceType & 2 != 0` 的**当前可见**行，88.6% 陈年 `&2==0` 存量**永远进不来**。这不是靠「曾 ∈ respIds」前置条件挡的，是**成员判据本身（可见行）挡的**——F10 的「前置条件是唯一防线」在此被更硬的「成员判据 = 可见行」替代。
2. **⛔ 判据只读 `T_SRC` 的 `first_seen/last_seen/source_type`，永不读 `fixed_orig`**。`fixed_orig` 是补位台账语义（R31h 红线：`sns_visible_src` 补位台账不得作「被删」判据）。复用 `T_SRC` 作成员台账**不触碰红线**，因为读的是「曾可见的时间戳」而非「补位次数」。
3. **快照只能存「活着时看到的」**：`pageVisible` 只收 `&2!=0` 当前可见行 ⇒ 天然拿不到「已经不可见」的行，这是**正确**的（快照本就是「见到过才存」）。
4. **天花板**：单轮 30 页 × 100 = 3000 行，从最新往回翻（`SnsTimelineSrcLogic.kt:55/58`）。对活跃账号覆盖不到深历史。**够不够**：够——判删侧（H）只关心「进过近期响应」的动态（本就 ≤3000 行的量级），深历史本就不在 H 的有效范围（§3.5）。
5. **增量定义**：`T_SRC` 的 `CONFLICT_IGNORE` 意味着老行不删、台账只增不减 ⇒ 长期是一张**全历史 everVisible 表**，这是成员台账该有的形态；`T_SNS` 内容表则要单独定 TTL（见 §5 第 1 期 gate）。

**补档旁路的具体形态（复用 snapshotVisible，加窗口点查）**：
| 补档项 | 答案 |
|---|---|
| 触发时机 | 每次**独立同步轮次**，`respIds`/窗口确定后，用 `[ctBot_k, ctTop_k]` 点查（F12 已证可复现响应集合） |
| 补哪一段 | `SnsInfo WHERE localFlag=2 AND (sourceType & 2)!=0 AND createTime ∈ [ctBot_k, ctTop_k]`，逐条 `readRow`（`SnsGuard.kt:680`）取内容 → 写 `T_SNS`（`GroupDb.kt:417 archiveSns` 复用/同型入口） |
| 怎么防「满屏已删」 | 成员判据 `&2!=0` 天然排除 88.6% 陈年存量（见上）；补档行**只进 `T_SNS` 内容表、不进判据**——判删仍只信 respIds 缺席 + `&2==0 && &4==0` |
| 与 `T_SRC`/`T_SNS` 的关系 | 成员同源（都是 `&2!=0` 可见行）：`T_SRC` 记「曾可见 + first_seen/last_seen」，`T_SNS` 记「可见时的内容 payload」；两表同轮写、成员判据一致，无「台账说有/快照说没有」分叉 |

**补档的价值**：让「翻页可见但从未进响应」的历史动态也能被 resurrect（注入侧），并给 H 的「曾可见」证明提供更稳的来源（窗口点查不依赖响应对象存活）。判删覆盖仍由 H 决定，两者解耦（`docs/_r38_plan.md:124-129`）。

### 9.2 A / B / C 判决（先定尺子，再选，不写"各有优劣"）

**三条硬标准**（尺子，先立后用）：
- **S1 信号来源**：判据用的信号必须是**用户能看见的事实**（UI 看不见 / 库里不可见位），不能是窗口几何、轮次计数器、响应集合的补集。
- **S2 确认机制**：判删的"确认"不得建立在「不在某次响应里」之上。R31h（`docs/_r38_disproved.md:32`）与 §1-7 分页假消失（`:28`）都是这一个动作造成的，F13 已证明这个动作在分页预取下**必然误判**。
- **S3 证据现成度**：方案的可满足率/覆盖率必须有现成实测支撑；"以后探针验证"不算。

| 方案 | S1 | S2 | S3 | 结构性死因 / 存活理由 |
|---|---|---|---|---|
| **A 拆 session/page** | ❌ | ❌ | ❌ | 见下 3 条 |
| **C 严格版（页内 ct 覆盖）** | ❌ | ❌ | ❌ | 继承 A 的 2、3，并多一条自我指涉 |
| **B 降级为状态判据** | ✅ | ✅ | ✅（需 2 处加固） | 唯一不需要"缺席"的方案 |

**A 必须死，三个理由都是结构性的，不是风险偏好**：
1. **session 归属没有硬信号**。实测能拿到的只有：页内间隔 3367ms / 3294ms（`_r41_srcdist.md:218-220`）与"进页→下拉"的 59s。代码侧也没有 page 序号 / `isLast` / 请求参数（`SnsRoundLedger` 记录的字段只有 `no/atMs/n/ctTop/ctBot/ids/same`，`SnsRoundLedger.kt:39-58`）⇒ 阈值只能在 3.3s~59s 之间**拍**一个。拍错的失败模式是**静默**的：阈值偏大 ⇒ 两次真操作被并成一个 session ⇒「连续 ≥2 个 session 缺席」**永远凑不齐** ⇒ 判据退化为"永不判删"，而 gate 里看不出来（没有误报，只有零产出）。
2. **即使 session 分对，"同一窗口体系内的缺席"仍要落到 `ct ∈ [ctBot,ctTop]`**，而 F14 已证包围盒由未删行反推 ⇒ 被删行若在页首/页尾，包围盒收缩到不含它 ⇒ **永不触发**。
3. **A 的确认机制仍是"响应集合的补集"**，只是把"轮"换成"session" ⇒ 直接违反 S2，是 R31h 同一动作的换皮。

**C 必须死**：它就是 A 的第 2 条，且更糟——它要求"该页**应不应当**包含它"，而"该页范围"由该页**实际返回的行**定义。用「它没被返回」去证明「它本该在返回集合里」，是循环论证，逻辑上不可判定。

**B 存活，但必须加固两处（否则会在另外两个地方翻车，见 9.4）**：
- **B-1 成员面宽度**：`T_SRC` 只增不减 ⇒ 里面有多年累积的"曾可见、后来被删"的老行，若全用，开功能当天就会把历史删除一次性上标（41,281 条 `&2==0` 的入口，`docs/_r41_srcdist.md:30-31` 已预警）。⇒ 加 **`T0`（判据启用时刻）截断**：只判 `last_seen ≥ T0` 的成员，历史成员永不补标。
- **B-2 单次观测不够稳**：清位写入与回填之间有一个**瞬时中间态**（这段时间读到的 0 是假的），加上读失败/采样噪声。⇒ 加**快照周期持续性确认**（§9.3.2 分支 5）：它用的是"同一状态被**重复观测**"，**不是**"缺席"。
  ⚠️ **必须说清持续性确认救不了什么**：如果 `&2==0` 是"永久未回填"（F17 的另一支），那它会一直保持 0 ⇒ 持续性确认会**把它确认成删除**，不但救不了、还加速误判。**这一支只能靠 §9.6 G0 的零删除基线排除**，不能靠确认机制。两件事分工：`epoch` 挡瞬时态，G0 挡语义错。

⇒ **判决：选 B（记作 B+，B 主体 + T0 截断 + 快照周期持续性）。**

**为什么 B 比 A 更硬，一句话**：A 把"删了"证明成"它不在这次响应里"；B 把它证明成"**我在库里看得见它的可见位被关掉了，而且关掉之后一直是关着的**"。后者不经过任何窗口、任何页面、任何轮次。

#### 9.3.2 新主干（优先级分支，命中即停）

### 9.4 两个反问的正面回答

#### 9.4.1 「区分不了『刚被删』和『三天前就删了但一直躺在快照里』」——时间戳够不够？

**先看现有表能给什么**（`GroupDb.kt:252-258/646-668`）：

| 字段 | 语义 | 对本题的作用 |
|---|---|---|
| `first_seen` | 第一次被观测到可见 | 与"删于何时"无关，只用于算"可见了多久" |
| `last_seen` | **最后一次**被观测到可见（每次 upsert 都刷新，`GroupDb.kt:666`） | **下界**：删除必然发生在 `last_seen` 之后 |
| `source_type` | 最后一次观测到的值（`:665`） | 成员资格自证（`&2!=0` 才算曾可见） |
| `fixed_orig` | 补位前原值 | ⛔ 禁用（R31h） |

⇒ **删除时刻 ∈ (`last_seen`, 首次观测到 0 的时刻]**。现有表**没有**"首次观测到 0"这个字段，所以现在只有下界、没有上界。补一列 `zero_seen_at`（追加列，非新表，放在观察态表或 `T_SRC` 均可）就能把区间闭合。

**会不会把"三天前删的"当"刚删的"？**
- **会被判成「已删除」——这是对的**，它确实被删了，不是误报。
- 会**不知道具体是哪天**删的：若用户三天没进朋友圈，快照这三天没跑，`last_seen` 停在三天前、`zero_seen_at` 是今天 ⇒ 区间宽达三天。分辨率 = **快照周期**（`epoch` 间距），不是秒级。
- ⇒ **产品口径硬约束：文案只能写「已删除 / 已不可见」，⛔ 不得写「刚刚删除 / 今天删除」**。这条不是文案偏好，是这条判据唯一诚实的表述。写"刚刚"就变成了一句判据支撑不了的断言。

**所以：时间戳够用来回答"删没删"（产品要的就是这个），不够用来回答"什么时候删的"（产品不需要，文案也已回避）。** 若要更细，补 `zero_seen_at` 把分辨率从"无上界"收到"两个相邻 epoch 之间"，成本一列。

**必须同时锁死的一条**：`last_seen < T0` 的历史成员**永不判**（9.3.1）。少了这条，"三天前"不是问题，"三年前"的 41,281 条（`docs/_r41_srcdist.md:20-31`）才是问题——那就是开功能当天满屏灰标。

#### 9.4.2 R31h 红线：B 用 `T_SRC` 当成员来源，凭什么不算触碰？

**第一步，把红线的因果链拆开。** `SnsTimelineMerge.kt:159-163` 的原文说得很具体：

> 绝不能用 `listSrcFixedIds`（补位台账 `fixed_orig`）：台账装的是「补过位的可见动态」，每条正常动态都在里面，而时间线是**分页**的（一页 10 条）——200 条台账里必然有 190 条不在当前页，「不在响应里」被判成「被删」。

⇒ 这条链有**两环**：(i) 成员集用了补位台账；(ii) **删除信号 = 「不在这一页的响应里」**。真正致命的是 **(ii)**：铁证是那次注入的 24 条**全部**能从 `SnsInfo` 读回 `attrBuf`（`attempt=24 ok=24 emptyBuf=0`）；而它们来自补位台账（`listSrcFixedIds`），补位的动作本身就是把 bit1 置回（`fixTarget`/`FIX_BITS`，`SnsTimelineSrcLogic.kt:46-52`）⇒ 这 24 条的 `&2` 全为 1，全是正常动态。**如果当时用的是 `&2==0`，这 24 条一条都不会被选中，R31h 根本不会发生。**

**第二步，形式化说明"成员面变宽"在这一维上无害。**

B 的误报充要条件 = 「一条**正常**动态当前满足 `&2==0 && &4==0`」。
- 这个条件**与成员集多大完全无关**：把成员从 10 条扩到 3000 条，只要那 3000 条当前都 `&2!=0`，误报数为 **0**。
- 反过来说：只要存在一条正常动态当前 `&2==0`，**旧的 H（窄候选）也会误判**，因为它读的是同一个 `&2==0`。
- ⇒ **B 与 H 在"误报"这一维上是同一个风险源，B 没有额外增加。** B 唯一扩大的是**候选面**（召回），而误报由状态位决定，不由候选面决定。

**第三步，B 确实引入了 H 没有的一个新风险面（必须承认）**：**历史成员**——曾经可见、很久以前被删、一直躺在 `T_SRC` 里。它当前就是 `&2==0 && &4==0` ⇒ 会被判"已删"。用户可见症状与 R31h 一样（满屏灰标），但成因完全不同（这是"陈年旧账被翻出来"，不是"分页误判"）。

**⇒ 结论：B 不触碰红线，前提是下面三条同时成立，缺一条就不成立。**

| # | 护栏 | 为什么必须有 | 落地位置 |
|---|---|---|---|
| a | **成员只来自快照路径**：`snapshot()` 的键集扫描（查询自带 `(sourceType & 2 != 0)`，`SnsTimelineSourceFix.kt:724`）→ `upsertVisibleSrc`（`:709`）。**排除** `SnsGuard.setSrc` 的写入口（`SnsGuard.kt:1239`，它会把任意值——**包括 0**——写进台账） | 否则台账里会混进 `&2==0` 的成员，成员资格不再等价于"曾可见" | 给 `upsertVisibleSrc` 加来源参数，或把成员判据写成「记录值 `&2!=0`」 |
| b | **⛔ 永不读 `fixed_orig` / `listSrcFixedIds`** | 原禁令原封不动；`fixed_orig` 是补位前原值，与"曾可见"无关 | `SnsTimelineMerge.kt:159-163` 注释保留 |
| c | **`T0` 截断 ∧ 首启不回灌** | 挡掉 41,281 条陈年 `&2==0` 的入口（`docs/_r41_srcdist.md:30-31` 已预警"前置条件是唯一防线"） | 新增 kv `T0`，判据只吃 `last_seen ≥ T0` |

|---|---|---|
| 成员资格来源 | `id ∈ respIds` | `T_SRC` 成员（`source_type & 2 != 0` ∧ `last_seen ≥ T0`） |
| "当时可见"的证明 | 「`respIds` 成员资格本身就是当时可见的证明」 | 「**台账里 `source_type` 仍是 `&2!=0`，且 `last_seen` 是观测时刻**」——即"某个时刻，模块亲手读到它的可见位还在" |
| 为什么原理由塌了 | — | `respIds` 只证明「**这一页返回了它**」，不证明"它一直可见"；而且 `respIds` 的时间戳依附 `round`，`round` 的定义已被 F15 污染（每页一个"轮"） |
| 还要不要读 src | 不要（"读 src 反而引入 F9 污染"） | **要，但必须区分两种 src**（见下），这是本节唯一的实质改动 |

**两种 `src`，一个能读一个不能读——这是最容易写错的地方**：

| 来源 | 性质 | 能不能当证据 |
|---|---|---|
| `T_SRC.source_type` | 模块**自己写的观测记录**（唯一写入点受 `admit()` 的 `&2!=0` 过滤，`SnsTimelineSrcLogic.kt:22`；`snapshot` 查询自带 `&2!=0`，`SnsTimelineSourceFix.kt:724`） | ✅ **能**。它是"某时刻我亲眼看到它可见"的存档，不会被微信改写（`upsertVisibleSrc` 只在 `CONFLICT_IGNORE` 失败时覆盖，且只有快照路径会调） |
| `SnsInfo.sourceType`（历史值） | **共享可变状态**：微信清位 + 微信自愈（F6）+ 模块补位（F9）三方写，不可归因 | ❌ **不能**。只能读**当前值**（`&2==0` 这一瞬间的事实） |

⇒ 新表述：**「时序证明由 `T_SRC.last_seen`（观测时刻）+ `T_SRC.source_type`（观测到的值）承载；删除判定只读 `SnsInfo` 的当前值」**。原 §3.3 那条"两个 id 都进过 respIds 无法区分"的反例依然成立，只是区分手段从"respIds + 时间戳"换成"`last_seen` 时间戳"——后者更硬，因为它是**模块自己记的**，不依赖响应对象存活（比 §4.2 Gate③ 的窗口点查还少一层假设）。

#### 9.5.2 §4.2 Gate② 改写（删掉"等双轮缺席"）

```bash
# 【旧】删后等双轮缺席 + 清位（3~7 分钟）   ← ❌ 作废：双轮 = 两个"页"（F13/F15）
# 【新】三段式：
# ① 删前：确认目标在 T_SRC 成员里（last_seen ≥ T0），否则本次实验无效
adb shell "am broadcast -a com.lx.wxgroup.action.PROBE --es op snsg --es sub srcstat -p com.tencent.mm"
# ② 删后：等一次真同步（清位）→ 读当前值（补位必须已关，否则永远读不到 0）
adb shell "am broadcast -a com.lx.wxgroup.action.PROBE --es op sql --es q \
  'select snsId,sourceType from SnsInfo where snsId=<目标负id>' -p com.tencent.mm"
# ③ 再跑一次快照（推进一个 epoch）→ 再读一次当前值，仍为 0 才进 suspect
adb shell "am broadcast -a com.lx.wxgroup.action.PROBE --es op snsg --es sub srcfix -p com.tencent.mm"
# gate 线：suspect 集合 == 恰好 {目标 id}，精确率 100%
adb shell "am broadcast -a com.lx.wxgroup.action.PROBE --es op snsguard --es sub stat -p com.tencent.mm"
```

**三处口径变化（别照旧脚本跑）**：
1. **不再需要第二次"缺席"**——需要的是第二次**状态读数**，而且中间必须跨一个完整 `epoch`（快照跑完），否则 ②③ 是同一个时间点的两次读，等于没复核。
2. **删前必须确认它是成员**。不是成员 ⇒ 判据根本不会评估它 ⇒ 实验无效（旧脚本的"删前确认进 respIds"这一步语义换成"确认进 `T_SRC`"）。
3. **Gate② 的等待时间不再由微信节流决定**，而由"用户下一次进朋友圈 / 手工跑一次快照"决定 ⇒ 实验可控性**变好**（这是 B 相对 A 的一个额外好处：不用等 ≥5 分钟凑两轮，F3 那个死结在这里不存在）。
4. **③ 里 `sub=srcfix` 现在会连补位一起跑**（`run()` 里快照步 + 补位步连着做，`SnsTimelineSourceFix.kt:121-167`）；补位关掉后它又会整段 return（F16 ②）。⇒ 拆开关（9.5.3）之后要给一个"**只快照不补位**"的入口（建议 `sub=srcfix sub2=pure` 或独立 `sub=snap`），否则 Gate② 的 ③ 跑不了。**这是命令级的前置条件，不是可选项。**

| 期 | 原计划 | B+ 下的改动 | 净变化 |

### 9.6 新增 gate 与假设（B+ 的地基，按"能不能上线"排序）

#### G0（**硬 gate，决定第 2 期是否存在**）：零删除基线

> 回答 F17：`&2==0` 到底是"服务端逐条判定不可见"，还是"全表清位后只回填本批"。

**做法**（不需要任何删除动作，纯被动）：
0. **必须在可控好友环境里做**：新账号只加 verity 一个好友（或测试机上的独立账号）。⛔ 主账号（几百好友）**做不了**——每小时都可能有人真删，增量非 0 分不清是"未回填"还是"真删"，增量 0 也证明不了什么。这一步的成本必须提前接受。
1. verity **不发也不删**；
2. 我方连续进朋友圈 / 下拉刷新 10 次，并等 2 次后台同步；
3. 每次操作前后取 `count(*) from SnsInfo where localFlag=2 and (sourceType & 2)=0`；
4. **gate 线：全程增量必须 = 0。任何一次出现新增 0，本 gate 失败。**

**失败分级处置（写死，不留现场讨论）**：
| 增量 | 判读 | 处置 |
|---|---|---|
| = 0 | `&2==0` 是删除专属信号 ⇒ B+ 地基成立 | 继续第 2 期 |
| 1~5 条/10 次操作 | 存在少量"未回填"路径 | **必须**保留 `epoch` 持续性闸门，且 suspect 只作"观察态"、**永不升级打标** |
| > 5 条/10 次操作 | `&2` 含大量"页外"成分 ⇒ 与 C1 同类 | **第 2 期取消**，产品降级为"只做可见侧注入"（`docs/_r38_plan.md:124-129` 的既有边界） |

> ⚠️ 为什么这条 gate 必须先跑：它决定的是"判据存不存在"，不是"判据准不准"。跑之前写任何 `SnsWinArbiter` 代码都可能是白写。这是本 lane 认为**优先级高于一切实现**的一条。

#### G1 零回灌（上线 gate）：开启后 `suspect` 必须瞬间为 0

`T0` 写完后第一次评估，`suspect` 集必须为空。非空 ⇒ `T0` 截断失效 ⇒ 就是 §9.4.2 的"缺 c"情形 ⇒ 症状与 R31h 一致 ⇒ **回滚**。
探针：`op=sql` 查 `count(*) from T_SRC where last_seen < T0`（应 >0，说明历史成员确实存在且被挡）与 `snsguard sub stat` 的 `suspect=0` 对照。

#### G2 `epoch` 闸门真的生效

人为把一条正常行动的 `sourceType` 置 0（`op=snsg sub=setsrc`，只改单行），它必须在**跨过一个 epoch 之后**才进 `suspect`；同一 epoch 内重读不得进。
探针：置 0 → 立即 stat（`suspect` 不含它）→ 跑一次快照（epoch+1）→ stat（含它）→ 再 `setsrc` 恢复 → 下个 epoch 后标自动撤销。

#### G3 成员覆盖率

`T_SRC` 里 `last_seen ≥ T0 ∧ source_type & 2 != 0` 的条数，对照 7 天内可见行 856 条（`docs/_r41_srcdist.md:49-54`）。
若成员数 ≪ 856 ⇒ 快照 30 页上限（3000 行）不是瓶颈，瓶颈在触发频率 ⇒ 提高触发频率（每次真同步），不是提高页数上限。
