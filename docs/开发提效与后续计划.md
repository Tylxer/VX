## 一、慢在哪（拿本轮实测说话）

### 1.1 最大的浪费不是写代码，是**取证回路**

R31 这半小时（02:35–02:50）为了 4 个取证维度（窗口排名 / 逐列对比 / 表清单 / 表结构）
写了 `rank` / `cols` / `tbl` / `sch` 四个专用探针，代价是：

| 动作 | 单次耗时 | 次数 | 合计 |
|---|---|---|---|
| 编译 `assembleDebug` | ~40 s | 4 | 160 s |
| 装包 `adb install -r` | ~20 s | 4 | 80 s |
| `force-stop` + 拉起 + `sleep 12` | ~24 s | 4 | 96 s |
| **微信被迫重启（打断你）** | — | **4** | 你要重新进页面 4 次 |

**≈ 5.6 分钟纯等待，外加你被打断 4 次。** 而这 4 件事本质都是「跑一条 SQL 看结果」。

### 1.2 次大的浪费是**判据失效**，不是执行慢

本课题累计 3 次因为「对着工具输出下结论，而不是对着事实」：

| 事故 | 我当时看到的 | 实际 | 代价 |
|---|---|---|---|
| `sourceType in (64)` | 反汇编里的立即数 | 全表 0 行命中 | 一整轮方向错误 |
| 「already 分支也记台账」 | 逻辑上说得通 | 把 229 条**正常**动态标成已删 | 真机事故，要清洗数据 |
| 「attrBuf 全为 null」 | `getString` 返回 null | 实际 174 字节（BLOB 取值失败） | 差点推出"6.2 无解"的相反结论 |

⇒ **判据错一次，代价相当于 5 次装包。** 所以提效要优先投在"少犯判据错"上。

### 1.3 第三是**工具与脚本脱节**

- `dev.py loop`（全流程编排）、`logclear` 探针**早就存在**，这轮一次都没用；
- `_snsq.py` 每次运行仍 `force-stop` 重启微信，理由是「日志 5000 行上限」——
  但 `logclear` 早就能解决，**脚本比功能旧了一代**。

## 四、这次提效的验收标准

不是"感觉快一点"，而是三个可量化的数：

1. **单次取证耗时**：85 s（编译+装包+重启）→ **~1 s**（`probe sql`）
2. **一轮真机批次的装包次数**：N 次 → **1 次**
3. **每轮判据返工次数**：近三轮 1~2 次/轮 → 目标 **0**

第 3 条靠的是纪律而不是工具，所以写进 `开发回路速查.md` §1.4：
**BLOB 禁止用 `getString` 判空**；以及"先在库层用 `op=sql` 否掉，再上界面看"。

## 五、从《开发技术手册（总文档）》摘出来的东西

2026-10-28 通读该手册（2490 行 / 61.6 KB）。结论：**只采纳 2 条流程机制**（5.1 / 5.2），
第三条（版本断言）我们已有且更强、不采纳（5.3）；其余不采纳，理由见 5.4。

采纳的 2 条共同点：**成本半小时内、治的是我们真实存在的空档**。

### 5.1 复核报告绑 diff hash（原手册 4.4）

**空缺在哪**：`派发审计台账` 只记"派了什么任务"，不记"复核的是哪一版代码"。
中途再改一行，报告就与代码对不上，而没人能发现。

**⛔ 不能直接照抄"绑 git sha"**：我们的流程是 **先复核 → 再 commit**（§六 有 post-commit
自动推 main），复核那一刻 `HEAD` 还是上一版，记 HEAD sha 是错的。

**改法：把改动「暂存后」算 hash，不绑 HEAD。**

```bash
# 复核开始与放行前各算一次，必须相等
git add -A                                  # 暂存全部改动（含新增文件），不 commit
git diff --cached | git hash-object --stdin # 得到 <diffhash>
```

**⛔ 不能只写 `git diff`**：`git diff` 不含未跟踪文件，而我们经常新增 `.kt` 文件 ——
新文件改了 hash 不变，校验等于没做。必须先 `git add -A`。

报告文件名与首行：

```
<task>-<diffhash前8位>-review.md
# Review <task> @ diff:<diffhash>
- 结论: 通过 / 需修改
- 证据: <文件:行号 / 签名字符串 / 命令输出>   ← 禁止纯断言
- 问题清单: <编号 + 严重度 + 后果>
- 回滚方案: <git revert sha / 关 X 开关>
- commit: <放行并提交后回填 40 位 sha>
[DONE]
```

**放行判据（三条全中才算有效报告）**：① 有「结论」字段 ② 至少一条可复算的证据引用
③ 结尾 `[DONE]`。`[DONE]` 只证明"写完了"，不证明"结论对"。
**放行前必须复算** `git add -A && git diff --cached | git hash-object --stdin`，
与报告里的 diffhash 不一致 ⇒ 复核作废、重派。半截文件（无结论 / 无证据）不得放行。
（暂存区在 commit 前保持不变，所以"再改一行"必然让 hash 变 —— 这正是我们要的。）

### 5.2 金丝雀：定期验证"复核者本身"（原手册 4.5）

**空缺在哪**：我们做过**单测的变异验证**（改坏代码看测试是否红），但**从没验证过复核子代理**。
它说 PASS 时，我们没有任何证据区分"真没问题"和"它根本没看出问题"。

**做法**：准备两个已知带 bug 的 diff，定期（每 5 轮 / 换模型路由后）丢给复核者：

| 编号 | 变异 | 应报出 |
|---|---|---|
| K1 | hook 签名少一个参数类型 | 签名不匹配 / 注册必失败 |
| K2 | 回调层删掉 `try/catch` | 异常会打穿宿主 |

**判据**：两个都报出 ⇒ 该复核者本周期内结论可信；**漏一个 ⇒ 本次复核结论降级为「参考」，
关键 hook（改写返回值 / 碰存储层）强制人工终审**。
台账记一行：`金丝雀 YYYY-MM-DD K1=pass K2=pass`。

### 5.3 版本断言：手册这条**不采纳**（我们已有且更强），但顺手挖出我们自己的一个 fail-open 缺口

**先订正一处我自己的错判**：我一开始以为我们没有运行时版本断言。读代码后确认
`core/VersionGate.kt` 早已实现，而且比手册那条强得多：

| 维度 | 手册 | 本项目现状 |
|---|---|---|
| 包名过滤 | 有 | `HOST_PACKAGE` |
| 主进程白名单 | 有 | `isMainProcess()`（`HookEntry.kt:74`，非主进程打 `skip process=`） |
| versionCode 断言 | `!= 2588` 拒绝 | 白名单逐条比对（`VersionGate.kt:67`） |
| 签名校验 | 无 | **SHA-256 指纹比对**（`:73`） |
| 拒绝时留痕 | 打日志 | `LogX.w("DISABLED: ${verdict.reason}")`（`HookEntry.kt:117`） |

⇒ 手册这条对我们**零增量**。

**但对照时发现一个真缺口**：`whitelist` 第二条

```kotlin
Target(Channel.GOOGLE_PLAY, "8.0.72"),   // versionCode=0, signatureSha256=null
```

`versionCode = 0L` 和 `signatureSha256 = null` 在 `check()` 里都是**"不校验"**语义
（`:67`、`:73` 的短路条件）。即：微信一旦升到 8.0.72，门禁**放行**，
但锚点全是按 2588 硬编码的（`Anchors848.kt`），而**跨版本自动定位的 `DexKitLocator`
尚未接入**（`DexKitLocator.kt:45` 仍写"M1 接入后"）⇒ 变成「门禁说 OK、hook 全都挂不上」的
**半死不活态** —— 正是我们最想避免、也是 `VersionGate` 注释说要避免的那一态。

**这就是 fail-open，和这个文件的唯一职责（宁可失效不可闪退）方向相反。**

**改法（二选一，需你定）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（保守，推荐） | 删掉 `8.0.72` 条目，等真装 8.0.72 再连同锚点一起加 | 该版本会被拒（`not whitelisted`），日志明确 |
| B（留位但关门） | 保留条目，但 `check()` 遇到 `versionCode==0L` 时直接 `Reject("target incomplete")` | 多 3 行，防以后再有人填空条目 |

**另**：`VersionGate.kt` 顶部 KDoc 写「版本不匹配时静默退出，一行桩都不打」，
与 `HookEntry.kt:117` 实际打 `DISABLED:` 日志不符 —— 注释漂移，改一行即可。

**判据**：`grep whitelist` 后每个条目都有非 0 versionCode + 非 null 签名；
模拟改 `versionCode` 不符时日志出现 `DISABLED: versionCode mismatch` 且无 `hook registered`。
