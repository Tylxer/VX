## 轮次 3 尝试：**未产生轮次**（2026-11-03 22:33，第二次冷启后进朋友圈）

22:33 冷启 → 用户进朋友圈 → 有完整 UI 渲染日志（`SNS_DELTAG tree depth=9 host=g2`，10 条动态），
但 **`c3.N` 一次都没被调用** ⇒ 账本无新增轮次。

### 结论：微信首屏有缓存/节流，反复冷启不能堆轮次

| 尝试 | 结果 |
|---|---|
| 22:27 同进程：进 → 刷 → 刷 → 退 → 进（4 个动作） | 只 1 次 `c3.N` |
| 22:31 冷启后进朋友圈 | 1 次 `c3.N` ✅ |
| 22:33 再冷启后进朋友圈 | **0 次**（走本地缓存） |

⇒ **第 0 期拿多轮的正确顺序只能是**：
1. 冷启 → 进朋友圈（拿 1 轮）
2. **必须有新数据**（好友发动态）→ 再进/刷新（拿第 2 轮）
3. 或等足够长的间隔（>5 分钟）再冷启

⛔ 纪律：不能靠「让用户多刷几次」或「反复冷启」堆轮次，两者都已被实测证否。

### ⭐ 重大发现：`subset=false` 的原因是「新动态走 INSERT，不走 UPDATE」

| 观察 | 说明 |
|---|---|
| `miss=-3399959319660981746` | 这个 id **在响应里、不在 upsert 批次里** |
| 但库里查到了它，`src=2` | ⇒ 它**确实落库了**，只是没经过 `updateWithOnConflict` |
| `ctTop` 1793715767 → 1793716520 | 正是这条新动态，顶锚变了 |

⇒ **新动态首次出现 = INSERT**。`SnsGuard.onSnsUpdateAfter` 只挂 `updateWithOnConflict`，
**采不到新增行** ⇒ 我的 P0-1 判据「`respIds ⊆ upsertIds`」在「本轮有新内容」时**必然 false**。

### 判据缺陷定性

| 命题 | 结论 |
|---|---|
| **假设 A**（`respIds` 能代表服务端本批返回行） | ✅ **仍然成立** —— 新动态确实落库了（库里查得到），A 说的是「代表返回行」，不是「走 update」 |
| **P0-1 判据**（`respIds ⊆ upsertIds`） | ❌ **表达有误** —— 它实际测的是「这批 id 是否都走了 UPDATE」，而新增行永远走 INSERT |

**修法（下轮装包必改）**：集合比对必须并入 INSERT 采样。
```kotlin
// SnsGuard 里补一个 insert 钩子（同一 db 对象上的 insertWithOnConflict / insert）
XposedHelpers.findAndHookMethod("com.tencent.wcdb.database.SQLiteDatabase",
    lpparam.classLoader, "insertWithOnConflict",
    String::class.java, ContentValues_cls, Int::class.java, afterHook)
```
判据改为 `respIds ⊆ (upsertIds ∪ insertIds)`，日志加 `insertN=`。
**在此之前，`subset=false` 不能作为 A 证伪的证据** —— 这是必须写进 `_r40_p0_verify.md` 的判读纪律。
