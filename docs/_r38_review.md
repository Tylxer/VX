## 结论

**GO-WITH-CONDITIONS**

三句话理由：

1. **事实底子极好**：约 60 处代码/文档引用逐条回查，**0 处硬伤（❌）**、5 处轻微瑕疵（⚠️，均为 1 行漂移或标签错位，不影响任何判据结论）；R31h 红线、互斥分支、窗口闸门纪律完整保留。这份计划可以作为开发基线，不需要推倒重写。
2. **但有 2 个 P0 必须改才能开工**：① 第 0 期量化 gate「`respIds` 与 `fixed=N` 同量级」**量纲不成立**（`N`≈全台账 2118 行、`M`≈单批 10~20，字面永不达标 ⇒ 按 §5.5「任一 gate 不过 ⇒ 停当期」四期链整体锁死）；② 存档侧「成员资格 = 本轮 `respIds`」与项目**自己的**混合渲染取证冲突（`docs/conclusions/moments.md:219-224`：首屏/刷新走响应、**翻页走 DB 查表**）——滚过的历史动态不进快照表，且判删/注入被窗口闸门锁死在「顶部近期窗口」，计划未声明这个有效范围。
3. **另有 5 个 P1**：判据表行 4 的短路位置使「假设 B 证伪后改以方向 B 为主」的退路在表内走不通（行 7 要 `D`，`D` 内嵌 `W`）；行 7 打标在正常使用下命中率≈0（需用户手动进好友主页）；「看得见」被绑死在「判删成立」上；「删了看不见」前提只在首屏/刷新路径被验证过，翻页路径（srcfix 开启时行还在且 `src=10`）未验证；`snsTagIds()` 有**双活跃读端**（`SnsTag.kt:679` + `SnsDeletedTag.kt:1690`）而计划只列一个，「同一读端」表述事实错误，P3 只改一处会静默失效或 2s 闪烁。

## §3 Gate 可执行性问题（§5）

### 3.1 「`respIds` 与 `fixed=N` 同量级」——量纲不成立，字面永不达标（P0-1）

复现方式：读了 `SnsTimelineSourceFix.kt:530-569`（`reFixAfterClear` 全文）与 `SnsTimelineMerge.kt:139-144`。

- `M`（`SNS-INJECT first hit: respIds=M`，`:155`）= **单批响应的 id 数**。非空 `c3.N` 响应是首屏/刷新批次，量级 10~20（分页一页 10 条，`GroupDb.kt:555`）。
- `N`（`SNS srcguard re-fix after clear fixed=N`，`SnsGuard.kt:220`）= **整本台账里当前处于「被清位」状态的行数**。`reFixAfterClear` 不判断服务端是否返回，只按台账全量补（`:535-537` 取 `listVisibleSrc` 全量 → 分块 UPDATE）；`updateFilterTimeLine` 每轮全表清位 ⇒ 每轮 `N` ≈ 台账总量。台账实证：`派发审计台账.md:2455`「上一轮 `fixed=2118`」、`_r38_disproved.md:46` F5「`re-fix fixed=2118`」。
- ⇒ `N ≈ 2118` vs `M ≈ 10~20`，**常态差 ~100 倍，「同量级」字面永不成立**。而 §5 第 0 期 gate 四项是 AND 关系（「任一不达标 ⇒ 停在第 0 期」），§5.5 又写「任一 gate 不过 ⇒ 停在当前期」⇒ **第 0 期永远无法通过，四期链整体锁死**。
- 附带说明：假设 A 的探针文本（§3.1）同样写「比对 `N` 与 `M` 是否同量级；长期无关即被推翻」——按上述量纲，即使假设 A 为真，探针也永远给出「无关」的假阳性证伪。**这条探针从设计上就无法区分 A 的真假**。
- 修改建议：换一个同量纲的判据。例：`op=snsg sub=sqlspy on` 抓同一轮 `updateWithOnConflict("SnsInfo", …)` 批次的 id 集合（挂点已在 `SnsGuard.kt:241-246`），与该轮 `respIds` 做**集合比对**（不是数量比对）：每轮响应 id ⊆ 同轮回填批次 id，且连续多轮成立 ⇒ A 成立。或退一步：只验「`M` 随退出重进首屏增长、且快照表成员能逐条对应到某轮 `respIds`」（第 1 期 gate 已有后半句，可前移）。

### 3.2 「正常动态被判缺席 = 0 次」——受控窗口内可达，但测的不是判据精确率

- 结构上，新基准（上一轮 `respIds` + 按 id 的窗口覆盖闸门）已把 R31h 分页噪声（`attempt=24 ok=24`）排除在外：翻页不走 `c3.N`（见 §4.2），所有非空轮次都是首屏/刷新同构窗口，混合轮次问题不存在——这一点比计划自己以为的还要干净。✅
- 但「正常动态缺席」在真实世界**不等于删除**：权限变更/对方设可见性/屏蔽同样让 id 退出响应（R37:373 G7 自认「这类只能靠 H3b 区分」，而 H3b 已废）。第 2 期 gate「正常动态 `suspect.n` 必须为 0」同理：测试期间只要有好友改一次权限，`suspect.n` 就 >0 ⇒ 立即回滚。**这条 gate 实质上测的是「测试窗口内没发生权限变更」，不是「判据精确」**。
- 修改建议：gate 拆成两条——①「正常动态**被打标** = 0」（这才是 R31h 复发的真口径，行 6 默认不打标时它恒真，价值在于守住未来升级）；②「`suspect.n` 增量须可归因」（每条 suspect 能对应到一个真实删除样本或一次已知权限变更，否则登记为未解项）。
- **对主会话追问的回答（结合分页，这条 gate 是否永远过不了）**：**不是永远过不了**。分页不走 `c3.N`（`moments.md:222`），所有非空轮次都是首屏/刷新同构窗口——「上一轮 `respIds`」基准里混入分页噪声的路径**结构性不存在**，R31h 的 `attempt=24 ok=24` 正是被这个结构排除的。真正会让正常动态缺席的非删除因素只剩**权限变更/屏蔽**（R37:373 G7，H3b 已废无法区分）。受控测试窗口内（期间没有好友改权限）该 gate 可达；但它测的是「窗口内没发生权限变更」而非「判据精确率」，所以仍建议按上述拆两条。另确认一个有利细节：现有代码 `respIds` 的收集（`SnsTimelineMerge.kt:139-144`）发生在注入（`:190-237`）**之前**，注入元素不会污染下一轮基准——P3 必须保持这个顺序。

### 3.3 四期 gate 链：不是逻辑死锁，是概率性锁死（P1 级）

- 第 0 期 gate 四项里两项高危：C1 可满足率（R37 预测大概率不过）+ 3.1 的量纲判据（字面永不达标）。§6.1 假设 B 证伪后的正当动作是「切换已注册的备选架构继续」，但 §5.5 只给了「停在当前期，退回 §6 重设计」——**证伪假设和 gate 失败被混为一谈**。若不补一条「假设证伪 ⇒ 就地切换备选方案（代价已登记）⇒ 继续下一期」的通道，四期链有较大概率永远停在第 0 期。
- 另：「5 轮真同步」的时间成本未评估。§1-13 已定案只有后台定时同步/退出重进首屏才真同步（`MSYNC watch` 60s `observed=0`）。5 轮可能要以小时计；判据里应明确允许「退出重进首屏」凑轮次，并给出单轮判真标准（`MSYNC OK scene=256 type=214` + `SNS srcguard re-fix` 行）。
- 第 1/2/3 期 gate 本身量纲正常（成员可对应、`suspect.n=0`、开/关对照一致、界面硬证据），无死锁风险。第 1 期 gate「`archive` 零新增」恒真（零 DELETE 事件），作为对照项可以，但别当 gate。

## §4 架构缺陷（重点）

### 4.1 `respIds` 到底是什么——已静态判定：纯网络响应集合

复现方式：通读 `SnsTimelineMerge.kt:112-243`（`onBeforeResp` 全文）。

- `respIds` 来自 `param.args[3]`（`c3.N(IILjava/lang/String;Lq54/zb5;)V` 的第 4 参数）的字段 `f`（`:129-131`），逐条取 `Id` 入集合（`:139-144`）。**它是 `zb5` 响应体列表的 id 集合，即当次网络响应的内容，不含任何本地库读出的条目。** 计划「存档成员资格 = `respIds`」= 「只存档**经过当次同步响应**的 id」。
- 佐证：文件头 `:16-19` 自证「联网首屏/刷新是拿响应内存对象渲染的，根本不读库」；`docs/conclusions/moments.md:220-221` 独立佐证（`w5.onSceneEnd` 全方法无 `d2` 存储层调用）。

### 4.2 「越滚越存不到」——部分成立，且比计划想的更严重的是「判删/注入的窗口锁死」（P0-2）

复现方式：读 `docs/conclusions/moments.md:219-224`（项目自己的静态取证，计划全文未引）。

- 事实：UI 是**混合渲染模型**——「首屏/刷新：列表由响应内存对象渲染」；「**翻页：走 `d2.t5`，带 `stringSeq` 游标——查表**」（moments.md:220-222）。即用户滚动看的历史动态**从 SnsInfo 库读出**，不进任何 `zb5.f` 响应。
- 对存档侧的影响（「只存档最新 10~20 条」的精确回答）：
  - **不完全等于**只存最新 10~20 条——若后台同步的新批次也经 `c3.N` 投递（与 `x2`/scene 256 的关系静态不可判定，列为假设 H1），则模块活动期内**所有同步过的内容**都会进快照表，不只是首屏。
  - **真实缺口有两个**：① 模块安装/钩子激活**之前**就已存在的历史（除非微信重传，一般不传）；② 任何不走 `c3.N` 的投递路径（H1）。
- 对判删/注入的影响（更硬）：判据要求「本轮响应 ct 区间覆盖该 id 的 ct」（C2/C3/G2），而所有非空 `c3.N` 轮次都是**首屏/刷新窗口**（翻页不进 `c3.N`，轮次反而同构干净）。⇒ **只有顶部近期窗口内的动态，其缺席才可判、才可被注入**（P3 候选 ∩ 当前窗口）。一条 3 天前的动态被删：没有任何一轮的窗口覆盖它的 ct ⇒ 永远 `放弃(静默)`，永远不进疑似集合，永远注入不回。
- 计划的自相矛盾处：§3.0 称「从『事件耦合』改为『时序/窗口耦合』」，自我评价为解耦；但实际「存档 ∩ 判删 ∸ 注入」三者的有效范围全被「必须出现在某次同步响应里/窗口内」绑定。计划对 C1 可满足率有自觉（假设 B），但对**有效范围 = 顶部近期窗口**这个产品级限制没有任何声明——按现在的写法，会在第 2/3 期验收时以「旧动态判不出/注不回」的形式意外撞上。
- 修改建议：① 第 0 期加探针量化「翻页可见内容 ∩ 历史 `respIds`」覆盖率（进首屏 → 滚到底 → 对比快照/`respIds` 账本）；② 快照写入器补一条旁路：按当轮响应窗口 `[ctBot, ctTop]` 从库点查补档（**不读 sourceType**、只做内容存档）——存档可以过富，判据仍只信 `respIds`，这样不碰 R31h 红线又能覆盖翻页历史；③ 在 §3 显式写明「本功能有效范围 = 顶部近期窗口」，并升级为带探针的假设。
- 严重级别：**P0**。它决定整个功能的产品上限，且与 §3.0 的自我评价冲突；不修则第 2/3 期的验收标准（合法样本恰好都在近期窗口，能过）会给出虚假的安全感。

#### 4.2.1 对主会话三问的直接回答（`respIds` 边界专题，已独立复核其提供的事实）

1. **§3「存档从删除事件解耦」成立吗**——**只成立一半**。解耦的是**写入触发**（不再依赖被拦的 DELETE，改由响应出现驱动，这部分成立且是真实改进）；没有解耦**覆盖范围**——成员资格从「被拦的 DELETE」换成「本轮 `respIds` 出现 + ct 落在该轮窗口」，只是把耦合对象从「删除事件」换成「同步响应窗口」。对「用户从未在响应里见过的动态」（长期没刷期间发的、沉到分页底部以下不再被重传的）**永久不覆盖**。建议把 §3.0 的自我评价改为：「**写入触发已从删除事件解耦；覆盖范围收敛为『看到才存、看不到不存』**」。
2. **存档覆盖率的产品边界要不要写进文档**——要，且必须写成显式边界句：「**存档成员 = 曾在某次同步响应窗口内出现过的 id；从未出现过的动态不进存档、不进判据、不进注入候选。**」并同步收紧第 3 期验收口径：合法样本「她发→用户刷到→她删」能全覆盖（刚发的必在响应里），但验收结论只能覆盖这个场景，**不能外推为「防删除一般有效」**。
3. **P3 注入是否事实上只对「当前窗口内的近期动态」有效**——**是，三重锁死**：判据侧 C2/C3 要求本轮响应 ct 区间覆盖 id.ct（旧 id 永远「放弃」）；候选侧 ∩ 当前窗口；渲染侧注入只进首屏响应、按 ct 插到首屏底部（`SnsTimelineMergeLogic.kt:40-45`），滚到下面是 DB 路径照样看不到。一周前进过快照、如今 ct 在窗口外的动态，注入不成立（与主会话判断一致）。建议 §3.2 可见侧把「**注入有效范围 = 首屏 + 近期窗口**」写成不变式，并明确「老动态注入」不做——现有 `archiveCursor` 轮转注入旧动态的行为（`SnsTimelineMerge.kt:169-186`）正是要消除的已观察副作用。

### 4.3 注入与微信自身写库/清位的交互——§3.4③ 的对策答非所问（P2）

复现方式：读 `SnsTimelineMerge.kt:24-28`（注入机理注释）、`SnsGuard.kt:227-239`、`SnsTimelineSourceFix.kt:510-514`。

- 先纠正一个机理错误：计划 §3.4③ 担心「注入的响应元素被下一轮 upsert 清掉 ⇒ 抖动」。实际每轮 `c3.N` 拿到的是**新建的 `zb5` 响应对象**，上一轮注入的元素随旧对象消亡，不存在「元素被覆盖」。真正的交互在另外两处：
  1. 注入元素会**随微信自己的「写库 + 事件 + 渲染」全链路走完**（`:24-28` 明证）——即模块虽「不写库」，**微信会把注入元素写进 SnsInfo**。写进去的 `sourceType` 是什么，静态不可判定（假设 H3）。若写入带 bit1，下一轮 `updateFilterTimeLine` 全表清位又打回 0（F3）⇒ 库存在 2→0→2→0 间振荡；若恰好被 `reFixAfterClear` 收编（该 id 在台账里，曾可见），则停在 10——这正是 F4「开着开关删的已回 10」的路径。
  2. 计划给的対策「重现走分支 0 `revoked_at` 撤销」是**判据侧**动作，防的是「误判删除」，防不了上述库层振荡与 UI 闪烁。真正的抖动防护只能是「每轮重新注入」（现状天然如此，因为注入挂在每个非空 `c3.N`）+ 明确接受同步间隙的闪烁并写进代价。
- 修改建议：§3.4③ 该行重写为「注入元素经微信写库链路落库，`sourceType` 终态静态不可判定（H3）；抖动防护 = 每轮重注入 + 第 0 期 sqlspy 抓注入同轮 `updateWithOnConflict` 的 values 实测」。
