#### ⛔ R32-B 的分诊价值 —— 以及主会话在这里写错过一次

**关掉「分组行」开关后仍然跳。** 主会话当时的推论是「⇒ 否掉了我们的锅」—— **这个推论是错的**，
已由 R34-3 分诊纠正（2026-10-28）：

- `ConvFilter.install` **不看** `CHAT_GROUP_ROW_ENABLED`。关掉开关后模块**仍然**：换了 adapter、
  hook 了 `setAdapter` / `correctTooHigh` / `LongClickRemap`、走 `onPinFoldChanged` **和**
  `onDataChanged` 的两次 `notifyDataSetChanged`。
- ⇒ 该实测**只证伪**了「跳 = `GroupRowView.build()` 重建整棵 View 树」（R32-2 的整改目标），
  **完全没有排除我们**，反而成了主假设的强证据。

#### R34-3 分诊结论（详见 `docs/_r34_foldjump.md`）

**主假设**：「跳」= `getCount()==layout.size`（`ConvFilter.kt:1399`）与 `wrapped.count` 在折叠过程中
**分两次不同步地对齐**（±19 行 ≈1700px）；「顿」= 第二次那次全量 rebuild（含 `rebuildModels` 的
N 次 SQL + `nameOf` 查表）。**顿 ≠ 跳**，是两个现象。

支撑事实（①档）：`rebuildForPinFold` 刻意不更新 `lastStamp`（`:1236`）⇒ 下次必然全量；
inner 一 notify 就 `onDataChanged()` ⇒ 250ms 后**无条件** rebuild+notify（`:1193-1203`、`:672-683`）
⇒ **一次折叠必然两次 notify**，第二次落在用户以为已经结束之后。

候选处置：P1（`rebuild()` 返回 Boolean，只在 changed 时 notify）+ P2（行数对齐从折叠检测解耦，
在 inner observer 里 `|wrapped.count - snaps.size| >= 2` 时即时对齐）。⛔ 三条硬约束都不碰。

**当前状态**：已批准落 5 条纯日志补丁（零行为），装机后由用户跑 G-A/G-B/**G-C** 三组。
**G-C = LSPosed 取消勾选模块、重启后折叠 5 次，是唯一能证伪「锅在我们」的实验，优先级最高。**
在 G-C 结果出来前不落 P1/P2。
