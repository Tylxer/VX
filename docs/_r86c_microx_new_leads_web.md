## 一句话结论

**搜到一条有实质价值的新线索：runtime DEX dump 工具族（FART / frida-dexdump / R0DUMP）专门解决「InMemoryDexClassLoader 无落盘中间态」——这正是我们 `_r72_microx_forward_parse.md:235` 判「微X壳打不开」的卡点C 论据。** 该论据现已不成立（有成熟工具可绕过），但「工具能 dump ≠ 能治本」：dump 出业务 dex 后还要重新定位字节来源、再判可控性，离治本仍隔两层，且工具部署有真机成本。

## 新线索逐条

### L1【新·高价值·未验证】runtime DEX dump 可绕过卡点C
- 我方旧论据（`_r72_microx_forward_parse.md:235`）：「卡点C（无中间态）：材料里没有已解密的 ZIP 临时文件或 dex 缓存，InMemoryDexClassLoader 不落盘」。
- 外部事实（2026-07 横评 `https://cn-sec.com/archives/5331973.html`）：
  - **frida-dexdump**（4.5k star）：全进程内存搜 DEX magic + map_list 校验 + 磁头修复，一代壳/整体加密类事实标准。
  - **FART**（`github.com/hanbinglengyue/FART`，2.7k star，2025-01 仍更新）：主动 loadClass + hook `ClassLinker::LoadMethod` + CodeItem 重组，**二代壳（方法抽取）唯一通用方案**，有 frida_fart_hook.js 分支免刷机。
  - **R0DUMP**（`github.com/tiwe0/r0dump`）：FART 思路移植到 Android 16/ART，**明确支持捕获 InMemoryDexClassLoader 加载的内存 DEX**，官方参考构建 OnePlus 9。
  - **BlackDex**（6.4k star）：独立 APK、免 root(5-10)/root(11-13)、不依赖 frida/xposed。
- 判定：卡点C 从「物理不可达」降为「有工具路径但未在本机验证」。**不自动推翻「微X字节来源不可复制」的最终裁决**——那只依赖卡点A（key/算法在 native .so，已证实），_dump 只解决「拿到业务 dex 代码」这一步_，不解决「模块能否调用私有通道」。
- 落地成本：FART 需 AOSP 镜像或 frida 环境；R0DUMP 官方仅适配 OnePlus 9/Android16；我方设备 1440×3200 未核型号/Android 版本 ⇒ 适配性 UNKNOWN。

### L2【新·方法论·可借鉴】同类 Xposed 模块静态脱壳先例（非微X本身）
- `52pojie.cn/thread-617193`（2017）：某微信群发工具（包名 `wechat.simpleforwarder`）assets 加密 dex + `libJpush.so`，native `JNI_OnLoad` 动态注册 `getXClass` → 读首字节当 XOR key（该例 0x2D）→ `decryptFun` 单字节异或 → `DexClassLoader` 加载，解密后不删文件 ⇒ 运行时可直接拖出明文 dex。
- 价值：证明「Xposed 模块 + assets 密文 + native so 解密」这类架构在本生态有成熟静态分析方法，且微X同族（`_r72:69-76`：Android≥26 用 InMemoryDexClassLoader、<26 用 DexClassLoader；`:227`：两个 `libwxcoreloader.so` 有 `JNI_OnLoad`/`CallMethod` 导出）。
- 局限：该例是单字节 XOR（极弱），微X是 rolling-XOR 字符串混淆 + native CallMethod（`_r72:111/:117/:235`），**算法不同，脚本不能直接套**；只能借鉴「先定位 native 解密入口、再找落盘/内存中间态」的思路。

### L3【旧料·新发现但非现版源码】微X前身 WechatForwarder 的第三方反编译 smali
- `github.com/Everpure/wechatforwarder`（及 starhacker/csxrzeng/lzpfmh 等 fork）：README 明写「generated by reversing engineering from WechatForwarder by fkzhang」，Smali 71.4% / Java 28.6%，`assets/WFHooks` 59KB，创建于 2016-05，支持微信 6.x 时代。
- 价值：这是微X作者早期独立转发模块的**逆向产物**（非原版源码、非现版微X），可看早期转发 hook 形态。
- 局限：微信 6.x 与 8.0.48 的 hevc/ImgInfo2/fullpath 链完全不同； forn 无新提交（pushed 2016-05）。对 R86c 治本无直接价值，仅作历史参考。
- 作者本人 GitHub（`fkzhang`）目前仅 `WechatUnrecalled` 一个公开仓库（Java，防撤回），无 WechatForwarder 源码公开。

### L4【噪音·已排除】
- **微X本体源码**：`github.com/Xposed-Modules-Repo/com.fkzhang.wechatxposed` 只有 README，最后 commit 2021-02、最后 Release 2.43 在 2024-01；多篇 2026 年下载站仍写「曾开源、现闭源」。⇒ 无新源码放出。
- **NewMiko/Nuke**：`dartcv/NewMiko` 已改名 `dartcv/Nuke` 且**明确闭源**，「1.0.4 存档源码」链接（`dartcv/NewMiko/tree/archives`）已 404。其「自动发送/接收原图」是**发图时勾选原图**，不是本项目「转发历史消息图片」场景，不可直接用。
- **WAuxiliary / NewMiko 类模块的「自动原图」**：均为发送时自动勾选原图选项，与"保证转发源图字节在场"是不同问题；下载站描述无实现细节，不足以采信。
- **wcx**（`github.com/Johnny520/wcx`，2026-11-25 仍活跃、Kotlin、带 deobf/unidbg-harness 去混淆工具链）：功能表含「发送原图/自动查看原图/一键转发」，但同属发图勾选语义；其去混淆工具链可作参考，不是现成解。
