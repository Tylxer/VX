## 维度2：dev.py probe
结论：部分成立（编排思路正确，但旗舰链路实测不可用）
理由（含实跑证据）：
1. 机制本身工作：`probe snsg stat --n 6` 实跑成功（8.7s），广播投递、拉日志、过滤、去重都正常。
2. 硬伤一：**参数名对不上**。`EntryReceiver.kt:870` 的 `op=sql` 读的是 extra `q`，而 dev.py `cmd_probe` 只把 `--val` 映射成 `--es val`（dev.py:209-210），probe 根本没有 `--q` 选项。计划 §二 与速查 §1.2 的旗舰示例 `probe sql --val "select …"` 实际会收到空 q → 返回 `SQLX 拒绝：只允许 select/pragma/with（收到 ''）`。
3. 硬伤二：**adb shell 二次解析**。实跑 `probe sql --val "select count(*) from SnsInfo"` 直接 `/system/bin/sh: syntax error: unexpected '('`，广播都没发出去。这正是速查 §360 记录过的坑（值要包单引号），但 dev.py probe 没做任何转义——SQL 里的空格、括号、`*`、`|`、引号都会被设备端 sh 吞掉或杀死。
4. `--n` 只控制本地显示行数，不会转成 `--ei n` 传给模块；`op=sql` 的行数上限恒为默认 60。
5. `--clear` 竞态：logclear 与探针是两条独立广播（dev.py:201-211），微信被冻结/后台延迟时可能出现「探针输出先落盘、logclear 后清空」→ 空日志假阴性。0.4s 间隔 + 无回读确认，赌的是有序投递。
6. **失败时静默返回旧数据（最危险）**：实测微信在后台（前台是番茄小说）时，probe 的「Broadcast completed」检查通过，然后安安静静打印 3 分钟前的旧日志尾部（`共 22 行`），没有任何「模块没响应」提示。`am broadcast` 的 completed 只证明 AMS 收了广播，证不了模块执行了——这个判据近乎虚设。
7. 耗时虚标：实跑 probe 8.7s、`_snsq.py` 12.4s，不是文档说的 ~1s。
8. n 截断按设计取「去重后最后 n 行」，sch/rank 这类多行输出超长时头部会丢，使用者要意识到。
问题与改法：
- probe 增加 `--q` 选项（或 sql 分支同时接受 `val`），三处文档示例同步改；
- 所有 `--es` 值按速查 §360 修法包 sh 单引号（值内 `'` 转义为 `'\''`）——不修这条，SQL 里的 `userName='wxid_x'` 一样死；
- `--n` 同时传 `--ei n` 给模块；
- 投递确认改为「发后回读校验」（日志 mtime 变化 / 出现 `PROBE logclear 已清` 行），失败时响亮报「微信不在前台或模块未响应」，别把旧日志当结果打印；
- `--wait` 默认 3s 对 io 线程查询偏短，sql 类建议默认 5s；
- ⚠️ 另提醒：审核任务给的 `probe snsg srcfix stat` **不是只读**——sub2=stat 会落到 srcfix 的 else 分支执行 `SnsTimelineSourceFix.run()`（EntryReceiver.kt:578-579），这是**写微信库**。我因此没有执行它。建议把 srcfix 家族在速查标注写操作（本仓已有 `snsg show` 同类前科）。

## 维度4：runReadOnlySql 安全性
结论：部分成立
理由：
- 成立的：BLOB 处理正确（`getType==4 → getBlob → <blob NB>`，失败显 `-1B` 与 `<blob 0B>` 可区分，cellOf SnsGuard.kt:1267-1278），正是 1.2 事故的修法；跑在 `io{}` 后台线程，无 ANR 风险；cursor 在 finally 里 close，异常路径不会锁库；行数 cap 防爆。
- 判据可绕过的点：
  1. **`with` 是大口子**：`WITH x AS (SELECT 1) DELETE FROM SnsInfo` 以 with 开头通过检查；Android 的 `rawQuery` 不校验语句类型，会编译并 step 传入的语句——**非 select 语句会被真正执行**（已知坑：rawQuery 不像 execSQL 有反向限制）。⇒ 可任意 update/delete/insert 微信库。同理 WITH…UPDATE / WITH…INSERT。
  2. **pragma 部分可写**：`pragma user_version=9`、`pragma application_id=`、`pragma auto_vacuum=`、`pragma journal_mode=` 等改库头/状态，也都以 pragma 开头通过检查。
  3. 多语句 `;`（如 `select 1; delete …`）：rawQuery 只编译执行第一条、尾部被忽略，**这条实际无害**；但在判据里显式拒绝内部 `;` 是便宜的纵深防御。
  4. 注释/大小写绕过不存在（`/*x*/select` 会被拒，fail-closed；大小写已 lower）——这两条没问题。
  5. **接收器是导出的**（RECEIVER_EXPORTED，EntryReceiver.kt:78/127），设备上任何 app 都能发这条广播。注释说判据是「防误写库」，实际上它同时是防第三方 app 借模块写微信库的唯一闸门。开发机自用可接受，但注释应写明这是安全边界，不能当纯防误触。
- UI 线程/卡顿：cap 只限行数不限语句——`select * from SnsInfo order by createTime desc`（17 万行）在返回前 60 行前要全表排序，秒级；在 io 线程不卡 UI，但短暂持读锁（WAL 下读者不互斥，影响有限）。异常路径不会锁库（cursor 必 close）。
问题与改法：
- 把 `with` 从白名单去掉，或解析 CTE 列表后要求主语句仍是 select；
- pragma 收敛成白名单（table_info / table_list / database_list / foreign_key_list 等只读项）；
- 显式拒绝内部 `;`；
- 注释补一句「此判据同时是导出接收器的安全边界」。
