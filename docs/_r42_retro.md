# R42 反思：为什么绕了一大圈才用最简单的甲方案

写于 2026-11-05 22:10，甲方案真机验证通过之后。
不是检讨书，是给下一轮用的判据。

## 0. 先把账摆平

| | 路线甲（写时拦截） | 路线乙（事后补救） |
|---|---|---|
| 核心动作 | 一个钩子 + `values.remove("sourceType")` | 判据 + 快照台账 + 补位 + 响应注入 + 归档恢复 + 灰标 |
| 代码量 | **约 300 行**（含探针） | **约 5,000 行**（本轮已删） |
| 额外写库 | **0** | 实测 13 分钟改写 636 行 |
| 需要判「哪条被删」吗 | **不需要** | 需要，且这是最大难点 |
| 竞态 | 无（写在发生前） | 有（写后 350ms 静默窗，可能被同批覆盖） |
| 从决定到真机验证 | **1 小时**（21:41 装包 → 21:53 通过） | R27 ~ R41，跨 5 轮 |

**这张表我一开始就该画。** 如果画了，选择不需要犹豫。

## 1. 根因一：我一直在回答「观测」问题，而用户要的是「控制」问题

用户要的是「她删了，我还能看见」—— 这是一个**控制**问题：能不能阻止删除写进库。
我做的却是**观测**问题：如何在删除写进去之后，判断出「哪一条被删了」。

这两件事的难度完全不对称：
- 控制：找到写入口，把要写的键摘掉。**写入口是唯一的**，R27 就已经找到了（`updateWithOnConflict`）。
- 观测：`sourceType` 会被微信自己修回来、会被分页预取掩盖、会被 ctTop 节流卡住 —— 我为此设计了
  C1 满足率、双轮缺席、B+ 状态判据、`T0` 截断、`epoch`，一次次塌。

**最要命的认知错误**：我把「判据做不出来」误读成「这条路没有简单解」。
实际上判据做不出来，恰恰说明**这个方向选错了** —— 需要判据本身就说明你在补救，而不是在阻止。

## 2. 根因二：把一次局部失败泛化成路线否决

R27 有过一个正确结论：「拦住 SQL ≠ 拦住删除」—— 撤回语音还走
`File.delete(voice2/<md5[0:2]>/<md5[2:4]>/msg_<imgPath>.amr)`，光 hook SQL 不够。

这条结论本来的含义是**「拦截要覆盖所有通道」**，我却读成了**「拦截这条路不可靠」**，
于是转向事后补救。可事实是：只要把 `File.delete` 也 hook 上（R21c 后来确实这么干了，
36ms 生效、闭环），拦截就是可靠的。

**一次局部失败告诉我的是「这里还有个洞」，不是「这条路不通」。我把前者当成了后者。**

## 3. 根因三：局部进展制造的「快成了」错觉

判据路线上每一轮都真有进展：发现分页预取、发现 ctTop 节流、发现私密位可分、
发现 88.6% 的 0 是历史存量。每次都有新事实，每次都像「再改一版就成了」。

这就是沉没成本的典型形态：**进展是真的，但进展的方向是错的。**
真正该问的问题不是「判据还能怎么改」，而是「我为什么需要一个判据」。

后来出现的转折点是 `SnsTimelineSourceFix.run()` 和 `reFixAfterClear()` 共用一个
`enabled()` 开关（关补位则快照停、B+ 无成员）——那已经是**结构在报警**了：
一个方案需要拆开关才能被验证，说明它自己就不自洽。我当时只是记下"要拆开关"，
没有把它当成"这个方案该放弃"的信号。

## 4. 根因四：没去看别人怎么做的 —— 最大的时间损失在这里

防朋友圈撤回不是新问题。**2017 年就有开源实现**（WechatMagician，GPL-3.0），
代码明明白白：hook `updateWithOnConflict` 的 **before**，`sourceType == 0` 时
`values.remove("sourceType")`，顺手把 `content` 改写成「已删除」提示。

我是在用户问「微X怎么做的，你能反编译吗」之后才去查的。查完到真机验证通过，**1 小时**。
如果这个检索放在 R27 拿到「写入口是 `updateWithOnConflict`」的那一刻，
R38~R41 四轮全部可以省掉。

**这是纯粹的浪费：不是因为难，是因为没查。**

而且我当时的检索顺序是错的 —— 把「反编译商业加壳模块」（微X 加壳、核心代码加密存
`assets/`、需要运行时解密）排在「找同问题的开源实现」前面。开源实现是明文、有注释、
有 issue 记录，成本低一个数量级。

## 5. 根因五：复杂本身被我当成了正确性的替代品

甲方案看起来"太简单所以不可靠"：一行 `remove`，没有快照、没有版本号、没有 epoch、
没有 `T0` 截断。而乙方案正在长成一套完整体系 —— 有台账、有迁移、有回滚、有观察态表。

**复杂给了我"我在认真做"的安全感。** 但复杂度不是质量指标，它只是成本的另一种写法。
事后看，甲的简单性正是它的优点：
- 没有额外写库 ⇒ 不会有写库引发的级联问题（R40 就因为补位写了 636 行而污染了判据）
- 没有竞态 ⇒ 不需要 350ms 静默窗这种"用时间换正确性"的补丁
- 不需要判据 ⇒ 不存在"判据塌掉"这个失效模式

## 6. 根因六：用户的暗示被当成背景音，没当成架构约束

用户早就说过两句关键的话：

> 「该功能只针对还有模块，不需要对自己生效」
> 「时间线上 1 还在，是不是模块有影响了」

第一句其实已经把验收标准说清楚了：**能看见就行**，不需要精确判定"是不是被删"。
这不是随口一提，这是把「观测需求」砍掉的明确授权 —— 我没有把它读成架构约束。

## 7. 这次做对了什么（要保留的）

1. **一听到「微X怎么做的」就立刻转去对照开源实现**，不再自己从头设计。这个反应是对的。
2. **实验设计做了单变量隔离**：关补位、只开拦截，所以"还在"这个结果不可能有第二种解释。
3. **判据字段先读源码确认语义再下结论**（`C`=含 content、`A`=含 attrBuf、`blk`=摘键成功、
   `after`=写后回查），没有靠猜。这条纪律救了我一次 —— 否则"还在"可以被解释成"UI 缓存没刷新"。
4. **拦不住的通道也留了眼睛**：`execSQL` 钩子保留，所以发现了那条未被接管的
   `sourceType & -9` 批量 SQL。如果当初为了"干净"把它一起删了，这个洞就永远看不见。

## 8. 落成规则（D 系列，进 CLAUDE.md）

- **D1｜先查后设计**：任何「要不要自己设计一套判据/体系」的问题，先花 ≤30 分钟检索
  同类开源实现与 issue。有成熟实现就直接对照；只有在明确没有时才自研。
  ⛔ 检索顺序：开源实现 → 官方文档/社区 → 商业模块反编译（加壳的最贵，排最后）。
- **D2｜路线对照表前置**：动手前必须写一张表，列「核心动作 / 代码量 / 是否额外写库 /
  竞态 / 失效场景 / 验证成本」，贴给用户选。**没有这张表不许开工。**
- **D3｜判据连塌即停**：同一判据连续两轮被证伪，禁止再改判据，强制回头问
  「是不是问题本身选错了」。判据塌往往不是判据不够好，是方向不对。
- **D4｜控制优先于观测**：能阻止事件发生，就不要先费力检测事件是否发生。
  只有在无法阻止时，才退到观测 + 补救。
- **D5｜简单方案要给出可证伪的失败条件**：不允许用"太简单了不可靠"否决方案。
  要说不可靠，就指名「在什么情况下会失效」，再去测那个情况。
  （本轮就是这样：担心"微信会覆盖回去"→ 实测 30 分钟 trace，两次重试都被拦，W1 有答案。）

## 9. 一句话

**我不是在解决"好友删了还能看见"，我是在解决"怎么知道好友删了"。
前者是一个钩子，后者是一个无底洞 —— 而我先跳进了无底洞，才回头发现门根本没锁。**
