## 0. 结论速览（TL;DR）

1. **判据层已经做完**：`SnsCommentLogic`（纯函数）把「识别删评论 SQL / attrBuf 差量 / 三种删除形态 / 正文对账 / 标签文本」全部实现并单测锁住（`SnsCommentLogicTest` 34 例）。这一层**一行都不用改**，只等取证结果填一个常量（`DELETED_FLAG_MASK`）。
2. **防删除层（`SnsCommentGuard`）已能拦 + 归档**：hook `execSQL`/`delete` 拦下 `delete from SnsComment`，整行写进 `sns_comment_archive.db`。但**attrBuf 差量还原是死的**（`AUTO_RESTORE_ATTR=false`，快照只在取证窗口里才有）。
3. **标签层（`SnsCommentTag`）骨架已搭好但落点未接线**：两个待取证常量 `PENDING_COMMENT_ROW_CLASS` / `PENDING_COMMENT_ID_METHOD` 留空 → 精确路径不生效，只剩「正文对账」降级路径。
4. **核心缺口只有一处**：`SnsCommentTag` 现在假设「评论行 View ↔ commentSvrID」能拿到（T3/T4），但**评论被删后界面上的评论行本身随 `attrBuf` 重写而消失**——没有一个"目标行"可供打标。要落地必须先解决「被删评论在界面上怎么定位 / 怎么呈现」。
5. **推荐方案**：**A（attrBuf 差量还原，让被救评论复活到界面）为主 + B（纯 UI 正文对账追加占位）兜底**。两者都绕不开**三项取证**（见第 5 节）：T2（删评论是否重写 attrBuf）、T3/T4（评论行 View ↔ commentSvrID 映射）、form（删评论后本地库形态）。

## 2. 缺口分析

### 2.1 完整链路拆解

「评论 [已删除] 标签」要跑通，需要 4 个环节：

```
[1 数据源] 哪些评论被删过
   → sns_comment_archive.db（snsId → Set<commentSvrID>）  ✅ 已就绪
[2 定位]   界面上哪条评论行对应哪个 commentSvrID
   → 精确路径(T3/T4) 或 降级路径(正文对账)                ⛔ 缺（且见 2.2 更深的坑）
[3 判据]   这条评论"是否已删"（MISSING/EMPTY/FLAGGED）
   → SnsCommentLogic.classify                              ✅ 已就绪（等 form 定形态）
[4 渲染]   往定位到的评论行插 [已删除] TextView
   → SnsCommentTag.applyLabel                               ✅ 已就绪
```

**缺的是 [2] 定位**，而且 [2] 的难度被 [2.2] 的 `attrBuf` 问题放大了一个量级。

### 2.2 「`attrBuf` 已被重写」的准确含义

这是整个任务最关键的一句，展开讲清楚微信删评论时**到底做了什么写操作**：

**✅ 已实测**（`SnsCommentGuard.kt:32-33` 头注释 + `取证结论.md` 朋友圈 #8）：
删评论的 SQL 顺序是三连写：

```
① update  SnsInfo  ...          （先把 attrBuf 重写：把要删的那条评论从可见列表里抹掉）
② replace SnsInfo  ...          （整行 replace，attrBuf 覆盖为新值）
③ execSQL "delete from SnsComment where snsID=? and commentSvrID=?"   ← 我们只拦了这个
```

**关键点**：
- 评论的**可见列表**存在 `SnsInfo.attrBuf`（protobuf BLOB，实测 235B~1069B），**不是** `SnsComment` 表。界面渲染评论读的是 `attrBuf`，`SnsComment` 是另一份明细。
- 我们现在的 `SnsCommentGuard` 只 hook 了 `execSQL`/`delete`（第 ③ 连）。**此时 attrBuf 已经被 ①② 重写完了**。
- 所以拦截后：`SnsComment` 行还在库里（内容也归档了），但界面（读 attrBuf）上**那条评论已经消失**。

**结论**：拦住 `delete SnsComment` **留不住详情页/时间线预览里那条评论的"可见性"**，因为没有"目标评论行 View"可供打标。这就是「成本高一个量级」的根源。

**一个更隐蔽的推论**（⛔ 待取证，不能当结论）：
- 现有 `SnsCommentTag` 注释（:37-38）假设「评论画在动态 item 内部的子 View 上，不是独立列表项」。**这一点本身未取证**。
- 实际上微信朋友圈有两个渲染场景：① 时间线（`ImproveSnsTimelineUI`）里动态 item 底部**预览前几条评论**；② 点进动态的**详情页**（独立评论列表）。评论 [已删除] 标签要打在哪个场景、还是两个都要，**需求未定、代码未取证**。
- 若评论是详情页里**独立的 RecyclerView item**（有独立 adapter），那 T3/T4 的取证对象、hook 点、位置对账方式都跟「动态 item 内部子 View」完全不同。**这是方案落地的第一个分叉，必须先用探针定下来。**

## 3. 差量检测方案（候选对比 + 推荐）

### 方案 A：attrBuf 差量还原（让被救评论复活到界面，再打标）

**思路**：把「防止评论撤回」补全——不只拦 `delete SnsComment`，还 hook `update`/`replace SnsInfo` 在**写之前**抓 attrBuf 快照，在 `delete SnsComment` 拦截点把 attrBuf **写回快照**，让评论重新出现在界面；然后评论行 View 存在了，走 T3/T4 精确路径（或正文对账）打标。**与动态侧「拦 + 恢复可见位」完全同构。**

**可行性**：高。框架已在 `SnsCommentGuard` 搭好 80%——`attrSnap` 容器、`tryRestoreAttr`、`planAttr` 判据、`writeAttrBuf` 写回、`traceon` 取证钩子全都有，只差：① T2 实证；② 把 `AUTO_RESTORE_ATTR` 打开；③ 把「抓快照」从取证临时钩子升级为常驻拦截。

**代价**：中。
- `update`/`updateWithOnConflict` 是微信**所有表**的写路径（message/rcontact…），常驻 hook 会给每次写库加一层开销（`SnsCommentGuard:324` 注释明说这是热路径）。需先取证「到底只有 `replace` 改 attrBuf，还是 `update` 也改」——若只有 `replace` 改，就只常驻 hook `replace`（比 update 轻）。
- attrBuf 是 protobuf，整块写回有风险（见风险）。

**风险**：中。
- 写坏 attrBuf 会把整条动态的可见评论列表搞坏（`SnsCommentGuard:284-286` 原话）。现有 `planAttr` 只看**字节数**（缩容 2K 内才 RESTORE），太粗；要安全还得取证 attrBuf 结构，做「条目级」差量。
- 语义上「评论复活了还要打 [已删除]」跟动态侧一致（动态也是复活了还打标），可接受。

### 方案 B：纯 UI 正文对账 + 评论区追加占位（不碰 attrBuf）

**思路**：不动 attrBuf，让被删评论"消失就消失"。在 `onBindViewHolder` 回调里拿到 `snsId`（已能拿到），查归档该动态有哪些已删评论（正文），遍历 itemView 现有 TextView 文案对账，找出「**归档里有、界面上没有**」的评论 → 在**评论区容器末尾追加一个 `[已删除]` 占位 TextView**（不追求还原到原位置，只标记"这里曾有一条被删评论"）。

**可行性**：中。它是 `SnsCommentTag` 现有降级路径（`markByText` :310）的变体——现有降级路径是「命中的行打标」，本方案要改成「**未命中**的归档评论追加占位」。依赖：评论区容器 View 类名（待取证，与 T3 重叠）。

**代价**：低。纯 UI 层，不写微信库，不动 attrBuf，无热路径 hook。

**风险**：中。
- 位置不精确（只能追加到评论区末尾，评论顺序会乱、且无法标在"原位置"）。
- 正文对账的误判风险（`textHit` 是近似切片，打错标签比不打糟）。需 `SnsCommentLogic.textHit` 严格判据兜底。
- 「归档有、界面无」也可能因为评论本就没渲染（如折叠、分页），误判成"被删"。

### 方案 C：利用 `SnsComment` 的 `commentflag` 标志位

**思路**：假设删评论不是物理 DELETE，而是置 `commentflag`（或 `isSilence`/`msgRelevanceType`）某一位；则 `classify` 走 `FLAGGED` 分支，行还在、界面也还在，直接打标。

**可行性**：**低**。✅ 已实测删评论是物理 `DELETE`（`execSQL delete from SnsComment`），行被抹掉，`FLAGGED` 形态大概率不成立。除非 `form` 探针证伪"物理删除"（即行还在、被置了 flag）。

**代价**：低。只读 `commentflag`，填 `DELETED_FLAG_MASK` 常量即可。

**风险**：大概率无效，只能作为 form 取证后的意外惊喜，不能作为主方案。

| 方案 | 可行性 | 代价 | 风险 | 依赖取证 |
|---|---|---|---|---|
| A. attrBuf 差量还原 | 高（框架 80% 就绪） | 中（常驻 hook update/replace + protobuf 写回） | 中（写坏 attrBuf 搞坏评论列表） | T2 + attrBuf 结构 + T3/T4 |
| B. 纯 UI 对账 + 追加占位 | 中 | 低 | 中（位置不准/误判） | 评论区容器 + T3 相关 |
| C. commentflag 标志位 | 低（实测是物理删） | 低 | 低（大概率无效） | form |

### 推荐

**A 为主，B 兜底，C 待 form 取证定夺。**

- **首选 A**：与动态侧「拦 + 恢复可见」完全同构，工程心智一致，且 `SnsCommentGuard` 的 `tryRestoreAttr`/`attrSnap`/`writeAttrBuf`/`traceon` 骨架已搭好，落地成本主要是**取证 + 打开开关 + 把抓快照常驻化**。
- **B 作为 A 的降级**：若 T2 取证发现「attrBuf 写回风险不可控」或「评论渲染场景特殊（如详情页独立列表无法精确还原）」，退到 B——只标记"这里曾有被删评论"，不强求还原原位置。
- **C 是被动选项**：`form` 探针跑完，若发现删评论其实是置 flag 而非物理删（与当前实测相悖，概率低），则最省事——填 `DELETED_FLAG_MASK` 即可，A/B 都不需要。

**为什么 A 仍是首选而非直接选 B（更省事）**：需求语义是「显示评论[已删除]标签」，B 只能追加一个"漂浮的占位"，位置错、且无法精确到"是哪条评论、评论者是谁"。A 能让评论复活到原位置，标签打上去就是准确的「`昵称：[已删除]`」（`labelText` 支持昵称）。两者质量差一个档次。

## 6. 纯逻辑单测设计

`matchDeleteSql` / `matchDeleteCall` / `snsIdOf` / `planAttr` / `classify` / `isDeleted` / `labelText` / `textCandidates` / `textHit` / `key` / `hex`——均已单测（`SnsCommentLogicTest`）。

### 6.2 建议新增：attrBuf 条目级差量（方案 A 安全写回的前提）

当前 `planAttr` 只按**字节数**缩容判定，太粗。取证到 attrBuf 结构后，建议抽：

```kotlin
/** 估算 attrBuf 里的评论条目数。null = 无法估算（结构不认得，宁可不写回）。 */
fun attrEntryCount(blob: ByteArray?): Int?

/** 条目级差量：old 比 new 少了几条、是否"只少了"（没有新增/变更）。 */
data class AttrDiff(
    val oldEntries: Int?, val newEntries: Int?,
    val shrinkBy: Int,       // 条目减少数；无法估算时为 -1
    val safeToRestore: Boolean,
)
fun diffAttr(old: ByteArray?, new: ByteArray?): AttrDiff
```

**测试用例**（取证到结构后按真实字节补）：
- 正常多条目 blob → `attrEntryCount` 返回正确条数。
- 空 blob / 全噪声 → 返回 null。
- 减少 1 条 → `safeToRestore=true`。
- 减少多条第**同时新增**（新评论插入）→ `safeToRestore=false`（覆盖会抹掉新评论）。
- 无法估算 → `safeToRestore=false`（保守不写）。

### 6.3 建议新增：方案 B 的「归档有、界面无」判定

```kotlin
/** 归档正文候选里，哪些没有在界面现有文案里命中（= 被删/未渲染）。 */
fun missingComments(
    archivedCands: List<List<String>>,   // 每条已删评论一个 List<String>
    visibleTexts: List<String>,          // 界面 itemView 现有 TextView 文案
): List<List<String>>
```

**测试用例**：
- 全部命中 → 返回空。
- 部分命中 → 只返回未命中的候选。
- 2 字碎片文案（`textHit` 的严格边界）→ 不算命中，进返回集。
- 空输入 → 空返回。
- 未命中但界面文案为空（评论折叠/未渲染）→ 标注为"待确认"（返回集可带标志，避免误判成被删）。

### 6.4 建议新增：定位增强（从 boolean 到下标）

现有 `textHit` 只返回 boolean，方案 B/精确路径要「定位到哪一行」时不够：

```kotlin
/** 返回第一个命中的 visibleTexts 下标；多候选歧义（匹配到多行）时返回 -1（不猜）。 */
fun firstHitIndex(cands: List<String>, texts: List<String>): Int
```

**测试用例**：
- 唯一命中 → 返回正确下标。
- 两行都命中 → -1（歧义，宁可不打）。
- 无命中 → -1。
- 短碎片命中 → 不认（沿用 `textHit` 严格规则）。
